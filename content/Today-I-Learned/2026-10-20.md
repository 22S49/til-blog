# `useEffect(콜백함수, [...])`
- 시점별로 실행되는 훅 (비동기식)
- 어느 시점에 실행되는가? 컴포넌트가 렌더링을 완료하면 호출된다. 
	- 호출 단위 ─ 컴포넌트 
	- 사용 환경
		1. 원격 데이터 조회
		2. DOM 선택
		3. Native 이벤트 바인딩
- 배열 자리는 의존성을 의미
	- 배열에 요소가 없으면 ─ 컴포넌트 렌더링 후 1번 콜백함수 호출 → 초기 작업에 활용
	- 배열에 요소가 있으면 ─ 의존성 값이 변경되면 콜백함수 재호출
```jsx
useEffect(() => {
    if (state.success) {
        alert(state.message);
        router.push('/');
        router.refresh(); // csr 방식이기 때문에 화면만 바뀜 → 지정 갱신
    }
}, [state.success, state.message, router]);
// state.success 상태가 변경되면 state.message가 실행되고 router 실행
```

## useState vs useEffect

||useState|useEffect|
|---|---|---|
|역할|컴포넌트가 기억하는 값(상태) 보관|렌더링 이후에 실행할 부수효과 등록|
|반환값|`[값, setter]`|없음 (cleanup 함수를 반환할 수는 있음)|
|호출 시점|렌더링 중|렌더링과 화면 반영이 끝난 뒤|
|결과|setter를 호출하면 리렌더링 발생|리렌더링을 직접 일으키지 않음 (안에서 setState를 하면 일으킴)|

```tsx
const [count, setCount] = useState(0);        // 기억하는 값

useEffect(() => {
  document.title = `count: ${count}`;          // 렌더 밖의 세계(DOM, 네트워크, 타이머)와 동기화
}, [count]);
```

- **useState**는 화면에 보여줄 데이터를 다룹니다.
- **useEffect**는 React 바깥과 동기화할 때 씁니다. 예로는 API 호출, 이벤트 리스너 등록, 타이머, `document.title` 변경이 있습니다.
- 렌더링 중에는 계산만 하고(순수하게), 바깥 세계를 건드리는 일은 effect로 보냅니다.

**모든 훅에 배열이 있는 것은 아닙니다.** 의존성 배열이 있는 훅은 아래와 같습니다.

|훅|형태|배열의 의미|
|---|---|---|
|`useEffect(fn, deps)`|효과 실행|deps가 바뀌면 effect를 다시 실행|
|`useLayoutEffect(fn, deps)`|효과 실행 (페인트 전)|위와 동일|
|`useMemo(fn, deps)`|값 캐싱|deps가 바뀌면 값을 다시 계산|
|`useCallback(fn, deps)`|함수 캐싱|deps가 바뀌면 함수를 새로 생성|

의존성 배열의 동작은 이렇습니다.

- `[]`: 마운트 시 한 번만 실행합니다.
- `[a, b]`: 마운트 시, 그리고 a나 b가 바뀔 때 실행합니다.
- 배열을 생략하면 매 렌더링마다 실행합니다.

배열이 없는 훅도 있습니다.

- `useState(초기값)`, `useRef(초기값)`, `useContext(Ctx)`, `useReducer(reducer, 초기값)`은 인자가 초기값이나 대상입니다.

공통점은 "훅은 컴포넌트 최상위에서, 항상 같은 순서로 호출해야 한다"는 규칙입니다. React가 호출 순서로 각 훅의 상태를 구분하기 때문에, 조건문이나 반복문 안에서 호출하면 안 됩니다. 인자 구조가 같은 것은 아닙니다.


동기식 
- useInsertionEffect
	- DOM 변경 후 레이아웃 계산 전
- useLayoutEffect
	- DOM 변경 후 레이아웃 계산 직후 (렌더링 전)

useRouter()
- window.location 객체와 비슷한 역할
- CSR 방식으로 동작: 실제 페이지 이동이 아니라 history 이력을 이용해서 동작
- 화면을 갱신하는 것이 아니라 화면을 교체 (화면 이동 없이 화면 교체)
- 방문 기록을 남기지 않는 이동 ─ replace 메서드
- 방문 기록을 남기는 이동 ─ push 메서드
- 새로고침 ─ refresh 메서드





## DOM → 레이아웃 계산 → 렌더링

**브라우저가 화면을 그리는 과정**입니다. React의 "렌더링"과는 다른 개념입니다.

1. **DOM 생성**: HTML을 파싱해서 DOM 트리를 만듭니다. CSS는 CSSOM 트리로 만듭니다.
2. **Render Tree**: DOM과 CSSOM을 합칩니다. 보이는 요소만 포함하므로 `display: none`은 제외됩니다.
3. **Layout (Reflow)**: 각 요소의 크기와 위치를 계산합니다. 너비, 높이, 위치 같은 기하 정보가 여기서 정해집니다.
4. **Paint**: 색, 텍스트, 그림자, 테두리 등을 픽셀로 칠합니다.
5. **Composite**: 여러 레이어를 합성해서 화면에 표시합니다.

성능 관점에서는 이렇습니다.

- 너비나 위치를 바꾸면 Layout, Paint, Composite를 모두 다시 거쳐서 가장 비쌉니다.
- 배경색만 바꾸면 Layout은 건너뛰고 Paint부터 다시 합니다.
- `transform`이나 `opacity`는 Composite만 거쳐서 가장 싸고, 그래서 애니메이션에 권장됩니다.

**React와 연결하면** 이렇습니다.

- React의 렌더링은 컴포넌트 함수를 실행해서 UI가 어때야 하는지 계산하는 단계입니다. 아직 화면은 아닙니다.
- 그다음 commit 단계에서 React가 DOM을 실제로 수정합니다.
- 그러고 나서 브라우저가 위의 Layout, Paint 과정을 진행합니다.
- `useLayoutEffect`는 DOM 수정 후 Paint 전에 실행되어 요소 크기를 측정할 때 씁니다. `useEffect`는 Paint 이후에 실행됩니다.

## 최초 로드 때의 전체 그림

처음 페이지를 열 때는 앞에 단계가 붙습니다.

```
HTML 다운로드 → DOM 파싱 + CSSOM 생성 → JS 번들 로드/실행
   → React 첫 Render → 첫 Commit(DOM 생성) → useLayoutEffect
   → 브라우저 Layout/Paint → 화면 표시 → useEffect
```

## 한 줄 요약

|구분|누가|하는 일|
|---|---|---|
|Render|React|무엇을 그릴지 계산 (메모리상)|
|Commit|React|DOM에 반영|
|Layout, Paint, Composite|브라우저|크기와 위치를 계산하고 픽셀로 그림|
|useLayoutEffect|React|Commit 직후, Paint 전|
|useEffect|React|Paint 후 (보통)|

React의 "렌더링"은 계산이고, 브라우저의 "렌더링"은 그리기입니다. 두 용어가 같은 단어를 쓰기 때문에 헷갈리기 쉽습니다.


같은 단어를 쓰지만 가리키는 대상이 다릅니다.

||React의 렌더|브라우저의 렌더|
|---|---|---|
|하는 일|컴포넌트 함수를 실행해 UI 설명(Virtual DOM)을 계산|DOM을 바탕으로 화면에 픽셀을 그림|
|실행 주체|React (JavaScript)|브라우저 엔진|
|결과물|JS 객체 (메모리상의 데이터)|화면에 보이는 이미지|
|화면 변화|없음|있음|
|DOM 접근|건드리지 않음|DOM을 읽어서 사용|

둘의 관계는 이렇습니다.

```
React 렌더(계산) → React Commit(DOM 수정) → 브라우저 렌더(Layout/Paint)
```

- React 렌더가 일어났다고 해서 브라우저가 반드시 다시 그리는 것은 아닙니다. 렌더 결과가 이전과 같으면 Commit에서 DOM을 바꾸지 않고, 그러면 브라우저는 다시 그릴 것이 없습니다.
- 반대로 브라우저가 다시 그리는 것(스크롤, CSS hover 등)은 React 렌더 없이도 일어납니다.

그래서 "리렌더링이 많아서 느리다"고 할 때는 보통 React 쪽 계산 비용(함수 실행, diff)을 말합니다. "리페인트나 리플로우가 많아서 느리다"고 할 때는 브라우저 쪽 비용을 말합니다. 둘은 원인도 해결책도 다릅니다. 예를 들어 React 쪽은 `memo`나 `useMemo`로 줄이고, 브라우저 쪽은 `transform`을 쓰거나 Layout을 건드리는 속성을 줄여서 해결합니다.

## 전체 흐름: 이벤트에서 화면 반영까지

```
 ① 트리거
    클릭 등 이벤트 → setState() 호출
          │
          ▼
┌─────────────────────────────────────────────┐
│ ② React Render 단계  (JS 실행, 화면 변화 없음)  │
│   컴포넌트 함수 실행 → 새 Virtual DOM 생성       │
│   이전 Virtual DOM과 비교(diff) → 바뀐 부분 계산 │
└─────────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────────┐
│ ③ React Commit 단계  (JS 실행, 동기)           │
│   바뀐 부분만 실제 DOM에 반영                    │
│   └ useLayoutEffect 실행 (cleanup 먼저)        │
└─────────────────────────────────────────────┘
          │   JS 실행이 끝나고 브라우저에 제어권이 넘어감
          ▼
┌─────────────────────────────────────────────┐
│ ④ 브라우저 렌더링 파이프라인                     │
│   Style 계산  (DOM + CSSOM → Render Tree)     │
│   Layout      (크기와 위치 계산)               │
│   Paint       (픽셀 칠하기)                    │
│   Composite   (레이어 합성 → 화면 표시)         │
└─────────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────────┐
│ ⑤ useEffect 실행  (화면이 그려진 뒤)            │
│   API 호출, 이벤트 등록, 타이머 등               │
│   (setState를 하면 ②로 돌아가 다시 반복)         │
└─────────────────────────────────────────────┘
```

## 단계별 설명

**① 트리거**: 상태 변경이 출발점입니다. 첫 진입 때는 `root.render()`가 출발점입니다.

**② Render 단계**: React가 컴포넌트 함수를 호출해서 "UI가 어때야 하는지"를 객체(Virtual DOM)로 만듭니다.

- 이 단계에서는 DOM을 건드리지 않습니다.
- 그래서 렌더링 중에는 계산만 하고, 부수효과는 하면 안 됩니다.

**③ Commit 단계**: diff 결과를 실제 DOM에 한 번에 반영합니다.

- 이 시점에 DOM은 이미 바뀌어 있지만, 화면에는 아직 반영되지 않았습니다.
- `useLayoutEffect`가 여기서 동기적으로 실행되어 바뀐 DOM의 크기와 위치를 읽을 수 있습니다. 예를 들면 툴팁 위치 계산입니다.
- 여기서 상태를 바꾸면 사용자가 깜빡임 없이 최종 결과만 보게 됩니다. 반면 너무 무거운 작업을 하면 화면 표시가 지연됩니다.

**④ 브라우저 파이프라인**: JS 실행이 끝나야 브라우저가 화면을 갱신할 수 있습니다.

- DOM이 바뀌었으므로 필요한 만큼 Style, Layout, Paint, Composite를 다시 수행합니다.
- 바뀐 속성에 따라 어디까지 다시 하는지가 달라집니다. 크기와 위치는 Layout부터, 색은 Paint부터, `transform`과 `opacity`는 Composite만 다시 합니다.

**⑤ useEffect**: 화면이 그려진 뒤 실행되므로 사용자가 보는 화면을 막지 않습니다.

- 데이터 fetch, 구독, 타이머처럼 화면 표시를 지연시키면 안 되는 작업이 여기에 해당합니다.
- 클릭 같은 사용자 입력에서 시작된 업데이트는 React가 effect를 Paint 전에 실행하기도 합니다. "항상 Paint 이후"라고 외우기보다 "화면 표시를 막지 않도록 미뤄진다"라고 이해하는 편이 정확합니다.


## 4. 순수 DOM 방식(Vanilla JS)

React 없이 브라우저 API로 DOM을 직접 조작하는 방식입니다.

```js
const btn = document.querySelector('#btn');
const label = document.querySelector('#label');
let count = 0;

btn.addEventListener('click', () => {
  count++;
  label.textContent = `count: ${count}`;   // "어떻게" 바꿀지 직접 명령
});
```

||순수 DOM (명령형)|React (선언형)|
|---|---|---|
|사고방식|"이 요소를 찾아서 이렇게 바꿔라"|"상태가 이러면 UI는 이렇게 생겼다"|
|상태와 UI 동기화|개발자가 직접 맞춤 (빠뜨리면 버그)|React가 자동으로 맞춤|
|규모가 커지면|상태와 DOM이 꼬이기 쉬움|컴포넌트로 관리|
|업데이트|내가 바꾼 부분만 정확히 수정|Virtual DOM으로 diff해서 바뀐 부분만 반영|

순수 DOM이 나쁜 것은 아닙니다. 작은 페이지에서는 오히려 빠르고 가볍습니다. React가 해결하는 문제는 UI가 복잡해질수록 "상태가 바뀔 때 DOM의 어느 부분을 고쳐야 하는지" 직접 추적하기 어렵다는 점입니다.

`useRef`로 DOM에 직접 접근하거나 `useEffect`에서 `document.title`을 바꾸는 것이 React 안에서 순수 DOM 방식을 쓰는 예입니다. 이처럼 React가 관리하지 않는 영역에서만 제한적으로 씁니다.


## 'use server'가 파일에 하는 일

`'use server'`를 파일 맨 위에 쓰면, 그 파일에서 export하는 함수는 전부 Server Action으로 취급됩니다. Server Action은 브라우저가 네트워크로 호출할 수 있는 공개 엔드포인트가 됩니다. 그래서 Next.js는 이런 규칙을 둡니다.

- export는 **async 함수만** 가능합니다.
- 상수나 객체, 동기 함수는 export할 수 없습니다.

```ts
'use server'
export const getCurrentUser = cache(async () => {...})
//                            ↑ cache()가 반환하는 건 async 함수 자체가 아니라 래퍼 함수
```

`cache()`로 감싼 값이 이 규칙을 통과할지는 Next.js 버전과 검사 방식에 따라 다릅니다. 그래서 어떤 환경에서는 조용히 넘어가고, 어떤 환경에서는 빌드나 실행 때 오류가 납니다. 이렇게 "되다가 갑자기 안 되는" 상태가 더 위험해서 지시어를 뺀 겁니다.


## 기본 관례

|계층|표기|예시|
|---|---|---|
|JavaScript/TypeScript 코드 (변수, 함수, 객체 키, 타입 속성)|**camelCase**|`createdAt`, `getCurrentUser`|

|DB 컬럼, 테이블 (PostgreSQL, Supabase)|**snake_case**|`created_at`, `deleted_at`|
|Python, Ruby, Rust 코드|**snake_case**|`created_at`|
|상수|**UPPER_SNAKE_CASE**|`MAX_RETRY`|
|CSS 클래스, URL, 파일명|**kebab-case**|`sign-in`, `text-center`|

전통적인 **서버 세션 방식**과, Supabase가 쓰는 **토큰(JWT) 방식**입니다. 둘 다 쿠키를 쓰기 때문에 헷갈리기 쉽습니다. 앞에서 말한 "세션"은 사실 후자입니다.

## 1. 전통적인 서버 세션 방식

```
브라우저                              서버                    세션 저장소(DB/Redis)
   │  ① POST /login (id, pw)          │                          │
   │ ───────────────────────────────▶ │  비밀번호 검증            │
   │                                  │  ② 세션 생성 ───────────▶ │ { sid: abc123, userId: 7 }
   │  ③ Set-Cookie: sid=abc123        │                          │
   │ ◀─────────────────────────────── │                          │
   │                                  │                          │
   │  ④ GET /mypage (Cookie: sid=abc123)                         │
   │ ───────────────────────────────▶ │  ⑤ sid로 조회 ─────────▶ │
   │                                  │ ◀─ userId: 7 ─────────── │
   │  ⑥ 마이페이지 응답                │                          │
   │ ◀─────────────────────────────── │                          │
```

- 쿠키에는 의미 없는 **세션 ID**만 들어 있습니다. 사용자 정보는 모두 서버에 있습니다.
- 서버가 세션 저장소를 보유하므로 로그아웃이나 강제 만료를 즉시 처리할 수 있습니다. 세션을 삭제하면 끝입니다.
- 단점은 요청마다 저장소를 조회해야 하고, 서버가 여러 대면 저장소를 공유해야 한다는 것입니다.

## 2. 토큰(JWT) 방식

```
브라우저                                      서버
   │  ① 로그인 요청                            │
   │ ────────────────────────────────────────▶ │  검증 후 JWT 서명해서 발급
   │  ② access token(짧은 수명) + refresh token │
   │ ◀──────────────────────────────────────── │
   │                                           │
   │  ③ 요청마다 access token 첨부              │
   │ ────────────────────────────────────────▶ │  서명만 검증 (저장소 조회 불필요)
```

- **JWT**는 사용자 ID, 만료 시간 등이 담긴 토큰이고, 서버의 비밀키로 서명되어 있어 위조하면 검증에서 걸립니다.
- 서버가 상태를 저장하지 않아도 됩니다(stateless).
- 단점은 발급한 토큰을 만료 전에 무효화하기 어렵다는 것입니다. 그래서 access token은 짧게(예: 1시간) 두고, 만료되면 **refresh token**으로 새로 받습니다.

||서버 세션|JWT 토큰|
|---|---|---|
|쿠키 내용|세션 ID|토큰 자체|
|상태 저장|서버|클라이언트|
|즉시 로그아웃|쉬움|어려움 (만료 대기)|
|확장성|저장소 공유 필요|유리|

## 3. Supabase는 어디에 해당하나

Supabase는 **JWT 방식**입니다. 로그인하면 access token과 refresh token을 발급하고, 이 묶음을 supabase-js가 "session"이라고 부릅니다.

저장 위치는 환경에 따라 다릅니다.

- 순수 클라이언트라면 localStorage에 저장합니다.
- Next.js SSR이라면 `@supabase/ssr`이 **쿠키에 저장**합니다. 서버가 읽어야 하기 때문입니다.

즉 "쿠키에 담긴 JWT를 서버가 읽는" 구조이고, 쿠키는 전달 수단입니다.

## 4. Next.js + Supabase에서의 실제 흐름

```
① 로그인 (Server Action)
   supabase.auth.signInWithPassword() → 토큰 발급 → 쿠키에 저장(Set-Cookie)

② 이후 모든 요청
   브라우저가 쿠키를 자동 첨부

③ middleware
   쿠키에서 토큰 확인 → 만료됐으면 refresh token으로 갱신 → 쿠키 업데이트

④ Server Component / Action
   supabase.auth.getUser() → 로그인 사용자 확인 → 데이터 조회

⑤ 로그아웃
   supabase.auth.signOut() → 쿠키 삭제
```

## 5. 보안 포인트

쿠키 옵션이 중요합니다.

|옵션|역할|
|---|---|
|`HttpOnly`|JS에서 쿠키를 읽을 수 없게 해서 XSS로 토큰이 탈취되는 것을 막음|
|`Secure`|HTTPS에서만 전송|
|`SameSite=Lax`|다른 사이트에서 오는 요청에 쿠키를 제한해 CSRF를 완화|

참고로 `@supabase/ssr`의 브라우저 클라이언트는 클라이언트에서도 세션을 읽어야 해서 쿠키를 `HttpOnly`로 만들지 않는 것이 기본입니다. XSS에 대한 방어(입력 이스케이프, CSP 등)가 그만큼 중요합니다.

또 하나는 앞서 말한 `getUser()`와 `getSession()`의 차이입니다. 쿠키는 사용자가 조작할 수 있는 값이므로 서버에서 신원을 판단할 때는 `getUser()`로 검증해야 합니다.

## 한 줄 요약

- **서버 세션**: 쿠키에 번호표(ID)를 넣고, 서버가 그 번호표의 주인을 기억합니다.
- **JWT 토큰**: 쿠키에 서명된 신분증(토큰)을 넣고, 서버는 서명만 확인합니다.
- **Supabase + Next.js**: 신분증(JWT)을 쿠키에 담아 서버와 클라이언트가 함께 씁니다.


## 판단 기준: 코드가 어디서 실행되어야 하는가

||실행 위치|선언하는 곳|
|---|---|---|
|(아무것도 안 씀)|**서버** (Server Component, 기본값)|-|
|`'use client'`|**브라우저** (Client Component)|컴포넌트 파일 맨 위|
|`'use server'`|**서버** (Server Action: 브라우저에서 호출하는 서버 함수)|액션 파일 맨 위 또는 함수 안|

App Router에서는 **모든 컴포넌트가 기본적으로 서버 컴포넌트**입니다. 그래서 `'use server'`를 컴포넌트에 붙이는 것이 아니라, 필요할 때만 `'use client'`를 붙입니다.

## 1. `'use client'`를 쓰는 때

브라우저에서만 가능한 기능이 필요할 때 씁니다.

- `useState`, `useEffect`, `useActionState` 같은 훅
- `onClick`, `onChange` 같은 이벤트 핸들러
- `window`, `localStorage` 같은 브라우저 API
- 브라우저 전용 라이브러리

```tsx
'use client'
export default function SignInForm() {
  const [state, formAction] = useActionState(signIn, null)   // 훅 → client 필요
  return <form action={formAction}>...</form>
}
```

## 2. `'use server'`를 쓰는 때

**브라우저에서 서버 코드를 호출**해야 할 때 씁니다. 폼 제출이나 DB 쓰기 같은 변경 작업이 대표적입니다.

```ts
// domains/auth/actions/signin.actions.ts
'use server'                       // 이 파일의 export 함수는 전부 Server Action
export async function signIn(prev, formData: FormData) {
  const supabase = await createServerClient()
  // 서버에서 실행됨 → 비밀키, DB, 쿠키 접근 가능
}
```

클라이언트 컴포넌트가 이 함수를 import해서 호출하면, 실제로는 네트워크 요청이 서버로 가서 실행되고 결과만 돌아옵니다.

## 3. 아무것도 안 쓰는 때 (서버 컴포넌트)

데이터를 읽어서 보여주기만 하고 상호작용이 없을 때입니다.

```tsx
// app/(todo)/page.tsx  (지시어 없음 = 서버 컴포넌트)
export default async function Page() {
  const user = await getCurrentUser()    // 서버에서 직접 조회
  return <h1>{user.email}</h1>
}
```

DB나 Supabase를 직접 호출할 수 있고, 이 코드는 브라우저로 전송되지 않습니다.

## 4. 헷갈리는 포인트

**`'use server'`는 "서버 컴포넌트 표시"가 아닙니다.** 서버 컴포넌트는 지시어가 필요 없고, `'use server'`는 Server Action(함수)에만 씁니다.

**`'use client'`는 경계를 만듭니다.** 이 파일과 여기서 import하는 모든 것이 클라이언트 번들에 들어갑니다. 그래서 가능한 한 작은 컴포넌트에만 붙이는 것이 좋습니다. 페이지 전체가 아니라 버튼이나 폼 부분에만 붙이는 식입니다.

**서버 코드를 클라이언트가 import하면 안 됩니다.** 서버 전용 코드(service_role 키, DB 접근 등)는 `'use client'` 파일에서 import하지 마세요. 키가 노출될 수 있습니다.

## 5. 판단 플로우

```
이 코드가 사용자 입력/브라우저 기능(훅, 이벤트)을 쓰나?
 ├─ 예 → 'use client'
 └─ 아니오
      └─ 폼 제출/데이터 변경처럼 브라우저가 서버 함수를 호출해야 하나?
           ├─ 예 → 그 함수를 'use server' 파일에 작성
           └─ 아니오 → 지시어 없이 서버 컴포넌트로 (데이터 조회·표시)
```


## 컴포넌트 안에서는 문제가 없었을까

컴포넌트 안에서 직접 쓰면 `useState`를 바로 호출하게 됩니다.

```tsx
const [form, setForm] = useState(initialForm);
//     ↑ FormType   ↑ 함수
```

`useState`의 반환 타입은 React가 이미 **튜플** `[S, Dispatch<...>]`로 정의해 두었습니다. 그래서 첫 번째 칸은 `FormType`, 두 번째 칸은 함수로 칸마다 타입이 정해져 있습니다.

## 훅으로 분리하면 왜 달라질까

`useFormState`는 직접 만든 함수라서, 반환 타입을 TypeScript가 `return` 문을 보고 추론합니다. 이때 배열 리터럴 `[a, b]`는 기본적으로 **튜플이 아니라 일반 배열**로 추론됩니다.

```ts
return [form, onChange]            // 추론: (FormType | 함수)[]   ← 칸 구분이 사라짐
return [form, onChange] as const   // 추론: readonly [FormType, 함수]  ← 칸마다 고정
```

즉 "할당하니까 괜찮다"가 아니라, 직접 쓰면 React가 타입을 정의해 줬고 직접 만들면 내가 정의해야 한다는 차이입니다.

## 정리

||반환 타입을 누가 정하나|
|---|---|
|`useState(...)` 직접 사용|React의 타입 정의 (이미 튜플)|
|직접 만든 커스텀 훅이 배열을 반환|TypeScript 추론 (일반 배열이 됨) → `as const`나 반환 타입 명시 필요|

해결 방법은 두 가지입니다.

```ts
// 1) as const
return [form, onChange] as const;

// 2) 반환 타입을 직접 명시
function useFormState<T>(initialState: T): [T, (e: ChangeEvent<HTMLInputElement>) => void] {
```

이 문제는 훅이 배열을 반환할 때만 생깁니다. **객체로 반환하면** 키 이름으로 구분되어서 `as const` 없이도 타입이 정확합니다.

```ts
return { form, onChange };
const { form, onChange } = useFormState(initialForm);   // 이름으로 꺼내므로 안전
```

`useState`처럼 이름을 마음대로 붙이고 싶을 때는 배열이 편하고, 안전함을 우선하면 객체가 편합니다. 이 프로젝트에서는 `as const`면 충분합니다.

## 왜 오류가 있어도 돌아가나

TypeScript는 **코드를 실행하기 전에 검사만 하는 도구**입니다. 실행될 때는 타입이 전부 지워진 JavaScript만 남습니다.

```
TS 코드 → (타입 검사: 오류 표시) → 타입 제거 → JS 실행
                 ↑ 여기서 오류가 나도 JS 변환 자체는 진행됨
```

`return [form, onChange]`는 JS에서 실제로 `[객체, 함수]` 배열이고, 구조 분해를 하면 값은 정확히 들어갑니다. 타입이 틀렸다고 값이 틀린 것은 아닙니다. 오류는 "TypeScript가 그 사실을 추론하지 못했다"는 뜻일 뿐입니다.

그래서 개발 서버(`next dev`)는 에디터에 빨간 줄이 있어도 계속 실행됩니다. 개발 중에는 타입 검사로 서버를 멈추지 않기 때문입니다.

## 그래도 고쳐야 하는 이유

- **`next build`에서 실패합니다.** 배포 빌드는 기본적으로 타입 오류가 있으면 중단됩니다. 개발 때는 되다가 배포에서 막히는 상황이 생깁니다.
- **자동완성과 안전망이 사라집니다.** `form.`을 쳐도 `email`, `password`가 제안되지 않고, 오타를 내도 잡아주지 않습니다.
- **오류가 쌓이면 진짜 오류가 묻힙니다.** 빨간 줄이 늘 있으면 새로 생긴 중요한 오류를 놓치게 됩니다.

## 1. "layout"이라는 단어가 세 군데서 다르게 쓰인다

||의미|어디 소속|
|---|---|---|
|브라우저 Layout (reflow)|요소의 크기와 위치를 계산하는 단계|브라우저 렌더링 파이프라인|
|`useLayoutEffect`의 layout|위 Layout 계산이 쓰는 DOM 정보를 읽는 시점|React 훅|
|`layout.tsx`, `revalidatePath(..., 'layout')`|여러 페이지가 공유하는 껍데기 컴포넌트|Next.js 라우팅 구조|

`revalidatePath`의 layout은 파일 이름(`layout.tsx`)에서 온 말입니다. 화면 배치 계산(reflow)과는 아무 관련이 없습니다.

## 2. 연결되는 지점: 파이프라인의 맨 앞

`revalidatePath`는 앞에서 본 흐름보다 **더 앞단**에서 일어나는 일입니다.

```
[서버] 데이터/페이지 캐시 무효화  ← revalidatePath가 하는 일
   │
   ▼
[서버] 서버 컴포넌트를 다시 실행해서 새 결과(RSC payload) 생성
   │
   ▼
[브라우저] React Render → Commit(DOM 수정) → Layout → Paint ...   ← 앞에서 본 흐름
```

즉 `revalidatePath`는 "서버에서 어떤 결과를 다시 만들지"를 정하고, 그 새 결과가 브라우저로 와서 우리가 본 렌더링 파이프라인을 타는 겁니다.

## 3. revalidatePath('/')는 무엇을 지우나

이 프로젝트에 설치된 Next.js 문서([revalidatePath.md](vscode-webview://0vfje8hu9hbcg5hgpddts3ovr8jokcgt8rff7uhplo8p71965k09/09_nextjs_assignment-main/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md))를 확인했습니다.

```ts
revalidatePath(path, type?)   // type: 'page' | 'layout'
```

- `revalidatePath('/')`: 경로가 `/`인 **그 페이지 하나**만 대상입니다.
- `revalidatePath('/', 'layout')`: `/` 아래의 **레이아웃과 중첩 레이아웃, 그 아래 모든 페이지**가 대상입니다.

그래서 코드 주석의 "모든 경로의 캐시 삭제"는 **`'layout'`을 붙였을 때만** 맞습니다. 문서에도 전체 무효화는 `revalidatePath('/', 'layout')`로 안내되어 있습니다.

## 4. 왜 레이아웃을 지워야 하나

Next.js는 페이지 이동 때 **바뀐 부분만 다시 렌더링**합니다. 공통 레이아웃은 이동해도 다시 그리지 않고 재사용합니다.

```
app/layout.tsx              ← 공통 (Header 등)
└─ (todo)/layout.tsx        ← 공통
     ├─ page.tsx            ← /
     ├─ sign_in/page.tsx    ← /sign_in
     └─ sign_up/page.tsx    ← /sign_up
```

로그인한 사용자 정보(`getCurrentUser`)를 레이아웃의 Header가 읽는다면 이런 일이 생깁니다.

1. 로그인 성공 후 `revalidatePath('/')`로 `/` 페이지만 갱신합니다.
2. 페이지 본문은 새 데이터지만, 레이아웃에 있는 Header는 재사용되어 **로그아웃 상태 그대로**입니다.

그래서 로그인과 로그아웃처럼 **레이아웃에 영향을 주는 변경**에는 `revalidatePath('/', 'layout')`을 씁니다.

## 5. 이 프로젝트에 적용하면

[signin.actions.ts](vscode-webview://0vfje8hu9hbcg5hgpddts3ovr8jokcgt8rff7uhplo8p71965k09/09_nextjs_assignment-main/domains/auth/actions/signin.actions.ts)에서 로그인이 성공한 뒤에 호출합니다.

```ts
import { revalidatePath } from 'next/cache'

// ... 로그인 성공 처리 후
revalidatePath('/', 'layout')
return { success: true, message: '로그인 성공' }
```

참고로 문서에 이런 설명도 있습니다. Server Function에서 호출하면 지금은 이전에 방문한 모든 페이지도 다시 방문할 때 새로 불러온다고 합니다(임시 동작이라고 명시됨). 그래서 `'/'`만 써도 어느 정도 갱신되는 것처럼 보일 수 있지만, 의도를 분명히 하려면 `'layout'`을 쓰는 게 맞습니다.

## 한 줄 요약

> `revalidatePath`의 layout은 **`layout.tsx` 컴포넌트**이고, 브라우저의 Layout은 **위치 계산 단계**입니다. 이름만 같고, 파이프라인에서는 `revalidatePath`가 그보다 앞단에서 "서버가 새로 만들 결과"를 정합니다.ㄴ1
