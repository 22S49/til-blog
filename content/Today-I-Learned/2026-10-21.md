## 4. React: 화면 관리 방식 변경

- "요소를 직접 고친다"에서 **"데이터(state)가 바뀌면 화면이 알아서 바뀐다"**로 바뀌었습니다.
- 화면을 **컴포넌트**(Header, Button 등) 단위로 쪼개서 재사용합니다.
- 한계는 모든 것이 **브라우저에서** 일어난다는 점입니다.
    - 처음에 빈 HTML이 오고 JS가 실행돼야 화면이 뜹니다 (첫 화면이 느림).
    - 검색엔진이 내용을 읽기 어렵습니다.
    - 데이터를 가져오려면 화면이 뜬 뒤 API를 따로 불러야 합니다.
    - 페이지 이동(라우팅)도 라이브러리를 따로 붙여야 합니다.

## 5. Next.js: React + 서버

- React를 **서버에서도 실행**해서 한계를 해결합니다.
    - 완성된 HTML을 미리 보내서 첫 화면이 빠릅니다.
    - 서버 컴포넌트에서 DB를 바로 조회합니다.
    - 폴더 구조로 라우팅이 자동 생성됩니다 (`app/sign_in/page.tsx` → `/sign_in`).
    - 로그인 처리 같은 서버 로직(Server Actions)을 같은 프로젝트에 둘 수 있습니다.
- 대가는 **"이 코드가 서버에서 도나, 브라우저에서 도나, 언제 도나"**를 신경 써야 한다는 점입니다. 오늘 오류들이 그 대가입니다.

## 한 장 요약

```
HTML/CSS   → 정적인 화면
  ↓ 움직임이 필요해서
JavaScript → 동작 추가 (하지만 직접 DOM 조작은 복잡)
  ↓ 실수가 잦아서
TypeScript → 타입으로 사전 검증
  ↓ 화면 관리가 복잡해서
React      → 상태 기반 컴포넌트 (하지만 전부 브라우저에서 실행)
  ↓ 첫 로딩 속도, SEO, 서버 연동이 아쉬워서
Next.js    → 서버에서도 렌더링 + 라우팅 + 서버 기능
```

TS는 JS를 감싼 것이고, React는 JS(TS) 라이브러리, Next.js는 React 위에 얹은 프레임워크입니다. **전부 겹쳐서 쓰는 구조**라서 이전 단계를 버린 게 아니라 위에 쌓은 것입니다.

그래서 지금 막히는 부분은 새 언어를 못 배워서가 아니라 **"실행 위치와 시점"이라는 새 개념이 추가**

## 지금까지: 언어 계층 (문법 쪽)

```
JavaScript → TypeScript → JSX (JS+태그) → TSX (TS+태그)
```

- **JSX**: JS 안에 `<div>` 같은 HTML 태그를 쓸 수 있는 문법입니다. 브라우저는 못 읽어서 빌드 때 JS로 변환됩니다.
- **TSX**: JSX에 타입(TS)을 더한 것입니다. 지금 쓰는 `.tsx` 파일이 이것입니다.

여기까지는 **"코드를 어떻게 쓰느냐"**(문법)의 이야기입니다.

## 이어서: 도구 계층 (무엇으로 만드느냐)

```
TSX → React → Next.js → (스타일/UI) → (데이터/인증) → (배포)
```

|단계|무엇|해결하는 문제|이 프로젝트의 예|
|---|---|---|---|
|**React**|컴포넌트와 state로 화면 관리|직접 DOM 조작이 복잡함|`useState`, `onClick`|
|**Next.js**|React + 서버, 라우팅, 프리렌더|첫 로딩, SEO, 서버 연동|`app/(todo)/sign_in/page.tsx`|
|**스타일링**|Tailwind CSS, shadcn/ui|CSS를 일일이 쓰기 번거로움|`className="max-w-2xl mx-auto"`, `ui/button.tsx`|
|**백엔드(BaaS)**|Supabase|서버, DB를 직접 만들기 부담|`supabase.ts`, `profiles` 테이블|
|**인증**|Supabase Auth, 쿠키|로그인 상태 유지|`getCurrentUser`, `signoutAction`|
|**폼/검증**|입력 검증 함수|잘못된 입력 처리|`authValidation.ts`|
|**배포**|Vercel 등|인터넷에 공개|(아직 안 하신 단계)|

React는 화면을 만드는 라이브러리이고, 
Next.js는 React로 웹사이트 전체를 만들 수 있게 해주는 프레임워크
- **React** = 엔진. 화면 조각(컴포넌트)을 만들고 상태에 따라 갱신하는 일만 합니다.
- **Next.js** = 엔진이 달린 완성차. 라우팅, 서버, 최적화 등 나머지를 다 갖췄습니다.
React는 "화면을 어떻게 그릴까", Next.js는 "그 화면을 서버, 라우팅, 최적화까지 갖춘 서비스로 어떻게 내보낼까"를 담당합니다.
"이 코드가 서버에서 도는지 브라우저에서 도는지" 구분해야 합니다.
## 코드로 비교한 차이

**React 단독 (사용자 정보 표시)**

```tsx
function Header() {
    const [user, setUser] = useState(null);
    useEffect(() => {
        fetch('/api/user').then(r => r.json()).then(setUser);  // 화면이 뜬 뒤에 요청
    }, []);
    return <div>{user?.name}님</div>;
}
```

**Next.js (이 프로젝트의 Header)**

```tsx
async function Header() {
    const user = await getCurrentUser();   // 서버에서 바로 조회, 완성된 HTML로 전달
    return <div>{user?.name}님</div>;
}
```

## React(Vite 등)의 방식: 클라이언트 렌더링 (CSR)

1. 서버는 거의 빈 HTML 하나만 보냅니다 (`<div id="root"></div>`).
2. 브라우저가 JS를 내려받아 실행합니다.
3. JS가 화면을 그립니다.

모든 렌더링이 **브라우저에서** 일어납니다. 그래서 `useState`, `useEffect`, `window` 등을 마음껏 쓸 수 있고, 서버 쪽은 신경 쓸 게 없었습니다.

## Next.js의 방식: 서버에서도 렌더링

Next.js는 **서버에서 먼저 HTML을 만들어서** 보냅니다.

1. 서버에서 컴포넌트를 실행해 완성된 HTML을 만듭니다.
2. 브라우저는 그 HTML을 바로 보여줍니다 (빠름, 검색엔진에 유리).
3. 그 뒤에 JS가 붙어서 클릭 같은 상호작용이 가능해집니다.

서버에서 HTML을 만드는 시점은 두 가지입니다.

- **빌드할 때 미리 만들기** = 프리렌더 (정적)
- **요청이 올 때 만들기** = 동적 렌더링

## 그래서 React에서 안 하던 고민이 생깁니다

|질문|React|Next.js|
|---|---|---|
|이 코드는 어디서 실행되나?|브라우저|서버? 브라우저? 둘 다?|
|이 코드는 언제 실행되나?|화면이 열릴 때|빌드 때? 요청 때?|
|`Date.now()`, 쿠키 사용|아무 문제 없음|언제 실행되느냐에 따라 오류|

React에서는 모든 코드가 "사용자 브라우저에서, 사용자가 접속한 뒤에" 실행되어서 `Date.now()`가 항상 접속한 시각이었습니다. Next.js는 빌드 때 실행되면 빌드한 시각으로 굳어버릴 수 있어서, 이 오류들로 확인을 요구


## 타임라인

```
[개발자]  코드 작성 → npm run build  ← ① 정적 렌더링은 여기서 실행
                         ↓
                    서버에 배포
                         ↓
[사용자]  페이지 접속(요청) → ② 동적 렌더링은 여기서 실행 (접속할 때마다)
```

||정적 렌더링|동적 렌더링|
|---|---|---|
|실행 시점|**빌드할 때 1번**|**요청이 올 때마다**|
|결과물|완성된 HTML 파일을 저장해 둠|요청마다 새로 만듦|
|사용자가 접속하면|저장된 파일을 바로 전달 (매우 빠름)|서버가 그때 만들어서 전달 (느림)|
|모든 사용자에게|똑같은 내용|사용자/요청마다 다른 내용 가능|
|예시|블로그 글, 소개 페이지, 로고, 레이아웃|로그인한 사용자 이름, 장바구니|


# Next.js `cacheComponents`에서 `Date.now()` prerender 오류

## 1. 오류와 증상

```
Next.js encountered the unstable value Date.now() while prerendering.
This value can change between renders, so it must be either prerendered or computed later.
```

- 발생 위치: `TodoLayout`이 `<Header />`를 렌더링할 때
- 호출 흐름: `Header` → `getCurrentUser()` → `supabase.auth.getUser()` → 내부에서 토큰 만료 시각을 `Date.now()`와 비교

## 2. 핵심 개념

- `next.config.ts`에 `cacheComponents: true`를 켜면 Next.js가 페이지를 최대한 **정적으로 미리 렌더링(prerender)** 합니다.
- prerender 중에는 요청마다 달라지는 값을 쓰면 안 됩니다. 이런 값에는 `Date.now()`, `Math.random()`, 쿠키, 헤더가 있습니다.
- 이런 값을 쓰려면 **요청 시점 API를 먼저 호출**해서 "이 컴포넌트는 요청이 들어와야 렌더링할 수 있다"고 Next.js에 알려야 합니다.
    - 요청 시점 API: `await connection()`, `await cookies()`, `await headers()`

## 3. 시도와 결과

|시도|결과|이유|
|---|---|---|
|`<Suspense>`로 `Header` 감싸기|오류가 계속 남|Suspense는 로딩 UI 경계일 뿐입니다. 요청 시점 API보다 먼저 `Date.now()`가 실행되는 문제는 해결하지 못합니다.|
|`getCurrentUser` 맨 앞에서 `await connection()` 호출|해결책|요청 시점 렌더링으로 미루고, Suspense는 그 구간의 로딩을 처리합니다.|

원래는 쿠키를 읽는 코드가 `supabase.ts`의 `getAll` 콜백 안에 있었습니다. 그런데 `getUser()` 내부의 `Date.now()`가 그보다 먼저 실행돼서 오류가 났습니다.

## 4. 해결 코드

```ts
import { connection } from 'next/server';

export const getCurrentUser = cache(async () => {
    await connection();            // 요청 시점 렌더링으로 전환 (Date.now()보다 먼저)
    const supabase = createServerClient();
    ...
});
```

```tsx
// layout.tsx - Suspense는 유지
<Suspense fallback={<div>로딩중...</div>}>
    <Header />
</Suspense>
```

## 5. 정리

- 요청마다 달라지는 값을 쓰는 서버 컴포넌트는 **요청 시점 API로 먼저 동적임을 선언**해야 합니다.
- **Suspense**는 동적 부분을 감싸서 나머지 레이아웃을 정적으로 유지하고 로딩 UI를 보여줍니다. Suspense만으로 `Date.now()` 오류는 막을 수 없습니다.
- `getCurrentUser`처럼 인증을 확인하는 함수는 항상 요청 시점 데이터에 의존하므로, 함수 맨 앞에 `connection()`을 두는 것이 안전합니다.
- 같은 함수를 다른 페이지에서 부를 때도 그 위에 Suspense가 필요한지 확인해야 합니다.

**원인**

`SignInForm`(클라이언트 컴포넌트)이 `useSearchParams()`를 씁니다. URL 쿼리 값은 요청이 들어와야 알 수 있어서 prerender를 막습니다. 그런데 `sign_in/page.tsx`에서 `<SignInForm />`이 Suspense 밖에 있어서 오류가 납니다.

**앞의 오류와의 차이**

||Date.now() 오류|useSearchParams() 오류|
|---|---|---|
|원인|요청 시점 API보다 먼저 불안정한 값 사용|요청 시점 값(URL)을 Suspense 밖에서 사용|
|Suspense로 해결?|안 됨 (`connection()` 필요)|**됨**|

이번 오류는 메시지에 "outside of Suspense"라고 나와 있어서 Suspense로 감싸면 해결됩니다.

**해결**

```tsx
// app/(todo)/sign_in/page.tsx
import { Suspense } from 'react';

export default function SignInPage() {
    return (
        <>
            <h1>로그인</h1>
            <Suspense fallback={<div>로딩중...</div>}>
                <SignInForm />
            </Suspense>
        </>
    );
}
```

열어두신 `shared/components/Loading` 파일을 fallback으로 쓰셔도 됩니다. 파일명이 `Loadingtsx`로 되어 있어서 `Loading.tsx`로 바꾸셔야 합니다.

**참고**

- `useSearchParams()`를 쓰는 컴포넌트는 어디서 쓰든 위쪽에 Suspense가 있어야 합니다. `sign_up` 페이지에서도 같은 컴포넌트나 훅을 쓰면 같은 오류가 납니다.
- 또는 `page.tsx`가 서버 컴포넌트이므로 `searchParams` prop을 받아 `SignInForm`에 props로 넘기는 방법도 있습니다. 이 경우에도 페이지가 요청 시점 데이터를 쓰게 되므로 Suspense가 필요합니다.

**"빌드할 때와 요청이 올 때 결과가 달라질 수 있는가?"**

## 1. 요청마다 달라지는 값 (요청 시점 API)

|사례|왜 미리 못 만드나|표시 방법|
|---|---|---|
|`cookies()`|사용자마다 쿠키가 다름|Suspense로 감싸기|
|`headers()`|브라우저, 언어, IP 등이 요청마다 다름|Suspense로 감싸기|
|`searchParams` (서버 컴포넌트의 page prop)|URL 쿼리는 요청이 와야 앎|Suspense로 감싸기|
|`params` (동적 라우트 `[id]`)|어떤 id가 올지 모름 (`generateStaticParams`로 미리 알려줄 수도 있음)|Suspense로 감싸기|
|`useSearchParams()` (클라이언트)|위와 같음|Suspense로 감싸기|
|`connection()`|명시적으로 "요청을 기다림"을 선언|Suspense로 감싸기|

## 2. 실행할 때마다 값이 달라지는 것 (불안정한 값)

이쪽이 `Date.now()` 오류와 같은 종류입니다.

- `Date.now()`, `new Date()`: 현재 시각
- `Math.random()`: 난수
- `crypto.randomUUID()`: 랜덤 ID
- `crypto.getRandomValues()`

이 값들을 쓰려면 **먼저 `await connection()`으로 요청 시점임을 표시**해야 합니다. Suspense만으로는 안 됩니다. 이 부분이 두 오류에서 해결법이 달랐던 이유입니다.

## 3. 외부 데이터 조회

- `fetch()`로 외부 API를 부르는 경우
- DB 조회 (Supabase, Prisma 등)
- 파일 시스템 읽기가 요청마다 달라질 수 있는 경우

이것들도 결과가 시간에 따라 달라질 수 있어서, Suspense로 감싸거나 `'use cache'`로 "이 결과는 캐시해도 된다"고 표시해야 합니다.

## 4. 반대 방법: 캐시해도 된다고 선언

미리 만들어도 되는 경우라면 `'use cache'` 지시어로 표시할 수 있습니다. 예를 들어 "상품 목록은 1시간에 한 번만 갱신해도 된다"는 데이터입니다. 그러면 이 데이터는 빌드할 때 포함됩니다.

## 선택 기준

```
이 값이 사용자/요청/시간마다 달라지는가?
├─ 아니오 → 그냥 두면 됨 (미리 만들어짐)
├─ 예, 캐시해도 됨 → 'use cache'
└─ 예, 항상 최신이어야 함 → Suspense (+ 불안정한 값이면 connection())
```

모든 경우에 나오는 오류 메시지가 비슷하니, 새로운 오류를 만나면 **"이 값이 요청 시점에만 알 수 있는 건가?"**부터 따져 보시면 됩니다.

## 요청 한 번이 지나가는 순서

```
사용자 요청
   ↓
① proxy.ts          ← 가장 먼저 실행. 쿠키로 로그인 확인, 리다이렉트
   ↓
② layout / page     ← 서버 컴포넌트 렌더링
   ├─ 정적 부분 (빌드 때 만들어 둔 것)
   └─ Suspense 안 동적 부분 (Header의 getCurrentUser 등)
   ↓
③ 브라우저          ← 클라이언트 컴포넌트가 붙어서 동작
```
- proxy는 "들여보낼지 말지", Suspense는 "페이지를 어떻게 렌더링할지"입니다. 둘은 함께 쓰는 도구입니다.

# proxy vs Suspense

## 한눈에 비교

||proxy|Suspense|
|---|---|---|
|한 줄 정의|요청을 **중간에 가로채는** 문지기|동적 구역을 **표시하고 기다려주는** 경계|
|실행 단계|렌더링 **이전**|렌더링 **중**|
|실행 위치|서버 (요청 도착 직후)|서버가 HTML을 만드는 과정 (React 기능)|
|대상|**요청 전체** (경로 단위)|**화면의 한 구역** (컴포넌트 단위)|
|하는 일|리다이렉트, 쿠키 갱신, 헤더 수정, 차단|늦는 부분을 분리하고 fallback 표시|
|결과|페이지에 **도달할지 말지** 결정|페이지는 도착, 일부만 **나중에 채움**|
|정적/동적 렌더링과의 관계|무관 (항상 요청마다 실행)|직접 관련 (정적/동적 경계를 나눔)|
|어디에 작성|파일 하나 (`proxy.ts`)|JSX 안에 `<Suspense>` 태그|

## 비유: 놀이공원

- **proxy** = 입구 매표소. 표 없으면 돌려보내고, 있으면 손목밴드를 바꿔 줍니다. 놀이공원 **안에 들어가기 전에** 끝납니다.
- **Suspense** = 놀이기구 앞의 대기 구역 안내판. 입장은 이미 했고, 기구가 준비되는 동안 "대기 중"을 보여 줍니다.

## 이 프로젝트에서 순서

```
/todo 접속 요청
   ↓
[proxy] 쿠키 확인
   ├─ 비로그인 → /sign_in?redirectUrl=/todo 로 리다이렉트 (여기서 끝)
   └─ 로그인   → 통과
        ↓
   [렌더링 시작]
   layout
   ├─ div/main (정적, 바로 전달)
   └─ <Suspense>
        └─ Header (getCurrentUser 대기 → 완료되면 채움)
```

## 각각 언제 쓰나

**proxy를 쓰는 경우**

- 로그인하지 않은 사용자를 특정 경로에서 막고 싶을 때
- 로그인한 사용자가 `/sign_in`에 오면 홈으로 보내고 싶을 때
- 모든 요청에서 세션 쿠키를 갱신해야 할 때
- 국가나 언어에 따라 경로를 바꾸고 싶을 때

**Suspense를 쓰는 경우**

- 쿠키, URL 쿼리, 시각 같은 요청 시점 데이터를 쓰는 컴포넌트가 있을 때
- DB나 API 응답이 느려서 그 부분만 나중에 보여주고 싶을 때
- `useSearchParams()`를 쓰는 클라이언트 컴포넌트가 있을 때

## 헷갈리기 쉬운 지점

|상황|쓸 것|
|---|---|
|"비로그인이면 페이지를 못 보게 하고 싶다"|proxy|
|"로그인한 사용자 이름을 헤더에 표시하고 싶다"|Suspense + 서버 컴포넌트|
|"`Date.now()` 오류를 없애고 싶다"|`connection()` + Suspense|
|"페이지 전체를 막지 않고 일부만 늦게 로딩하고 싶다"|Suspense|

## 같이 쓰는 이유

- proxy만 있으면 접근 제어는 되지만, `Header`가 요청 시점 데이터를 쓴다는 것을 Next.js에 알릴 방법이 없습니다. 렌더링 오류가 납니다.
- Suspense만 있으면 렌더링은 되지만, 비로그인 사용자도 `/todo`에 들어올 수 있습니다.

그래서 **proxy는 "문 단속", Suspense는 "렌더링 구조 표시"**로 역할을 나눠 둘 다 씁니다.

- 오류 = 엔진 고장 → 엔진을 고쳐야 함 (connection + Suspense)
- 프록시 = 자동차에 도어락 달기 → 엔진 고장이랑 무관
