**구조분해(destructuring)**는 객체 안의 값을 같은 이름의 변수로 꺼내는 문법입니다. 컴포넌트가 받는 `props`는 그냥 객체라서, 이 문법을 쓸 수 있습니다.

**1. props는 객체로 들어옵니다**

```tsx
<ProductItem itemName="갤럭시" itemPrice={10000} />
// 받는 쪽이 받는 props = { itemName: '갤럭시', itemPrice: 10000 }
```

**2. 구조분해 없이 받기**

```tsx
function ProductItem(props) {
    return <dd>{props.itemName}</dd>;
}
```

**3. 구조분해로 받기**

```tsx
function ProductItem({ itemName, itemPrice }) {
    return <dd>{itemName}</dd>;
}
```

매개변수 자리에 `{ itemName, itemPrice }`를 쓰면, `props.itemName`을 `itemName`이라는 변수로 바로 꺼내 줍니다. 중괄호 안의 이름이 객체의 키 이름과 같아야 합니다.

**하이픈 이름이 문제인 이유**

JavaScript 변수 이름에는 `-`를 쓸 수 없습니다. `item-name`은 "item 빼기 name"으로 읽힙니다. 그래서 props 객체의 키가 `'item-name'`이면 점(`.`)이나 구조분해로 못 꺼냅니다.

**구조분해**, **비구조화 할당**, **비구조 할당**은 모두 영어 _destructuring assignment_를 한국어로 옮긴 표현이 달라서 생긴 이름 차이입니다.

- **구조분해 할당**: MDN 한국어 문서 등에서 쓰는 표현입니다.
- **비구조화 할당**, **비구조할당**: "destructuring"을 "구조를 해체한다"고 보지 않고 "비(非)구조화"로 직역한 표현입니다. 국내 강의와 블로그에 많이 보입니다.

어느 쪽으로 검색해도 같은 문법이 나옵니다. 문법 이름이 헷갈릴 때는 영어 `destructuring`으로 검색하면 가장 정확합니다.

뜻은 똑같습니다. 객체나 배열 안의 값을 변수로 꺼내는 문법입니다.

```tsx
const { itemName, itemPrice } = props;   // 객체에서 꺼내기
const [a, b] = [1, 2];                     // 배열에서 꺼내기
```

객체 동결
아마 **props는 읽기 전용(불변)**이라는 설명 맥락에서 나왔을 겁니다.

**왜 나오는지**

- React는 컴포넌트가 받은 props를 직접 바꾸면 안 된다고 규칙으로 정해 두었습니다.
- 그 규칙을 강제하려고 React가 개발 모드에서 props 객체를 `Object.freeze`로 동결합니다. 동결된 객체는 값을 바꾸거나 추가·삭제할 수 없습니다.
- 그래서 강의나 문서가 "props는 동결된 객체다"라고 설명하면서 이 개념이 튀어나옵니다.

**실제로 어떻게 되는지**

```tsx
function ProductItem(props) {
    props.itemName = '아이폰';   // 안 됨: 에러(strict 모드) 또는 무시됨
}
```

값을 바꾸고 싶으면 props를 고치는 게 아니라, 보내는 쪽(부모)에서 다른 값을 넘기거나 상태(state)를 써야 합니다. 이건 나중에 `useState`를 배울 때 이어집니다.

**구조분해와의 관계**

- `const { itemName } = props;`로 꺼낸 변수는 원본이 아니라 값을 복사해 담은 별개의 변수입니다.
- 다만 이 변수를 바꾸는 것도 React 규칙상 권장되지 않습니다.
- 
`'use client';`는 이 파일을 **클라이언트 컴포넌트**로 취급하라는 선언입니다. 파일 맨 위(import보다 앞)에 써야 합니다.

## 없으면 나는 오류

Next.js(App Router)에서는 컴포넌트가 기본적으로 **서버 컴포넌트**입니다. 서버 컴포넌트에서 `useState`를 쓰면 이런 에러가 납니다. 정확한 문구는 버전마다 조금 다를 수 있습니다.

```
You're importing a component that needs `useState`.
This React Hook only works in a Client Component.
To fix, mark the file (or its parent) with the "use client" directive.
```

[counter.tsx](vscode-webview://0vfje8hu9hbcg5hgpddts3ovr8jokcgt8rff7uhplo8p71965k09/09_react_nextjs/chapter02/app/counter/counter.tsx)는 `useState`를 쓰니까 이 선언이 꼭 필요합니다. 제가 지금 `'use client'`를 지우고 실행해서 이 에러를 직접 확인한 건 아닙니다.

## 왜 이런 구분이 있는지

||서버 컴포넌트 (기본)|클라이언트 컴포넌트 (`'use client'`)|
|---|---|---|
|실행 위치|서버에서만 실행|서버에서 첫 HTML을 만들고, 브라우저에서도 실행|
|`useState`, `useEffect`|못 씀|씀|
|`onClick` 등 이벤트|못 씀|씀|
|브라우저 API (`window` 등)|못 씀|씀|
|DB·파일·비밀키 접근|가능|불가 (브라우저에 노출됨)|
|브라우저로 보내는 JS|없음 (결과 HTML만 감)|있음|

서버 컴포넌트는 JS를 브라우저로 안 보내서 가볍습니다. 대신 상태나 클릭 같은 **상호작용**이 필요한 부분만 클라이언트 컴포넌트로 만드는 구조입니다.

## 언제 붙이면 되는지

- `useState`, `useEffect` 같은 훅을 쓸 때
- `onClick`, `onChange` 같은 이벤트 핸들러를 쓸 때
- `window`, `localStorage` 같은 브라우저 기능을 쓸 때

이 중 하나도 없으면 붙이지 않는 게 좋습니다.

## 알아둘 점

- **하위로 전파됩니다.** 이 선언이 있는 파일이 import하는 컴포넌트도 클라이언트 쪽 묶음에 들어갑니다. 그래서 가능하면 상호작용이 필요한 작은 컴포넌트에만 붙이세요.
- 지금 코드는 버튼에 `onClick`이 아직 없어서, 눌러도 숫자가 안 바뀝니다. `useState`가 있어 `'use client'`는 필요하지만, 동작시키려면 `onClick={() => setNumber(number + 1)}` 같은 걸 추가해야 합니다.

**실제로 일어나는 일**

- `increase()`는 그냥 "함수를 지금 실행해라"라는 평범한 호출입니다. JavaScript는 이걸 막을 이유가 없어서, 렌더링 중에 실행하고 그 반환값(`undefined`)을 `onClick`에 넘깁니다.
- 에러는 JavaScript가 아니라 **React**가 냅니다. 렌더링 중에 `setNumber`가 호출되면 다시 렌더링되고 또 호출되는 무한 반복이 생기는데, React가 이걸 감지해서 `Too many re-renders` 에러로 막습니다.

`setNumber`가 **"상태를 바꾸고, 컴포넌트를 다시 렌더링해라"**라는 요청이기 때문입니다. 렌더링 안에서 그걸 호출하면 자기 자신이 다시 렌더링을 부르는 고리가 됩니다.

**순서대로 따라가 보면**

```tsx
function Counter() {
    const [number, setNumber] = useState(0);

    function increase() {
        setNumber(number + 1);
    }

    return <button onClick={increase()}>+1</button>;
}
```

1. 첫 렌더링이 시작됩니다. 함수 `Counter()`가 위에서 아래로 실행됩니다.
2. `return` 안의 `onClick={increase()}`를 만나는 순간 `increase()`가 **즉시 실행**됩니다.
3. `setNumber(0 + 1)`이 호출되어 "상태를 1로 바꾸고 다시 렌더링해라"는 요청이 React에 들어갑니다.
4. 상태가 바뀌었으니 React가 `Counter()`를 **다시 처음부터 실행**합니다.
5. 다시 `onClick={increase()}`에서 `increase()`가 실행되고, `setNumber(1 + 1)`이 호출되어 또 재렌더링을 요청합니다.
6. 이게 끝없이 반복됩니다 (2 → 3 → 4 → 5 → ...).

**핵심은 두 가지입니다**

- `setNumber`는 값이 달라지면 **항상 재렌더링을 유발**합니다.
- 렌더링은 `Counter()` 함수 본문을 실행하는 것이고, 그 안의 `increase()`는 **렌더링 때마다 무조건** 실행됩니다.

그래서 "렌더링 → `setNumber` → 재렌더링 → `setNumber` → ..." 하는 순환이 끊기지 않습니다. React는 이게 무한히 이어지는 걸 막으려고 일정 횟수가 넘으면 `Too many re-renders` 에러를 던집니다.

**함수를 넘기면 끊어집니다**

```tsx
<button onClick={increase}>+1</button>
```

이때는 렌더링 중에 `increase`가 실행되지 않고, **클릭했을 때만** 실행됩니다. 클릭 한 번에 `setNumber` 한 번, 재렌더링 한 번으로 끝나서 고리가 생기지 않습니다.


**`useState`는 브라우저에서 상태를 기억하는 기능이라서 `'use client'`가 필요하고, `setNumber`는 그 상태를 바꾸는 도구입니다.**

```tsx
'use client';                                  // ① 이 파일은 브라우저에서도 돌아간다

const [number, setNumber] = useState(0);       // ② number = 기억하는 값, setNumber = 그 값을 바꾸는 함수
<button onClick={() => setNumber(number + 1)}> // ③ 클릭하면 setNumber로 값을 바꾼다
```

**연결 순서**

1. **`useState(0)`**: 화면이 기억해야 하는 값(`number`)을 만듭니다. 초깃값이 `0`입니다. 반환값은 `[현재 값, 바꾸는 함수]` 한 쌍이고, 구조분해로 `number`와 `setNumber`에 받습니다.
2. **`setNumber`**: `number`를 직접 `number = 1`처럼 바꾸면 화면이 안 바뀝니다. `setNumber(1)`로 바꿔야 React가 알아채고 화면을 다시 그립니다.
3. **`'use client'`**: 이 "기억"과 "클릭 반응"은 브라우저에서만 일어납니다. 서버 컴포넌트는 HTML을 한 번 만들고 끝이라 기억할 곳이 없습니다. 그래서 `useState`를 쓰는 파일에는 `'use client'`를 붙입니다.

**한 줄 흐름**

클릭 → `onClick`이 실행되어 `setNumber` 호출 → 값이 바뀜 → React가 화면을 다시 그림 → 새 `number`가 보임.

`'use client'`가 없으면 에러가 나고, `setNumber` 없이 값을 바꾸면 화면이 안 바뀌고, `useState`가 없으면 기억할 값 자체가 없습니다. 세 개가 한 세트라고 보시면 됩니다.


**`increase`와 `decrease`가 이벤트 핸들러입니다.**

```tsx
function increase() { setNumber(number + 1); }   // ← 핸들러
function decrease() { setNumber(number - 1); }   // ← 핸들러

<button onClick={() => increase()}>+1</button>
```

**용어를 나누면**

- **이벤트**: 사용자가 한 행동입니다. 여기서는 "버튼 클릭"입니다.
- **이벤트 핸들러**: 그 이벤트가 일어났을 때 실행되는 **함수**입니다. 여기서는 `increase`, `decrease`입니다.
- **`onClick`**: 이벤트와 핸들러를 연결해 주는 **속성**입니다. "클릭되면 이 함수를 실행해라"라고 등록하는 자리입니다.

**정리**

```
클릭(이벤트) → onClick(연결 속성) → increase(핸들러 함수) 실행
```

`onClick`이 핸들러라고 헷갈리기 쉬운데, `onClick`은 핸들러를 꽂는 **자리**이고 핸들러 본체는 거기에 넘기는 함수입니다.

그래서 아까 `()` 얘기도 핸들러 관점으로 보면 이렇게 정리됩니다. 핸들러는 "나중에 이벤트가 일어나면 실행할 함수"라서 **함수 자체를 넘겨야** 하고, `increase()`처럼 호출 결과를 넘기면 핸들러가 아니라 `undefined`를 넘기는 셈입니다.

같은 방식으로 `onChange`(입력 변경), `onSubmit`(폼 제출) 등도 모두 이름이 `on`으로 시작하고 핸들러를 받습니다. 위 내용은 React 일반 개념 기준입니다.

React는 상태가 바뀌었는지 **이전 값과 새 값이 같은 객체(같은 참조)인지**만 비교합니다. 이걸 얕은 비교(shallow comparison)라고 합니다.

`map`과 `concat`은 하는 일이 달라서 서로 대신하는 관계가 아닙니다.

- **`map`**: 배열의 각 항목을 `<li>`로 바꿔서 **화면에 그릴 때** 씁니다. (`<ul>` 안)
- **`concat`**: 배열에 항목을 **추가한 새 배열**을 만들 때 씁니다. (`setItems`에 넘길 값)

`concat`은 아까 `[...items, newItem]` 자리에 대신 쓸 수 있습니다.

```tsx
// 스프레드 방식
setItems([...items, { title, checked: false }]);

// concat 방식
setItems(items.concat({ title, checked: false }));
```

둘 다 원본을 안 건드리고 **새 배열을 돌려주므로** 얕은 비교에서 "바뀌었다"고 판단됩니다. `push`와의 결정적 차이가 이겁니다.

||원본 변경|반환값|React 상태에 쓸 수 있나|
|---|---|---|---|
|`push`|변경함|새 길이(숫자)|안 됨|
|`concat`|안 함|새 배열|됨|
|`[...arr, x]`|안 함|새 배열|됨|

**어느 쪽을 쓸지**는 취향입니다. 요즘 React 코드는 스프레드가 더 흔하고, 맨 앞에 넣거나 중간에 끼우기도 쉽습니다.

```tsx
setItems([{ title, checked: false }, ...items]);   // 맨 앞에 추가
```

`concat`은 배열 두 개를 합칠 때도 자연스럽습니다(`a.concat(b)`). 위 내용은 JavaScript 일반 동작 기준이고 이 프로젝트에서 직접 실행해 비교한 건 아닙니다.

`push`는 원본 배열을 직접 바꾸고, `concat`은 원본을 두고 새 배열을 만듭니다. 이 차이가 React 상태에서 갈립니다.

## 문법 비교

```tsx
const items = [1, 2];

// push: 원본에 직접 추가
const r1 = items.push(3);
// items → [1, 2, 3]   (같은 배열이 바뀜)
// r1    → 3           (반환값은 새 길이, 숫자)

// concat: 새 배열을 만들어 반환
const r2 = items.concat(3);
// items → [1, 2]      (원본 그대로)
// r2    → [1, 2, 3]   (새 배열)
```

## 비교표

||`push`|`concat`|
|---|---|---|
|원본 배열|**변경됨**|그대로|
|반환값|새 길이(숫자)|새 배열|
|메모리 참조|같은 배열|다른 배열|
|인자|값 여러 개 (`push(1, 2)`)|값 또는 배열 (`concat(1, [2, 3])`)|

## React에서 갈리는 이유

React는 얕은 비교로 "이전 상태와 같은 참조인가"만 봅니다.

```tsx
// push: 같은 배열 → 변화 없음으로 판단 → 화면 갱신 보장 안 됨
items.push(x);
setItems(items);

// concat: 새 배열 → 바뀌었다고 판단 → 화면 갱신
setItems(items.concat(x));
```

또 `push`의 반환값은 숫자라서 `setItems(items.push(x))`처럼 쓰면 상태가 배열이 아니라 숫자가 되어 버립니다. 이 설명은 JavaScript와 React 일반 동작 기준이고, 이 프로젝트에서 직접 실행해 비교한 건 아닙니다.

## 정리

- **상태 배열에는 `push` 대신** `concat`이나 `[...items, x]`를 씁니다.
- `push`를 써도 되는 건 상태가 아닌 일반 지역 배열일 때뿐입니다.

맞습니다. `useRef`는 지역변수의 단점을 보완하는 용도입니다. 아까 말씀드린 지역변수의 문제 두 가지 중 **"렌더링마다 초기화된다"**는 걸 해결합니다.

```tsx
let count = 0;                          // 지역변수: 렌더링마다 0으로 초기화됨
const actionCount = useRef<number>(0);  // useRef: 렌더링이 다시 돼도 값이 유지됨
```

**`useRef`의 특징**

- 값은 `actionCount.current`에 들어 있습니다. (객체 `{ current: 0 }`)
- 값을 바꿔도 **화면이 다시 그려지지 않습니다.** 33번 줄 `actionCount.current++`이 그 예입니다.
- 다시 렌더링돼도 값이 **유지**됩니다.

**`useState`와의 차이**

||`useState`|`useRef`|
|---|---|---|
|값 유지|됨|됨|
|값 변경 시 화면 갱신|**됨**|**안 됨**|
|쓰는 곳|화면에 보여줄 값|화면과 무관하게 기억만 할 값|

그래서 "몇 번 눌렀는지 세는 값"처럼 **내부에서 기억만 하고 화면에는 안 보여도 되는 값**에 `useRef`를 씁니다. 화면에 보여줘야 하면 `useState`입니다.


React에서 DOM 요소를 직접 잡을 때는 `getElementById` 대신 `useRef`를 쓰는 게 맞습니다. 정석이라고 하는 이유가 있습니다.

**`useRef`로 DOM 요소 잡기**

```tsx
const inputRef = useRef<HTMLInputElement>(null);

const focusInput = () => {
    inputRef.current?.focus();   // 입력창에 커서 주기
};

<input ref={inputRef} type="text" />
```

`ref={inputRef}`로 연결하면 `inputRef.current`에 실제 `<input>` 요소가 들어옵니다.

**`getElementById`보다 나은 이유**

- `id`가 필요 없습니다. 같은 컴포넌트를 여러 번 그려도 `id`가 겹쳐서 엉뚱한 요소를 잡는 일이 없습니다.
- 컴포넌트마다 자기 요소를 따로 가집니다.
- React가 요소를 만들고 지우는 시점과 맞물려 동작합니다. 요소가 아직 없거나 이미 사라졌을 때 `null`이라는 걸 타입으로 알려 줍니다.
- 서버 렌더링(Next.js)에서 `document`가 없을 때도 안전하게 짤 수 있습니다.

**주의할 점**

- `inputRef.current`는 화면이 그려진 **뒤**(이벤트 핸들러나 `useEffect` 안)에서만 쓸 수 있습니다. 렌더링 도중에는 아직 `null`일 수 있습니다.
- 값을 읽고 바꾸는 건 `ref`를 쓰되, **화면에 보이는 값**은 `useState`로 관리하는 게 원칙입니다. 입력값을 `ref`로 직접 읽는 건 비제어 컴포넌트 방식입니다.

React를 안 쓰는 일반 HTML과 JavaScript 환경에서는 `getElementById`나 `querySelector`가 DOM 요소를 잡는 기본 방법입니다. 다른 방법이 없습니다.

```js
const input = document.getElementById('title');
input.focus();
```

`useRef`는 `getElementById`의 상위호환이 아니라, **React 안에서** 같은 일을 할 때 쓰는 React 방식의 도구입니다.

|환경|DOM 요소 잡는 방법|
|---|---|
|일반 HTML/JS|`getElementById`, `querySelector`|
|React|`useRef` + `ref={...}`|

React에서 `getElementById`를 쓰면 안 되는 건 아니고, 앞서 말한 이유(id 중복, 렌더링 시점, 서버 렌더링에서 `document` 부재)로 **권장되지 않는** 것뿐입니다.


- `getElementById`: 돌아가긴 하지만 React가 관리하는 화면에 끼어드는 방식이라 id 중복이나 렌더링 시점 문제가 생길 수 있어서 피하라는 겁니다.
- `useRef`: 같은 일을 React 방식으로 하는 도구입니다.

배우는 중에 쓴 걸 가지고 꼽 주는 건 좀 과하긴 합니다. 그래도 "왜 `useRef`를 쓰는지"를 한 줄로 설명할 수 있으면 다음에 같은 얘기가 나와도 당당하게 대답할 수 있습니다.

> React가 화면을 직접 관리하니까, 요소를 잡을 때도 React가 제공하는 `ref`로 연결하는 게 안전해서요.
