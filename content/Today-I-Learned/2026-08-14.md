### 연습장
#### 이터러블(iterable)
- 반복 가능한 객체
- 객체 안에 특정 함수가 정의 되어 있느냐 = 메서드를 가지고 있느냐
	- 객체 내 \_\_iter\_\_() 정의되어 있다면 반복 가능
		- 이게 정의되어 있다면 반복문을 쓸 수 있는 객체라는 것
#### 이터레이터(iterator, 반복자)
- 객체 내 \_\_next\_\_() 인덱스를 한 칸씩 이동하면서 요소를 꺼내오는 기능 정의
	- iter() 호출 ⇢ next() 호출 순서
	- 요소를 차례로 꺼내면서 위치를 기록
	- next() 실행 횟수만큼 차례로 요소를 꺼내고 더 꺼낼 요소가 없으면 StopIteration 예외 발생
- 반복을 하려면 이터레이터 객채를 생성 — 내부적으로 \_\_iter\_\_ 호출 ⇠ iter() 함수 활용
- 순서를 한 칸씩 이동하면서 요소 조회 — 내부적으로 \_\_next\_\_ 호출  ⇠ next() 함수 활용
- 예시 — `next(iter(fruits))
- 이렇게 직접 꺼내는 일이 거의 없고 반복문을 쓰겠지만 원리를 이해할 것
#### 제너레이터(generator)
- 함수의 실행을 정지하고 원할 때 다시 재개하는 형태, 비동기식 작동
- yield를 포함한 함수를 호출하게 되면 일반 함수 객체가 아니라 제너레이터 객체가 됨
```python
# 처음부터 힙 영역에 10, 20 30 할당
nums = [10, 20, 30] 

# 꺼내 올 때만 힙 영역에 해당 값을 할당
def generate_nums():
	yield 10
	yield 20
	yield 30
gen = generate_nums()
next(gen)
```
#### 제너레이터 표현식
- cf. 리스트 컴프리헨션 — 생성 결과가 처음부터 메모리에 적재, 메모리 부족 및 성능 저하 단점
- 리스트 대신 튜플로 리스트 컴프리헨션과 동일하게 사용 가능 — 메모리 경제적 사용 가능
	- 대용량 데이터 처리 시 활용
```python 
gen = (i for i in range(1, 101) if i % 2 == 0)

type(gen) # generator
# 튜플이면 요소가 보일텐데 그냥 제너레이터
# 요소를 호출하지 않았기 때문에 아직 메모리에 짝수가 적재되어 있지 않음

next(gen) # 2

for num in gen:
	print(num) # 2는 앞서 next()로 조회했기 때문에 4~100 까지의 짝수만 출력
```
#### 리스트와 제너레이터 메모리 사용 비교

- 리스트 컴프리헨션 
    - 즉시(eager) 모든 원소를 계산해서 연속된 배열에 포인터를 저장
    - 원소 개수가 늘어날수록 메모리도 선형으로 증가
    - 메모리를 다 쓰는 대신 임의 접근과 재사용 가능
- 제너레이터 표현식
    - 지연(lazy) 방식
    - next()를 호출할 때마다 값을 하나씩 계산
    - 어느 순간이든 "어디까지 진행했는지"만 기억하면 되기 때문에, 범위가 아무리 커도 크기는 그대로
    - 메모리를 아끼는 대신 한 번만 순회 가능, 인덱싱/슬라이싱 불가
- 참고
    - _sys.getsizeof_ 는 컨테이너 자체 오버헤드만 잴 뿐, 그 안에 들어있는 정수 객체들 자체의 메모리는 포함하지 않음  
        그래서 리스트의 진짜 전체 메모리 사용량은 _getsizeof_ 가 보여주는 것보다 더 큼
#### 제너레이터 쓰임과 사례

> **제너레이터는 언제 쓰나요?** 
> 모든 값을 미리 계산해서 저장해둘 필요 없이, 필요한 시점에 하나씩 꺼내 쓰고 싶을 때 

- 쓰임
    - 메모리 효율이 중요할 때
    - 무한하거나 매우 큰 시퀀스를 다룰 때
    - 큰 파일이나 대용량 데이터를 한 줄씩 읽을 때 (한 번에 다 읽지 않고 줄 단위로 처리하고 싶을 때)
    - 파이프라인(데이터 처리 체인)을 구성할 때 (lazy evaluation).
    - 무한 반복이나 상태를 유지하는 이터레이터를 만들 때
    - 함수 실행을 중간에 멈췄다가 다시 이어가고 싶을 때
- 사례
    - 대용량 로그 파일 분석 ― 한 줄씩 읽으면서 특정 패턴만 필터링
    - DB 쿼리 결과 페이징 처리 ― 다량의 DB 레코드를 커서 기반의 배치 단위로 가져와 순차 처리
    - 데이터 전처리 파이프라인 (머신러닝) ― PyTorch의 DataLoader, TensorFlow의 tf.data 파이프라인이 대표적
    - API 페이지네이션 순회, 웹 스크래핑, 무한 스크롤, 스트리밍 데이터, 트리·그래프 순회, 테스트 데이터 생성 등

#### 동기
- 순서대로 실행하고 결과도 순서대로 도출, 앞 선 작업이 종료가 되어야만 (결과가 나와야만) 다음 작업 진행
	- e.g. A 실행 ⇢ A 종료 ⇢ B 실행 ⇢ B 종료
- 전담마크하기 때문에 대기열 문제 발생
#### 비동기
- 순서대로 실행하지만 결과는 먼저 처리된 순서대로 도출
	- e.g. 손님 — 웨이터 — 주방
- 순차 실행(요구) ⇢ (대기) ⇢ 이벤트 발생(처리) ⇢ (대기) ⇢ 다음 작업 재개 ⇢ 이벤트 발생(처리) ⇢ …
	- e.g. next()를 실행해서 꺼내오는 행위가 즉 이벤트 발생과 같다. 
- 약간의 지연 발생하지만 적은 자원으로 동시에 여러 작업 처리 가능

#### import, from, as 키워드
- import — 모듈 불러오기, 모듈이 불러오면서 그 안에 있는 코드가 실행된다. 
	- 불러 온 모듈에서 마침표(.)를 통해 접근
- from 모듈명/패키지명 import 모듈에 있는 함수/변수/클래스
- from 모듈명 import * 
	- 모듈의 전체 클래스를 불러온다
- 모듈을 한 번 불러오면 \_\_pycache\_\_ 폴더가 생성되어서 최초 불러온 상태를 유지
	- 따라서 모듈이 업데이트 되어도 업데이트 된 모듈로 반영되지 않는 경우가 있음
	- 이 때는 \_\_pycache\_\_ 폴더를 삭제하거나 주피터 노트북에서 Restart
- import 모듈명 as 별칭
#### 패키지
- 모듈을 모아 놓은 디렉토리(꾸러미)
- from 패키지명.하위패키지 import 모듈/함수/변수/클래스
- 절대 경로 접근 — 전체 패키기 경로를 명시
	- e.g. chapter06.mod1
- 상대 경로 접근 
	- .. — 바로 위 패키지
	-  . — 현재 모듈이 있는 패키지
- \_\_name\_\_ — 모듈 이름
#### import 할 때와 실행할 때의 차이
- import 할 때 모듈명 — \_\_name\_\_
- 실행할 때 모듈명 — \_\_main\_\_
	- 실행을 위해 조건부로 main 모듈명으로 실행할 때 활용
	- `if __name__ == '__main__'
#### \_\_init\_\_.py
- 파이썬 3.3 이전에는 패키지 생성 시 필수였는데 (없으면 모듈 불러올 때 오류 발생)
	- 편의상 지금은 없어도 모듈을 불러올 수 있음
	- 하지만 특정 프레임워크에서는 필수이기 때문에 되도록 항상 정의하는 것이 좋음
- 현재 디렉토리가 패키지임을 알려주는 파일
- 초기화 역할
	- 패키지에서 공통적으로 처리해야 하는 내용을 정의할 수 있음
	  (패키지 내에서 사용할 공통적인 함수, 변수, 클래스를 정의)
	- 패키지를 불러 올 때, 최초 한 번만 실행되고 이 내용이 먼저 공통 처리되는 형식
- from 패키지 impot * 했을 때는 \_\_all\_\_ = \[문자열로 모듈명 나열] 에 정의된 모듈만 임포트
- 예시 — game 패키지의 모듈 lol, wow
```python
# init.py
from game import lol
print('공통 초기화 작업을 수행합니다.')
def common_func():
    return '공통 기능'
COMMON_VAR = '공통 변수'
__all__ = ['lol']

# jupyter notebook
from game import *
game.lol # <module 'game.lol' from …>
game.wow # AttributeError
```

### 비-상
### **2. 임포트/모듈 에러 해결하기**

#### 2-1. 문제 상황

**① 모듈을 수정했는데 변경 사항이 반영 안 됨 (AttributeError)**

- 함수를 새로 추가하거나 수정했는데도 "그런 속성이 없다"는 에러 발생
- **원인** ― 커널이 최초 import 시점의 모듈을 메모리에 캐싱하고 있어서, 파일을 고쳐도 커널은 예전 버전을 그대로 참조함

**② 절대 경로 import 에러 (ModuleNotFoundError)**

- 상위폴더.하위폴더.모듈 형태로 import 했는데 ModuleNotFoundError 발생
- **원인** ― 어느 폴더에서 실행하느냐(작업 디렉토리) 에 따라 파이썬이 인식하는 "루트"가 달라짐  
            ―  실행 위치 자체가 이미 최상위 폴더라면, 그 폴더 이름을 import 경로에 다시 포함시키면 안 됨

**③ 상대 경로 import 에러 (ImportError: attempted relative import with no known parent package)**

- 앞선 오류를 자구 해결해보려고 .모듈이름 형태의 상대 import로 바꿨더니 ImportError 발생
- **원인** ― 상대 import는 해당 파일이 "패키지의 일부"로 실행/인식되어야 작동하는데,  
                커널에서 개별 셀 실행이나 직접 import하는 방식으로는 그 소속 관계가 파이썬에 인식되지 않음

**④ 실행 위치가 바뀌면 같은 파일의 import가 깨짐**

- 같은 모듈 파일을 A라는 위치(예: 하위 폴더)에서 실행할 때와 B라는 위치(예: 프로젝트 최상위)에서 실행할 때,  
    필요한 import 경로 형태가 서로 달라 충돌
- **원인** ― import 경로는 파일의 물리적 위치가 아니라 현재 실행 시점의 기준 위치(sys.path)에 상대적으로 결정되기 때문

#### 2-2. 문제 해결

① 캐싱 문제 ― importlib.reload(모듈) 또는 커널 재시작 후 재실행

② 루트 인식 문제 ― 현재 실행 위치가 어디를 루트로 보는지 파악하고, 그 기준에 맞게 import 경로를 상대적으로 수정

③ 상대 경로 오류 ― 절대 import로 전환하고, 패키지로 취급할 폴더마다 __init__.py 추가

④ 실행 위치 병행 문제 ― 파일 자신의 위치(__file__) 기준으로 프로젝트 루트를 계산해 sys.path에 동적으로 추가하거나,  
                                       pip install -e .로 editable 패키지를 설치해서 실행 위치와 무관하게 항상 같은 import 경로 사용

#### 2-3. 명심할 점

① 모듈 수정 후 에러가 나면 캐싱부터 의심하기 — 코드가 맞는데도 이전 에러가 반복되면 커널 재시작 먼저

② import 경로는 실행시점의 기준위치로 삼기 — 어떤 폴더에서 실행하느냐에 따라 같은 코드도 다르게 동작함

③ 여러 실행 환경(주피터 노트북, 스크립트 등)을 병행할 계획이면 처음부터 구조를 통일하기     — pip install -e .처럼 실행 위치에 무관한 방식을 세팅해두면 이런 문제가 구조적으로 재발하지 않음

④ 패키지로 취급할 폴더에는 __init__.py를 넣는 습관  
     — namespace package로 동작은 하지만, 명시적으로 선언해두면 예측 가능성이 올라감

#### 1번 문항
- **Q**. 다음 중 이터러블(Iterable)과 이터레이터(Iterator)에 대한 설명으로 옳은 것은?
- **A**. 이터레이터는 \_\_iter\_\_ 메서드를 통해 생성되며, \_\_next\_\_ 메서드로 다음 요소를 순차적으로 반환한다.
- *이터러블 객체는 iter 메서드를 통해 이터레이터를 생성하고, 생성된 이터레이터는 next 메서드로 다음 요소를 하나씩 반환합니다. 이터러블 자체는 next__를 갖지 않으며, 순회가 끝나면 None이 아닌 StopIteration 예외가 발생합니다.*
#### 2번 문항
- **Q**. 제너레이터 함수 내부에서 yield를 만나 값을 반환한 이후, 함수는 완전히 종료되지 않고 실행 상태를 메모리에 보존한 채 어떤 상태가 되나요?
- **A**. 중지
- *yield는 값을 반환한 후 함수의 실행 상태(지역 변수, 실행 위치 등)를 메모리에 보존한 채 함수를 일시 정지시킵니다. 이는 실행 상태를 완전히 소멸시키는 return과 구분되는 핵심 특징입니다.*
#### 3번 문항
- **Q**. 리스트 컴프리헨션(\[])과 제너레이터 표현식(())의 메모리 사용 특성을 비교한 설명으로 옳은 것은?
- **A**. 리스트 컴프리헨션은 모든 결과를 즉시 메모리에 적재하지만, 제너레이터 표현식은 고정된 작은 메모리만 사용한다.
- *리스트 컴프리헨션은 대괄호 구조로 모든 결과값을 즉시 계산하여 메모리에 적재하므로 데이터 개수에 비례해 메모리가 증가하지만, 제너레이터 표현식은 소괄호 구조로 규칙만 저장해 두었다가 필요할 때 값을 생성하므로 항상 수백 바이트 수준의 고정된 메모리만 사용합니다.*
#### 4번 문항
- **Q**. 파이썬 패키지 구조에서 현재 모듈 기준으로 '나를 감싸고 있는 상위 폴더 위치'를 표시할 때 사용하는 상대 경로 기호는 무엇인가요?
- **A**. . **(오답)**
- *단일 점(.)은 현재 폴더 위치를, 더블 점(..)은 상위 폴더 위치를 나타내는 상대 경로 표기법입니다. 이러한 상대 경로는 패키지 전체가 하나의 구조로 실행될 때만 정상 동작합니다.*
#### 5번 문항
- **Q**. 다음 중 import, from, as 키워드에 대한 설명으로 옳지 않은 것은?
- **A**. from 키워드를 사용하면 모듈 전체를 통째로 불러와야 하므로 import보다 항상 메모리를 더 많이 사용한다.
- *from 키워드는 모듈 전체가 아닌 필요한 특정 함수나 클래스만 선택적으로 가져오는 방식이므로, 모듈 전체를 불러오는 import보다 메모리를 더 많이 쓴다는 설명은 틀린 설명입니다.*
