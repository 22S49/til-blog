# Typescript
- 정적 타입 + 일반 언어(Java, C# 등)의 특징 도입
- 타입스크립트 문법은 브라우저가 인식하지 못한다.
	- 브라우저의 자바스크립트 엔진은 정적 타입 선언이나 인터페이스 같은 문법을 해석할 수 없기 때문에 
	- TSC(컴파일러)를 통해 자바스크립트로 변환(컴파일, 트랜스파일) 후 실행해야 한다.
		- 컴파일 단계에서 타입(자료형)을 점검하고 이상이 있으면 자바스크립트로 변환하지 않는다. 
```ts
// 자료형 정의
const name: string = "홍길동";
const score: number = 95;
console.log(`이름: ${name}`);
console.log(`점수: ${score}`);
```

> [!NOTE] 타입스크립트에서의 자료형, 타입(type)
> - 자료형은 보통 *메모리에 어떤 크기/형태로 저장되느냐* 이고 타입스크립트 타입은 *이 값이 가질 수 있는 값들의 집합*
> - 타입스크립트에서 `type`은 키워드이기도 해서 타입을 만드는 문법과 개념으로서의 타입을 구분해 유의
> - 타입 예시
> 	 - `string` = 모든 문자열의 집합
> 	 - `"left"` = 문자열 하나만 든 집합
> 	 - `string | number` = 두 집합의 합집합
> 	 - `never` = 공집합 (가능한 값이 없음)
> 	 - `unknown` = 모든 값의 집합
>  - *e.g.* 튜플로 가능한 값들의 집합이 배열로 가능한 값들의 집합에 포함된다. 

# 배열 타입
- 대괄호 표기법
```ts
const orderPrices: number[] = [4500, 5000, 5500];
// orderPrices.push("ABC"); → 오류 발생
```
- 제네릭 표기법
```ts
const fruits: Array<string> = ["사과", "오렌지", "바나나"];
```
## 튜플 타입
- 배열의 하위 타입 (배열의 한 종류) ─ `튜플 ⊂ 배열 ⊂ 객체`
	- 런타임에서는 전부 같은 객체이고, 타입 수준에서만 튜플이 더 좁은 자료형
		- 튜플 → 배열 가능 (튜플은 배열의 한 종류라서)
		- 배열 → 튜플 불가 (길이와 위치별 타입 정보가 없어서)
```ts
const t: [string, number] = ["홍길동", 95];
t[0] = 123;                            // 오류: number는 string에 대입 불가
t[2];                                  // 오류: 길이 2인 튜플에 인덱스 2는 없음 
const x: [string, number] = ["홍길동"]; // 오류: 요소 개수 부족
```
# 특수 타입
- 타입을 명시하기 어려운 특수한 상황에서 사용
-  `any` ─ 모든 종류의 데이터를 대입할 수 있다. (동적 타입) → 컴파일 시 타입 점검 제외
	- 컴파일 시 타입 오류를 점검하지 못하기 때문에 런타임 시 오류 발생 가능성이 높아진다. → 사용 지양
- `void` ─ 반환 값이 없는 형태. 값이 존재할 수 없는 `never`와 달리 `undefined`를 값으로 담을 수 있다. 
	- 변수에 쓰는 일은 거의 없고 주로 함수 반환 타입에 사용한다.
```ts
let a: void = undefined;   // OK
let b: void = null;        // strictNullChecks 가 켜져 있으면 에러
let c: void = 1;           // 에러

// 함수 타입에서의 특이점
type Callback = () => void;   // OK: 이 함수의 반환값은 사용하지 않음 (void를 함수 타입에 대입)
const f: Callback = () => 123; // OK: 반환값이 있어도 허용 (반환값 무시)
//                  ^^^^^^^^^^ 123을 할당하는 게 아니라 123을 반환하는 함수를 Callback에 할당
const result = f(); // result의 타입은 void, 123이 실제로 반환되어도 타입상 쓸 수 없음

// 함수 타입에서의 특이점 예제
const nums = [1, 2, 3];
const list: number[] = [];
nums.forEach((n) => list.push(n)); // forEach의 콜백 타입은 (value) => void 인데
// list.push(n)의 실제 타입은 (n: number) => number 이다. → forEach가 요구한 반환 타입과 불일치
// 하지만 함수 타입에 void를 대입했기 때문에 값을 반환하는 함수도 할당할 수 있다. 
// → 반환값을 쓰지 않겠다고 약속했으니까 콜백이 숫자를 반환하든 말든 문제 없음 

// 함수 타입으로서 void와 일반 함수의 void 반환 선언은 서로 다르다. 
function g(): void {
    return 123;   // 반환값 있어서 에러 → Type 'number' is not assignable to type 'void'
} // void를 함수 타입에 대입하는 것이 아니라 함수에 직접 쓴 경우는 엄격하다. 
```
## 최상위 타입 ─ 모든 종류의 데이터 대입 가능
- `unknown` ─ 로직 상에서 타입을 알 수 있는 코드가 반드시 필요하고 모든 종류의 데이터를 대입할 수 있다.
	- 타입을 알 수 있는 코드가 없으면 컴파일 시 오류가 발생(사용을 제한)하므로 `any`보다는 안정성이 높다. 
	- `typeof`, `instanceof`, `in` 등의 연산자로 타입을 좁혀야 에러가 발생하지 않는다.
		- 다른 말로 표현하면, 타입 가드로 타입 내로잉을 해야 사용할 수 있다. 
	- *cf.* 타입 내로잉 ─ 아래 검증 방식들을 if 같은 조건문에서 사용해서 분기 내 타입을 추론하는 방식
## 최하위 타입 ─ 어떤 값도 포함하지 않는 타입
- `never` ─ 반환값이 없는 형태 (반환값이 없어야 한다. 반환값이 있으면 오류 → 값을 담을 수 없음)
	- 값을 가질 수 없고 (값이 존재할 수 없고) 함수의 실행이 정상적으로 종료되지 않음을 의미하는 타입
	- 의도적으로 예외 오류를 발생시키거나 무한 루프를 실행하여 반환값 자체가 존재하지 않는 구조에 사용
```ts
function process(): never{
    return 1;
} // 값을 가질 수 없으니까 오류 발생: Type 'number' is not assignable to type 'never'.

/* 의도적 예외 발생 예제 코드 */
function triggerSevereError(message: string): never {
    // 함수가 값을 반환하며 종료되지 않고 예외를 발생시킵니다. (정상 종료 자체가 없음)
    throw new Error(message);
}  

/* 조건이 참으로 유지되어 종료 지점에 도달하지 않는 함수 */
function processInfiniteLoop(): never {
    while (true) {
        console.log("프로세스 실행 중");
    }
}

/* 타입 내로잉에 "남은 경우가 없음"을 검사할 때도 사용 */
type Shape = "circle" | "square";

function area(s: Shape) {
  switch (s) {
    case "circle": return 1;
    case "square": return 2;
    default:
      const _check: never = s; // Shape에 새 값이 추가되면 여기서 컴파일 에러
      return _check;
  }
}
```

|            | `void`                   | `never`                       |
| ---------- | ------------------------ | ----------------------------- |
| **의미**     | 함수가 끝나지만 쓸 만한 값을 반환하지 않음 | 함수가 끝까지 도달하지 못함 (값이 존재할 수 없음) |
| **대표 상황**  | `console.log` 같은 일반 함수   | 항상 `throw` 하거나 무한 루프          |
| **변수에 할당** | `undefined` 가능           | 어떤 값도 불가                      |
```ts
let a: void = undefined;     // undefined 는 void 에 할당 가능
let b: unknown = a;          // void 는 unknown 에 할당 가능 (다른 타입 및 최하위에는 불가)
let c: string = a;           // 에러: void 는 string 에 할당 불가
let d: void = "hi";          // 에러: string 은 void 에 할당 불가
let e: void = neverValue;    // never 는 어디에든 할당 가능 (never 타입 값일 때)
```
# 타입 가드

- 타입 내로잉(타입 좁히기) 과정에서 쓰이는 검사 구문 또는 함수를 지칭. 타입 내로잉은 타입 가드의 결과
```ts
typeof v === "string"        // 원시 타입 검사
"cardNumber" in payment      // 속성 존재 검사 (이번 코드)
v instanceof Date            // 클래스 인스턴스 검사
payment.type === "card"      // 판별 유니온의 리터럴 비교
Array.isArray(v)             // 내장 검사 함수

// 1. typeof 연산자 예제: 원시타입 내로잉
function processInput(value: string | number) {
    if (typeof value === 'string') {
        console.log("문자열 길이:", value.length); // length는 string 타입이 가진 속성
    } else {
        console.log("제곱값:", value ** 2);
    };
}

// 2. in 연산자 예제: 객체 속성 검사
type Admin = { name: string; privileges: string[] };
type User = { name: string; startDate: Date };

function printUserInfo(account: Admin | User) {
    console.log(`이름: ${account.name}`);
    if('privileges' in account) {
        console.log(account.privileges);
    };    
}

// 3. instanceof 연산자 예제: 클래스 객체 검사
class Car { drive() { console.log("운전을 시작합니다."); } }  
class Truck { drive() { console.log("트럭을 운전합니다."); }
    loadCargo(amount: number) { console.log(`${amount}kg의 짐을 실었습니다.`); } } 

type Vehicle = Car | Truck;  

function useVehicle(vehicle: Vehicle) {
    vehicle.drive();
    if (vehicle instanceof Truck) {
        vehicle.loadCargo(1000);
    }
}

// 4. 직접 만든 검사 함수를 타입 가드로 사용
function isCard(p: PaymentMethod): p is CardPayment {
    return "cardNumber" in p;
}
if (isCard(payment)) { payment.cardNumber; }
```

| **검증 방식**       | **대상 데이터**  | **설명**                                                                                                                                                      |
| --------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| typeof 연산자      | 원시 타입       | - string, number, boolean 등 기본 데이터 타입 판별<br>- 유니온 타입을 구체적인 타입으로 제한하는 과정에도 사용<br>- 객체는 종류와 상관없이 모두 object 반환 (null 포함)<br>- 함수는 function으로 구분되므로 객체 판별에는 부적합 |
| in 연산자          | 객체의 속성      | - 객체에 특정 속성이 존재하는지 확인하여 타입을 구분할 때 사용                                                                                                                        |
| instanceof 연산자  | 클래스 인스턴스    | - 특정 클래스로부터 만들어진 객체인지 프로토타입 체인을 따라 검증<br>- 인터페이스와 type에는 사용 불가 (런타임에 존재하지 않기 때문)<br>- 원시 값에는 항상 false                                                       |
| Array.isArray() | 배열 구조       | - 데이터가 배열 형식인지 검증할 때 사용<br>- iframe 등 다른 실행 환경(realm)의 배열을 false로 판정 (안정적)                                                                                  |
| 사용자 정의 타입 가드    | 객체 및 커스텀 타입 | - is 키워드를 사용하여 객체의 내부 속성 구조를 직접 검증<br>- 인터페이스처럼 런타임에 존재하지 않는 타입을 검사할 때 필요                                                                                   |
# 타입 추론
- 타입을 직접 명시하지 않아도 대입된 초기값을 기준으로 이후 **컴파일러가 타입을 자동 지정**하는 메커니즘 ^9e6a20
	- 정적 언어에서는 변수에 자료형(타입)이 붙고 추론된 타입은 컴파일에 고정된다. (컴파일러가 채워준다.)
	- 주로 함수에서 쓰이고 인터페이스, 클래스, 타입에서는 직접 명시해야 한다. (단, 기본값이 있으면 생략 가능)
	- *cf.* 동적 언어는 값에 자료형이 있어서 재할당(형변환)으로 자료형이 변경된다. 
    - *cf.* 정적 언어는 타입 검사를 실행 전(컴파일 단계)에서, 동적 언어는 타입 검사를 실행 중(런타임 단계)에 실시
```ts
// 함수에서의 타입 추론
echo<string>("hi");   // 명시
echo("hi");           // 생략 (추론)
// 인터페이스에서의 타입 추론 (기본값 기반)
interface Box<T = string> { value: T }
const b: Box = { value: "hi" };         // OK: T = string
```
# 타입 단언
- **개발자가** 컴파일러에게 데이터를 특정 타입으로 간주하도록 **지시**하는 메커니즘
- 변수나 표현식 뒤에 `as 타입명`을 붙여 컴파일러에게 데이터의 타입을 지정하도록 한다. 
```ts
let unknownData: unknown = "TypeScript 5.0";

// 컴파일러는 unknownData의 속성을 모르지만, 개발자가 string임을 확신하여 단언
let strLength: number = (unknownData as string).length;
```
- 휴먼 포스로 컴파일러의 타입 검사를 강제로 우회하는 기능이기 때문에 타입을 확신할 수 있을 때 제한적 사용
```ts
// 잘못된 타입 단언 예시 (컴파일은 통과하지만 런타임 오류 발생)
let rawNumber: unknown = 12345;

// 실제 값은 숫자이지만 개발자가 string으로 잘못 단언 (컴파일 타임에 감지 못 함)
let wrongAssertedStr = rawNumber as string;

// 실행 시점에 toUpperCase() 함수가 없어 런타임 에러 발생 (TypeError)
console.log(wrongAssertedStr.toUpperCase()); 
```
- 타입 단언은 JSON 및 API 데이터의 비동기 처리에 활용된다. 
```ts
type Todo = {
    userId: number,
    id: number,
    title: string,
    completed: boolean,
}

const res = await fetch("https://jsonplaceholder.typicode.com/todos/1")
const json = await res.json();
console.log((json as Todo).userId); // 1
```

# 함수 입출력 정의
## 매개변수 타입
- 함수가 전달받는 변수 이름 뒤에 `: 타입` 형태로 정의
- 선택적 매개변수 ─ 필수 항목이 아닌 선택적 입력 항목을 처리할 때 변수명 뒤에 물음표`?`를 붙여 선언
	- 선택적 매개변수 뒤에는 일반 매개변수를 배치할 수 없다. ─ 항상 끝에서부터 순서대로 위치해야 한다.
	- 선택적 매개변수에 인자가 전달되지 않으면 내부적으로 `undefined` 값을 가진다. 
- 가변인자 ─ 매개변수의 개수가 고정되지 않고 여러 개가 들어올 때 사용하는 배열 타입 (`type[]`)
## 반환값 타입
- 매개변수 소괄호 우측에 `: 타입` 형태로 정의 → 함수 결과물의 형태를 제한
```ts
/* 매개변수 타입, 반환값 타입, 선언적 매개변수 */
function discountedPrice(amount: number, discountRate?: number): number {
    console.log("amount:", amount, "rate:", discountRate);
    return 0;
}
/* 가변인자 */
function aggregateScores(...scores: number[]): number {
    let total = 0;
    for (const score of scores) {
        total += score;
    }
    return total;
}
```
## 함수 타입

- 변수 선언부 자리에 `(매개변수: 타입) => 반환타입` 화살표 함수 형태로 함수 타입(반환 값)을 정의
- 콜백, 변수, 객체 속성에 사용하기 위한 화살표 함수를 할당하면 해당 객체들은 함수 타입이 된다. 
- *cf.* 인라인 시그니처 방식 ─ 중괄호 내부에 `(매개변수: 타입): 반환타입` 형태로 함수의 구조를 정의
```ts
// 인라인 함수 타입 정의 
const vipPrice1: (price: number) => number = (x) => x * 0.9; 
// 함수 타입에 별칭 할당
type calVipPrice = (price: number) => number; 
const vipPrice2: calVipPrice = (x) => x * 0.9;
// 인라인 시그니처 방식
const vipPrice3: {(price: number):number} = x => x * 0.9
```
# 객체 타입 정의 방식
- 자바스크립트의 객체가 어떤 모양의 데이터(문자열, 숫자 등)를 가져야 하는지 미리 규격을 정해두는 방식
## 타입 별칭
- 기존 타입에 새로운 이름을 붙이는 방식
- 객체뿐만 아니라 단순 문자열, 숫자 배열 등 모든 타입을 다룰 수 있다. 
```ts
type UserType = { id: number; name: string; email: string; } // 할당
```
## 인터페이스
- 오직 객체의 구조만 정의하는 방식 → 추상메서드만 정의할 수 있다. (인터페이스 메서드는 모두 추상메서드)
- 상속이나 확장성 측면에서 유용하고 React 등 웹 프레임워크에서 데이터 전송에 사용
	- 객체 구조 확장 ─ `extends`를 사용해서 새로운 속성을 상속으로 확장할 수 있다. 
	- 자동 선언 병합 ─ 동일한 인터페이스 이름으로 작성된 속성들을 컴파일러가 하나의 타입 구조로 병합한다.
- 클래스가 준수해야 할 행위 규격 정의 및 서로 다른 클래스 객체들을 동일한 인터페이스 타입으로 제어 가능
```ts
interface Product { code: string; price: number; brand: string; } // 선언
interface Electronics extends Product {
  warrantyMonths: number; // 보증 기간(개월) 속성 추가
}
```
### 인터페이스 구현
- `implements` ─ 구조적 규격 강제 및 다중 구현 가능
	- 인터페이스가 정의한 규격(메서드와 속성)을 클래스가 그대로 따라 구현하는 약속 키워드
	- 상속(`extends`)과 달리 물려받는 코드는 없지만 규격에 맞는 구현을 클래스가 직접 작성해야 한다. 
		- 클래스는 규격을 구현할 때 여러 인터페이스를 동시에 구현할 수 있다. (*cf.* 상속은 단 하나만 가능)
```ts
// 결제 행위를 정의하는 표준 인터페이스
interface PaymentMethod {
    // 결제 수행 메서드 규격 선언
    pay(amount: number): boolean;
}
interface Notifiable {
	// 알림 수행 메서드 규격 선언
    sendReceipt(message: string): void;
}

// PaymentMethod 인터페이스를 구현하는 신용카드 결제 클래스
// 쉼표(,)를 사용해서 paymentMethod와 Notifiable 인
class MultiPaymentCard implements PaymentMethod, Notifiable {
    constructor(private cardNumber: string) {}

    sendReceipt(message: string): void {
        console.log(message, "영수증 전송");
    }
    pay(amount: number): boolean {
        console.log(`신용카드(${this.cardNumber})로 ${amount}원이 결제되었습니다.`);
        return true;
    }
}
```
### 인터페이스 다형성(Polymorphism)
- 서로 다른 클래스의 객체들이더라도 동일한 인터페이스를 구현했다면 
  하나의 인터페이스 배열에 담아 동일한 메서드 이름으로 일괄 호출할 수 있다. 
```ts
// 새로운 결제 방식인 카카오페이 클래스 정의 (PaymentMethod 구현)
class KakaoPayPayment implements PaymentMethod {
    constructor(private accountId: string) {}

    pay(amount: number): boolean {
        console.log(`[3단계 성공] 카카오페이 계정(${this.accountId})에서 ${amount}원이 결제되었습니다.`);
        return true;
    }
}

// [다형성 예시 A] 함수 매개변수를 통한 다형성 처리
// PaymentMethod 인터페이스를 따르는 객체라면 어떤 클래스 인스턴스든 인수로 전달받을 수 있습니다.
function processPayment(method: PaymentMethod, amount: number): void {
    const result = method.pay(amount);   // 실제 클래스가 뭔지 몰라도 pay 호출 가능
    console.log("결제 결과:", result);
}

// 서로 다른 클래스의 객체를 모두 PaymentMethod 타입으로 받음
const cardPay: PaymentMethod = new CreditCardPayment("1234-5678");
const kakaoPay: PaymentMethod = new KakaoPayPayment("11111");
const multiPay: PaymentMethod = new MultiPaymentCard();

// [다형성 예시 B] 배열을 통한 다형성 일괄 처리
// 서로 다른 클래스(CreditCardPayment, KakaoPayPayment, MultiPaymentCard)로 만든 객체들을
// 모두 동일한 PaymentMethod[] 타입 배열에 담을 수 있습니다.
const payments: PaymentMethod[] = [cardPay, kakaoPay, multiPay];

console.log("--- [테스트 A] 단일 함수 다형성호출 ---");
processPayment(kakaoPay, 15000);
// --- [테스트 A] 단일 함수 다형성호출 ---
// [3단계 성공] 카카오페이 계정(11111)에서 15000원이 결제되었습니다.
// 결제 결과: true

console.log("\n--- [테스트 B] 다형성 배열 일괄 실행 ---");
payments.forEach((p) => p.pay(5000));
// --- [테스트 B] 다형성 배열 일괄 실행 ---
// 신용카드(1234-5678)로 5000원이 결제되었습니다.
// [3단계 성공] 카카오페이 계정(11111)에서 5000원이 결제되었습니다.
// 결제 진행
```

| ------------------------------- | ---------------------- | --------------------- |
| **객체(object) 구조 정의**            | 가능                     | 가능                    |

| **복합 타입 정의 (유니온 / 인터섹션)**       | `\|`, `&`로 가능          | 불가                    |
| **함수(function) 타입 정의**          | 가능                     | 불가                    |

# 속성 제어자
- `readonly` ─ 객체 생성 후 특정 속성의 값을 수정할 수 없도록 읽기 전용으로 잠그는 키워드 (데이터 훼손 방지)
	- JS 데이터 프로퍼티를 읽기 전용 상태로 변경 (객체의 writable, enumerable, configurable 상태 변경)
	- `readonly` 적용 속성을 변경하려고 시도하면 컴파일 단계에서 차단된다. 
- 물음표`?` 제어자 ─ 속성명 뒤에 물음표`?`를 붙여 데이터 입력의 선택 가능성을 제어하는 역할
	- 값이 없을 수도 있는 상황에서 오류 발생을 방지하기 위해 사용한다. 

# 인덱스 시그니처
- 사전에 Key를 알 수 없는 상황에서 Key와 Value의 타입 규격을 정의하고 동적 객체를 다루는 문법
	- Key 위치에는 string, number, symbol, 템플릿 리터럴 타입 지정 가능
		- 단, Key 위치에는 유니온 타입(`|`) 지정 불가 → 대신 `Record<K, T>` 또는 `Mapped Type` 사용
```ts
/* 속성 이름은 string 타입, 값은 number 타입으로 지정 */
interface SubjectScores {
    [subjectName: string]: number;
}

/* 속성 이름을 symbol 타입으로 지정 */
const idSymbol: unique symbol = Symbol("id");
interface SymbolKeyObject {
    [key: symbol]: string;
}

/* 속성 이름에 패턴 지정 */
interface ApiEndpoints {
    [key: `get_${string}`]: string; // 키가 반드시 'get_'으로 시작하는 문자열이어야 함
}
const apis: ApiEndpoints = {
    get_member: "회원목록",
    // post_member: "회원가입", → 오류발생
}

/* Record 활용 복합 타입 정의 */
type AllowedKeys = "id" | "name";               // Key 위치에 유니온을 못 쓰니까 우선 타입 정의
const UserInfo: Record<AllowedKeys, string> = { // 앞서 정의한 타입을 제네릭 표기법으로 기록
    id: "user01",
    name: "사용자01",
    // email: "user01@test.org", → 오류발생
}
```

# CSS vs. Javascript
- 기본적으로 HTML은 뼈대, CSS는 스타일, Javascript는 동적 요소를 정의·구현하지만 중첩되는 영역도 존재
	- 특히 상호작용에 있어서 CSS와 Javascript 간 동일한 구현이 가능한 영역이 있기도 하는데
		- CSS는 브라우저가 직접 최적화해서 처리하고, JS가 로드되기 전에도 적용되며, 코드도 적은 반면
		- JS는 상태를 기억하거나, 조건에 따라 동작·데이터가 달라져야 할 때 주로 사용한다. 
		- 다시 말해, 레이아웃은 CSS가 맡고, 화면 크기에 따라 로드와 메모리는 JS가 맡는 것이 권장된다. 

| CSS 기능 (예시)                                   | JS로 같은 일을 하는 방법                       | 어느 쪽이 나은가                                       |
| --------------------------------------------- | ------------------------------------- | ----------------------------------------------- |
| `@media` 화면 감지                                | `window.matchMedia()`<br>`resize` 이벤트 | CSS ─ 레이아웃, 스타일 변경 시<br>JS ─ 동작·콘텐츠가 달라질 때      |
| `::after` 문구 교체                               | `textContent` 변경                      | JS/HTML ─ 의미 있는 텍스트 반영<br>(CSS 콘텐츠는 텍스트로서 불안정함) |
| `transition`                                  | Web Animations API, 타이머               | CSS ─ 단순 전환 시<br>JS ─ 순서 제어나 중간에 멈추기 등          |
| Flex/Grid 배치                                  | 요소 크기 계산 후 `left`, `top` 지정           | 항상 CSS                                          |
| 일반 ─ `hover:`<br>터치 ─ `@media (hover: hover)` | `mouseenter`/`mouseleave` 이벤트         | 보통 CSS                                          |

> [!NOTE] JS로 스타일링 하는 것이 효율적인 일부 사례
> 1. 화면 크기별로 아예 다른 콘텐츠를 불러오기 ─ `matchMedia`
> 	- `resize` 이벤트는 창 크기를 조절하는 동안 이벤트가 너무 자주 발생해서 쓰로틀링 보완 필요 (주의)
> 2. 모바일 햄버거 메뉴 ─ 열림/닫힘 상태 관리를 위해 JS로 `aria-expanded`, `Esc`, 포커스 처리 등 필요
> 	- CSS만으로는 흉내만 낼 수 있고 실제 메뉴로서 접근성은 떨어진다. 
> 3. 다크 모드 토글 ─ OS 설정 적용은 CSS로 가능하지만 사용자 설정을 기억하려면 LS `localStorage` 필요

# TailwindCSS
- 모바일 우선(Mobile-First)
    - 기본 스타일은 모바일로 두고 화면이 커질수록 덮어쓰기만 추가 (이 원리는 `md:` 문법에 그대로 전달됨)
- 유틸리티 클래스(Utility Class)
	- 주로 특정한 목적을 위해 여러 메서드를 제공하는 클래스
    - CSS에서 클래스 이름을 짓는 비용을 없애고 스타일을 요소 바로 옆에 두어 구현
    - 구현 단위(4px 스케일과 색상 단계(50~900))가 정해져 있어 팀 전체의 디자인을 일정하게 유지 가능
- CSS 관리 관점에서 유용
    - 클래스 조합이 반복되면 CSS로 되돌아가는 것이 아니라 컴포넌트 단위로 묶어 관리
    - 실제 서비스에서는 CDN 방식이 아닌 빌드 방식 사용
## CSS vs. TailwindCSS

| 비교 기준      | CSS                               | TailwindCSS                                |
| ---------- | --------------------------------- | ------------------------------------------ |
| **코드 길이**  | CSS 파일이 길어지고 HTML은 짧음             | CSS 파일이 없고 HTML이 길어짐                       |
| **코드 밀도**  | 속성 1개당 1줄                         | 한 줄에 여러 속성이 압축됨                            |
| **이름 짓기**  | `.menu-card`, `.hero-box` 등 직접 작명 | 작명 불필요                                     |
| **조건 방식**  | `min`과 `max`를 조합한 구간 지정           | `min-width` 누적 (모바일 우선)                    |
| **값 지정**   | 제약 없음 (`gap: 30px 10px`)          | 4px 스케일 + 대괄호 임의값 (`gap-y-8`, `h-[212px]`) |
| **상태 변화**  | `.btn:hover {}` 별도 규칙             | `hover:bg-blue-600`                        |
| **수정 동선**  | CSS 파일과 HTML을 오가야 함               | HTML 한 곳에서 수정                              |
| **반응형 표현** | 파일 하단에 `@media` 블록이 분리됨           | `md:`, `lg:` 접두사가 요소 옆에 붙음                 |
| **상호 취약점** | 규칙이 많아지면 충돌 발생, 추적이 어려움           | 클래스가 길어져 가독성 저하, 학습 비용                     |
## 클래스 개념 비교
- 클래스라는 개념은 일치하지만 CSS와 TailwindCSS 간 작성 스타일과 방식이 다르다. 
- TailwindCSS도 결국 HTML 클래스에 CSS 클래스를 쓰는 방식
	- HTML, JS 코드에서 쓴 클래스 이름을 스캔해서, 그 클래스에 해당하는 CSS만 생성해 주는 도구

|                | CSS                                 | TailwindCSS           |
| -------------- | ----------------------------------- | --------------------- |
| **클래스 이름**     | 역할 기준 (`.menu-card`, `.search-bar`) | 기능 기준 (`flex`, `p-4`) |
| **클래스 하나의 내용** | 여러 선언을 묶음                           | 선언 하나                 |
| **스타일을 바꾸는 곳** | CSS 파일                              | HTML 클래스              |

```css
/* 일반 CSS로 직접 만든 유틸리티 클래스 */
.flex { display: flex; }
.items-center { align-items: center; }
.p-4 { padding: 1rem; }

/* 일반 CSS로 직접 만든 유틸리티 클래스를 HTML 파일에 적용 → TailCSS랑 똑같다! */
<div class="flex items-center p-4">
```

## TailwindCSS vs. Booststrap

- Bootstrap은 완성된 부품을 주는 방식, TailwindCSS는 재료만 주고 조립은 맡기는 방식
	- Bootstrap의 `.btn`은 이미 스타일이 정해져 있어서 우선순위 충돌을 신경 쓰며 덮어써야 한다.
	- TailwindCSS는 처음부터 아무것도 없어서 구현할 때 충돌할 게 없다.
		- 단, 클래스 조합이 여러 곳에 반복되면 관리 부담 발생 → React 같은 컴포넌트로 묶어서 관리
		- TailwindCSS 일부 진영에서는 컴포넌트를 제공한다. (TailwindCSS에 컴포넌트가 없는 게 아니다.)
- 최근에는 Booststrap을 선택하는 비중이 줄어듦
	- 쓰이는 영역 ─ 서비스 유지보수, 관리자 페이지(어드민) 템플릿, 빠른 개발이 필요한 곳 등
	- 줄어든 이유 ─ Bootstrap스럽게 생긴 사이트가 너무 많아졌고 기본 스타일을 덮어쓰는 과정에서 오류 발생
		- 최근에는 컴포넌트 기반 개발(React)이 일반적 → 컴포넌트는 직접 + 스타일링만 Tailwind 조합으로 사용

| 항목          | Bootstrap                     | TailwindCSS                            |
| ----------- | ----------------------------- | -------------------------------------- |
| **제공하는 것**  | 완성된 컴포넌트 (버튼, 카드, 네비바, 모달 등)  | 유틸리티 클래스 (낱개 스타일)                      |
| **기본 디자인**  | 있음 (특유의 모양)                   | 없음 (직접 디자인)                            |
| **커스텀**     | Sass 또는 CSS 변수로 조정, CSS를 덮어쓰기 | 클래스나 설정 파일에서 디자인 토큰 정의                 |
