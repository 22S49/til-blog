# 메서드 체이닝 → 빌더 패턴, 이 순서로 이해하면 안 헷갈립니다

강의가 왔다갔다 한 이유는 대부분 **"기법(체이닝)"**과 **"패턴(빌더)"**을 같은 걸로 뭉뚱그려서 설명했기 때문입니다. 아래 순서대로만 따라가면 정리됩니다.

---

## 1단계. 메서드 체이닝 = 그냥 문법 기술

체이닝은 패턴이 아니라 **"메서드가 self를 반환하면 이어 부를 수 있다"**는 단순한 사실입니다.

```python
class Pizza:
    def __init__(self):
        self.toppings = []

    def add_cheese(self):
        self.toppings.append("cheese")
        return self  # <- 이게 전부입니다. 이거 하나 때문에 체이닝이 됩니다.

    def add_olive(self):
        self.toppings.append("olive")
        return self

p = Pizza().add_cheese().add_olive()
print(p.toppings)  # ['cheese', 'olive']
```

**체크포인트:** 메서드가 `return self`를 하면 → 체이닝 가능. 다른 값(`response.data` 같은 최종 결과)을 반환하면 → 체이닝 불가능. 이게 전부입니다.

---

## 2단계. 그럼 빌더 패턴은 왜 필요한가?

문제 상황을 먼저 봐야 합니다. 생성자에 옵션이 많아지면 이렇게 됩니다.

```python
# 나쁜 예: 파라미터가 너무 많고, 뭐가 뭔지 순서로 외워야 함
pizza = Pizza(size="L", cheese=True, olive=False, bacon=True, spicy=False, thin_crust=True)
```

**빌더 패턴**은 이 문제를 "생성자 한 방"이 아니라 **"단계별로 쌓아가다가 마지막에 완성"**하는 방식으로 풉니다.

```python
class PizzaBuilder:
    def __init__(self):
        self._size = "M"
        self._toppings = []

    def size(self, s):
        self._size = s
        return self  # 체이닝을 위한 self 반환

    def add_topping(self, t):
        self._toppings.append(t)
        return self

    def build(self):
        # 여기서 진짜 최종 객체(딕셔너리든 Pizza 인스턴스든)를 만들어 반환
        return {"size": self._size, "toppings": self._toppings}

pizza = (
    PizzaBuilder()
    .size("L")
    .add_topping("cheese")
    .add_topping("bacon")
    .build()  # 마지막에 build()로 "완성"
)
```

**빌더 패턴의 핵심 3가지:**

1. 설정하는 메서드들은 `self`를 반환한다 (체이닝을 위해)
2. 마지막에 `build()` 같은 메서드로 "진짜 결과물"을 확정 짓는다
3. 목적은 **"복잡한 객체를 읽기 좋게, 단계적으로 만드는 것"**

즉 **빌더 패턴 = 메서드 체이닝을 "객체 생성"이라는 목적에 맞게 활용한 것**입니다.

## 3단계. 그럼 supabase 코드는 뭐였나?

```python
supabase.table("documents").insert({...}).execute()
```

이건 **supabase-py 라이브러리 내부**가 위 2단계처럼 빌더 패턴(정확히는 쿼리 빌더)으로 만들어져 있어서 가능한 겁니다.

- `.table()` → 쿼리 빌더 객체 반환 (체이닝 시작)
- `.insert()` → 자기 자신(빌더) 반환 (계속 설정)
- `.execute()` → PizzaBuilder의 `build()`처럼 "진짜 실행"해서 결과 반환 (체이닝 끝)

**여기서 헷갈렸던 지점:** 이건 "빌더 패턴을 배운다"가 아니라 **"빌더 패턴이 이미 적용된 남의 코드를 사용해본다"**였던 겁니다. 강의가 이 구분 없이 "이것도 빌더 패턴, 저것도 빌더 패턴"이라고 하면 당연히 헷갈립니다.

반면 원래 작성하신 `AiLog` 클래스는:

```python
def create_documents(self, title, content):
    response = supabase.table("documents").insert({...}).execute()
    return response.data  # self가 아니라 최종 데이터를 반환
```

`self`가 아니라 데이터를 반환하니 → **AiLog 자체는 빌더 패턴이 아니고, 그냥 supabase의 빌더를 "내부에서 사용"하는 평범한 서비스 클래스**입니다.

## 직접 연습해보고 싶다면

`AiLog`를 진짜 빌더 패턴처럼 바꿔보는 연습:

```python
class DocumentBuilder:
    def __init__(self, user_id):
        self.user_id = user_id
        self.data = {}

    def title(self, t):
        self.data["title"] = t
        return self

    def content(self, c):
        self.data["content"] = c
        return self

    def save(self):
        self.data["user_id"] = self.user_id
        response = supabase.table("documents").insert(self.data).execute()
        return response.data

# 사용
DocumentBuilder(user.id).title("제목").content("내용").save()
```

이렇게 바꾸면 `AiLog`도 진짜 빌더 패턴이 됩니다. 다만 실무에서 CRUD 서비스 클래스를 이렇게까지 빌더로 안 만드는 경우도 많으니, "이렇게도 만들 수 있다"는 감만 잡으시면 충분합니다.




#### RLS는 "개념/기능"이고, 정책은 그 개념을 실현하는 "재료"예요

**RLS(Row Level Security)** 자체는 하나의 문장으로 표현할 수 있어요:

> **"DB가 쿼리를 실행할 때, 누가 요청했는지에 따라 행 단위로 자동 필터링해준다. 클라이언트(파이썬 코드)가 뭘 보내든 상관없이."**

이게 전부예요. 이 개념은 `for`, `using`, `with check`, `to` 같은 문법이 아니라, **그 문법들이 모여서 만들어내는 동작 방식** 자체를 가리켜요.

그럼 지난번 정리에서 RLS는 어디 있었냐면:

- `alter table documents enable row level security;` → 이 한 줄이 RLS **개념 자체**예요. "이 테이블부터는 행 단위 자동 필터링을 켠다"는 스위치.
- 그 뒤에 나온 `create policy ...` 전체 (for/using/with check/to/auth.uid()) → 이건 RLS라는 개념이 아니라, **"그 필터링을 정확히 어떤 규칙으로 할지"를 정의하는 설정값**이에요.

#### 비유로 다시 보면

RLS를 "보안 카메라 시스템"이라고 하면:

- **RLS를 켠다** = 카메라 시스템 자체를 설치하는 것 (`enable row level security`)
- **정책(policy)** = 카메라한테 "누가 지나가면 녹화해라" 같은 개별 규칙을 입력하는 것 (`create policy`)

시스템(RLS)은 안 켜져 있으면 정책을 아무리 잘 써도 소용없고, 반대로 시스템은 켜졌는데 규칙(정책)이 하나도 없으면 — 지난번에 얘기했듯 **기본값이 "전부 차단"**이라 아무 데이터도 안 보여요.


정책(`create policy`) 구문 자체를 제대로 뜯어볼게요.

#### 기본 문법 뼈대

sql

```sql
create policy "정책이름"
on 테이블명
as permissive | restrictive
for select | insert | update | delete | all
to 역할(role)
using (조건식)
with check (조건식);
```

하나씩 뜯어봅시다.

#### 1. `for` — 어떤 작업에 적용할지

RLS 정책은 CRUD 네 가지 작업마다 **따로** 걸 수 있어요. 지금까지 본 `for all`은 편의상 네 개를 한 번에 묶은 거고, 실무에선 이렇게 세분화하는 경우가 훨씬 많아요:

sql

```sql
-- 본인 문서만 조회 가능
create policy "select_own_documents"
on documents for select to authenticated
using (auth.uid() = user_id);

-- 본인 명의로만 생성 가능
create policy "insert_own_documents"
on documents for insert to authenticated
with check (auth.uid() = user_id);

-- 본인 문서만 수정 가능
create policy "update_own_documents"
on documents for update to authenticated
using (auth.uid() = user_id)
with check (auth.uid() = user_id);

-- 삭제는 아예 금지 (정책 자체를 안 만들면 delete는 항상 거부됨)
```

왜 나누냐면, "조회는 다 허용하되 수정은 본인만" 같은 **비대칭 규칙**을 만들 수 있기 때문이에요. 예를 들어 게시판이면:

sql

```sql
-- 누구나(로그인한 사람은) 모든 글을 읽을 수 있음
create policy "read_all_posts"
on posts for select to authenticated
using (true);

-- 근데 수정/삭제는 본인 글만
create policy "modify_own_posts"
on posts for update to authenticated
using (auth.uid() = author_id);
```

`for all`로 뭉뚱그리면 이런 비대칭 설계가 안 나와요.

#### 2. `using` vs `with check` — 언제 뭐가 적용되는지

이게 제일 헷갈리는 부분인데, 표로 정리하면:

|작업|USING이 체크하는 것|WITH CHECK가 체크하는 것|
|---|---|---|
|SELECT|어떤 기존 행을 보여줄지|(해당 없음)|
|INSERT|(해당 없음)|새로 넣으려는 행이 조건 통과하는지|
|UPDATE|어떤 기존 행을 수정 대상으로 삼을 수 있는지|수정 **후** 결과 행이 조건 통과하는지|
|DELETE|어떤 기존 행을 삭제 대상으로 삼을 수 있는지|(해당 없음)|

UPDATE에서 왜 둘 다 필요한지가 핵심이에요. 예를 들어 `using`만 있고 `with check`가 없으면:

sql

```sql
create policy "update_own" on documents for update to authenticated
using (auth.uid() = user_id);
```

user02가 **자기 문서**를 골라서(USING 통과) `user_id`를 user01의 id로 **바꿔치기**하는 UPDATE를 시도할 수 있어요. USING은 "수정 전 이 행을 건드려도 되냐"만 보고, WITH CHECK가 없으면 "수정 후에도 여전히 내 소유여야 한다"는 검증이 빠지는 거죠. 그래서 UPDATE 정책엔 보통 둘 다 같이 써요.

#### 3. `to` — 누구에게 적용할지

Supabase는 기본으로 두 가지 role을 줘요:

- `anon` — 로그인 안 한 사용자 (비로그인 API 키로 요청)
- `authenticated` — 로그인한 사용자 (JWT 있음)

sql

```sql
-- 비로그인자도 공개 게시물은 볼 수 있게
create policy "public_read" on posts for select to anon, authenticated
using (is_published = true);
```

`to`를 생략하면 `public`(사실상 모든 role) 대상이 돼요. 보통은 명시적으로 `authenticated`를 써서 최소한 로그인은 했는지 걸러주는 게 안전해요.

#### 4. 같은 작업에 정책이 여러 개면?

`for select`에 정책을 두 개 이상 만들 수도 있어요 — 이때 기본(`permissive`)은 **OR**로 합쳐져요. 하나라도 통과하면 보여줘요.

sql

```sql
-- 본인 문서는 보임
create policy "own" on documents for select to authenticated
using (auth.uid() = user_id);

-- 공유받은 문서도 보임
create policy "shared" on documents for select to authenticated
using (
  exists (
    select 1 from document_shares
    where document_shares.document_id = documents.id
      and document_shares.shared_with = auth.uid()
  )
);
```

이러면 "내 문서" OR "나한테 공유된 문서"가 다 보이게 돼요. 이게 실무에서 RLS를 실질적으로 강력하게 만드는 패턴이에요 — 단순히 소유자 체크를 넘어서 **서브쿼리로 복잡한 접근 규칙**을 짤 수 있거든요 (팀 소속, 역할 기반, 공유 관계 등).

#### 5. `auth.uid()`는 사실 뭘 참조하는 거냐

이건 Supabase가 제공하는 SQL 함수인데, 내부적으로 현재 요청의 JWT에서 `sub` 클레임(=로그인한 유저의 id)을 꺼내주는 거예요. Python 코드에서 `sign_in_with_password`로 로그인하면 세션 토큰(JWT)이 생기고, 그 이후 모든 `supabase.table(...)` 요청에 그 토큰이 자동으로 실려가요. Postgres 입장에선 "이 요청은 누가 보낸 거지?"를 그 JWT로 판단하고, 정책 안의 `auth.uid()`가 그 값을 돌려주는 거예요.

즉 흐름을 연결하면: **로그인(JWT 발급) → Python이 요청에 JWT 자동 첨부 → Postgres가 JWT에서 auth.uid() 추출 → 정책의 using/with check 조건이 행마다 평가 → 통과한 행만 반환/허용.**
