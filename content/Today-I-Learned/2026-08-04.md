### 연습장
#### 스테이징 + 커밋 워크플로우
1. git status
	- 변경된 파일이 무엇인지, 변경 내용이 뭔지 확인하기
	- 관리할 파일을 상세하게 관리하기: git add -p 옵션 (추가할까 말까)
	- 스테이징이 잘 되었는지 확인하기: git diff staged 
2. git commit
	- 커밋 준비됨? 커밋은 되도록 기능별로 하는 것이 좋음, 한 꺼번에 하는 건 지양
	- 메세지 컨벤션: 관례가 있으니 미리 파악해 두는 것이 좋음, 접두사처럼 사용
		- 기능 추가 "feat: …" 
		- 버그 수정 "fix: …"
		- 문서화 "docs: …"
		- 다시 개발 (리팩토링, 수정보완) "refactor: …" 
		- 설정 변경 (간단한 변경) "chore: …"
		- 테스트케이스 "test:…"
	- 커밋이 잘 되었는지 확인하기: git log
	- 변경사항 되돌리기
		- git reset
			- --soft: 커밋만 취소, 변경이력 삭제, 원파일은 남아 있음
			- --mixed(기본값): 스테이징+커밋 모두 취소
				- Unstaged changes after reset: 변경이력 삭제, 원파일은 남아 있음
					- git diff --staged: 변경이력이 삭제됐으므로 출력되는 내용 없음
			- --hard: 스테이징+커밋 모두 취소, 변경이력 삭제, 원파일도 삭제 (코드 삭제)
				- 복구하면 로그가 복구되고 코드도 복구가 가능하긴 함
		- git reflog
			- 리셋 직전, 직후에는 리셋을 취소할 수 있음
				- 방금 리셋해서 취소된 커밋 내역을 확인할 수 있음
					- 왜냐하면 일정 기간 기록이 남아있기 때문
				- 리셋을 취소하려면 다시 리셋하면 됨 (이중부정이면 긍정인 것처럼)
		- git revert
			- reset과 다르게 커밋 기록을 삭제하지 않음 ⇢ 커밋 기록 유지
			- 그 시점에 대한 변경사항이 새로운 커밋으로 복구되는 방식
			- 복구를 했다는 기록을 남김 (reset은 그런 기록 없음)
				- 책임소재를 분명히 해야 할 때 활용하기 좋음 
#### 해시ID
- HEAD~: 직전 단계
- HEAD~n: n만큼 전 단계
- 해시 ID를 기억하기 어려울 때, reflog가 복잡할 때 단계 기준으로 이동할 수 있음 
#### 브랜치
- 사진을 폴더로 정리하듯 하는 것. 단, 참조하는 방식 (장바구니처럼) ⇢ 인덱스를 기반으로 동작
	- 기능을 만들었다고 하더라도 완성된 소스로 사용자가 사용해야 함
	- 메인 브랜치가 완성이 올라오는 최종 브랜치 ⇢ 최종적으로 통합되는 브랜치
- 브랜치는 기능별로 만들어야 함 (기능명세 단위로 상세하기 만드는 게 일반적)
	- e.g. 주문 브랜치(X) 바로구매, 장바구니 담기, … 브랜치(O)
	- 브랜치명 컨벤션
		- feature/"기능명"
			- e.g. feature/order-form
		- fix/…,  bugfix/…, hotfix/…, chore/…, release/…, test/…, docs/…, dev/…
- 브랜치가 추가되면 커밋이 하나 추가된 셈 (물리적 공간이 아니지만 물리적 공간)
1. 브랜치 생성하기: git branch "브랜치명"
	- 브랜치를 생성한다고 바로 생성하나 브랜치로 이동하는 것은 아님 (현재에 머물고 있음)
2. 브랜치 이동하기: git checkout "브랜치명"
	- 브랜치도 커밋과 같은 개념이므로 checkout 명령어를 쓸 수 있음 
	- 하지만 소스코드 커밋과 헷갈리기 때문에 요즘에는 switch 명령어를 많이 쓰고 있음
	- git checkout -b "브랜치명": 브랜치를 생성하면서 바로 이동
	- git switch -c "브랜치명": 브랜치를 생성하면서 바로 이동 
3. 브랜치 확인하기: git branch
- e.g. 페이먼트 브랜치에서 파일을 생성하고 오더 브랜치로 이동하면 페이먼트 파일이 보이지 않음 (VS코드 상에서는 삭제된 것처럼 취소성 생성됨)
1. 브랜치 삭제하기: git branch -d "브랜치명"(현재 위치의 브랜치는 삭제할 수 없음, 내가 나를 삭제 못함)
	- -D "브랜치명"(강제삭제)
2. 브랜치명 변경: git branch -m "변경할 브랜치명"(현재 위치의 브랜치명 변경)
	- -M "변경할 브랜치명"(강제변경)
- **(주의)** 브랜치 만들고 스테이지에 올렸는데 커밋을 안한 상태에서 다른 브랜치로 이동하면 브랜치 날라감
	- 이 경우를 방지하기 위해서 스테이지에 임시보관하는 기능이 있음 (다시 돌아와서 복구할 수 있도록)
		- 커밋 안 하고 넘어갈 때 경고가 뜨면: git stash 해서 임시보관하고 이동할 수 있음
		- 임시저장기록 확인하기: git stash list
			- git stash pop: 가장 최근 걸 반영하기 (다시 복구하기) ⇢ 복구하면 임시저장 내용 삭제됨
#### 브랜치 병합
- Merge Commit(병합커밋, 3way): 메인 변경이 있고 브랜치 변경도 있는 경우 활용
	- 교집합이 있는 합집합
	- 분기가 생성되기 때문에 로그 확인 시에 분기를 확인할 수 있음, 커밋함
- Fast-forward(빨리감기): 메인 변경이 거의 없는 경우 활용 (원래 메인은 잘 안 건들임)
	- 하나의 집합 자체가 교집합인 합집합 (메인에 브랜치가 포함되는 형태)
	- 마지막 커밋으로 커서만 변경해서 병합, 분기를 확인할 수 없음 (없으니까), 커밋 안함
- Conflict(충돌): 뭘 커밋해야 할지 모르겠어요 상태 ⇢ 충돌을 해결해 줘야 함
	- 다른 브랜치에서 같은 위치의 소스가 바뀌어 있는 경우 발생하는 충돌
	- 어디서 충돌났는지 보려면? git status ⇢ 코드 확인하고 어떤 걸로 반영할지 결정하면 됨
	- current change: 현재 위치, main에서의 변경사항
	- incoming change: 메인으로 넘어온 파일의 변경사항
	- 충돌을 해결하면 스테이지에 올림으로써 해결됨을 알려줌 (알려줘야 함)
- git merge "병합할 브랜치명"
	- main 브랜치 위치에서 병합해야 함, 조건에 따라 알아서 병합 방법을 선택해 병합함
#### 일반적인 브랜치 구조
- Main(소스의 완성본, 배포 대상, 보호 상태로 유지) 
	- Dev(최종 병합 대상, 보호 상태로 유지)
		- Dev를 향하는 기능별 브랜치 1, 2, 3, …(작업 공간, 완료되면 Dev에 병합
		- 작업 및 병합 완료된 기능별 브랜치는 삭제, 결국 완성본은 Main과 Dev만 남게 되는 구조 
		- 기능을 잘게 나누어서 빠르게 작업하고 빠르게 병합하는 게 충돌을 줄이는 방법
			- 그렇지 않으면 충돌만 몇 십개 되기 때문에 해결하는 게 더 일이 될 수 있음
#### Rebase
- 커밋 이력을 재배치: 보기 좋게 다듬기 
	- e.g. 분기된 시점을 떼어서 선형으로 붙여주기 
		- Fast-forward 같이 붙지만 3way-merge인 셈
- 많이 쓰는데, 쓰면 안 되는 경우도 있고 제약이 주어질 때도 있음. 혼자 작업할 때 많이 사용하기도
	- 공유된 브랜치에는 쓰면 안됨
- git rebase "붙을 브랜치"
- 충돌 해결 후 리베이스 다시 하기: git rebase --continue
	- 해결하지 않고 커밋만 하고 넘어가기 (현재 충돌 건너뛰기): git rebase --skip
	- 전체 리베이스를 포기하기: git rebase --abort
- rebase 후 merge 하면 Fast-forward로 결합
	- 분기가 있었다면 3way-merge 됐을 것

#### 원격 작업하기 (remote repository)
- 지금까지는 로컬 작업
- 이제는 협업을 위해 다른 작업자도 작업 상태를 공유받을 수 있는 공간이 필요: (대표적인) Github
	- 로컬A ⇢ push ⇢ 원격 저장소 ⇢ pull ⇢ 로컬B
	- 각각 독립적인 저장소가 있는 상태에서 각각의 상태를 공유하는 것 (브랜치 단위)
	- 저장소가 있어야 연결 가능하므로 반드시 각 로컬에 working directory를 만들어야 함
- 원격 저장소가 여러 개인경우에는 별칭을 지정해 주는데, 이건 <u>git remote add "별칭" "원격 SSH url"</u>
	- e.g. git remote add origin git@…
	- 현재 연결되어 있는 원격 저장소 확인하기: git remote -v
	- 원격 저장소도 브랜치로 관리 ⇢ 나중에 로컬에 원격 저장소 브랜치가 추가된다고 생각하면 됨
		- 별칭이 곧 브랜치의 이름 ⇢ push 할 때 별칭에 브랜치를 push 하면 됨
			- <u>git push "원격 브랜치 별칭" "원격 브랜치명"</u> git push origin main
		- 원격 저장소에 브랜치가 없었기 때문에 "new branch"라고 뜨고 
		- 로컬에 있던 main 브랜치가 원격 저장소의 new branch로서 올라가게 됨
		- 기본 고정하기 -u 옵션, 처음 해두면 이후에 push만 해도 해당 브랜치에 push 됨
- 원격 저장소에서 가져오기
	- <u>git pull "원격 브랜치 별칭" "원격 브랜치명"</u> git pull origin main
	- 원격에 있는 내용을 그대로 공유 받아서 작업할 수 있음
	- 기본 고정하기 -u 옵션
	- 처음하는 경우에는 clone 해서 그대로 가져오면 됨
		- 원격저장소 폴더 이름으로 생성되거나, 내가 원하는 폴더에 내려받을 수 있음
		- 현재 위치에 내려받는다면 . 찍어주면 됨
		- e.g. git clone git@… .
- main 수정 통제는 보통 원격 저장소에 합니다. (공동작업하면서 수정하지 못하게 하려고)

### 오늘의 퀘스트
#### 1번 문항
- **Q**. git diff --staged 명령어가 비교하는 대상으로 옳은 것은?
- **A**. 두 커밋 사이의 변경 **(오답)**
- *git diff --staged는 git add로 스테이징된 내용과 마지막 커밋(HEAD) 사이의 차이를 보여줍니다. 커밋 전에 실제로 무엇이 반영될지 최종 점검할 때 사용합니다. 반면 git diff는 워킹 디렉터리와 스테이징 영역을, git diff HEAD는 워킹 디렉터리와 마지막 커밋을 비교합니다.*
#### 2번 문항
- **Q**. 현재 작업 중인 브랜치(또는 커밋)를 가리키며, 브랜치 전환 시 함께 이동하여 워킹 디렉터리 상태를 결정하는 Git의 특수 포인터 이름은?
- **A**. HEAD
- *HEAD는 현재 체크아웃된 브랜치를 가리키는 특수 포인터로, 그 브랜치가 가리키는 커밋이 워킹 디렉터리에 반영된 상태입니다. git switch로 브랜치를 전환하면 HEAD가 이동하고, 이에 따라 워킹 디렉터리의 파일도 자동으로 바뀝니다.*
#### 3번 문항
- **Q**. git reset의 세 가지 모드 중, 커밋 이력·스테이징 영역·워킹 디렉터리의 변경 사항을 모두 되돌려 영구적으로 삭제하는 모드는?
- **A**. --hard
- *--hard 모드는 HEAD 이동뿐 아니라 스테이징 영역과 워킹 디렉터리까지 모두 리셋 대상 커밋 상태로 되돌려, 그 사이의 모든 변경 사항을 영구적으로 삭제합니다. --soft는 커밋 이력만 되돌리고 스테이징과 워킹 디렉터리는 그대로 유지하며, --mixed는 스테이징만 지우고 워킹 디렉터리는 유지합니다. 따라서 --hard는 가장 주의해서 사용해야 하는 모드입니다.*
#### 4번 문항
- **Q**. 이미 원격 저장소에 push되어 공유된 커밋의 변경 내용을 되돌리고 싶을 때, 기존 이력을 삭제하지 않고 반대 변경을 담은 새로운 커밋을 만들어 안전하게 되돌리는 명령어는?
- **A**. revert
- *git revert는 특정 커밋의 변경을 반대로 적용하는 새 커밋을 생성하여, 기존 이력을 지우지 않고 안전하게 변경을 취소합니다. 이미 공유된 커밋의 이력을 조작하는 reset과 달리 협업 환경에서도 안전하게 사용할 수 있습니다.*
#### 5번 문항
- **Q**. Rebase의 황금률에 따를 때, rebase를 수행해도 비교적 안전한 경우는?
- **A**. 아직 원격에 공유되지 않은 개인 로컬 브랜치
- *rebase는 커밋 해시를 새로 생성하기 때문에, 다른 사람이 이미 해당 커밋을 기반으로 작업 중이라면 이력 불일치와 충돌이 발생합니다. 따라서 '공유된 커밋은 rebase하지 않는다'는 황금률에 따라, 아직 공유되지 않은 개인 로컬 브랜치에서만 안전하게 rebase를 사용해야 합니다.*
