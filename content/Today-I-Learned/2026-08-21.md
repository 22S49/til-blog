1### 연습장
#### 동기(sync) vs. 비동기(async)
- 제어권 — 함수 실행 권한
- 동기식(서브루틴) — A작업이 실행되고 결과를 본 후에 B작업으로 제어권이 넘어감 
	- Blocking — 지연 시간 동안 스레드가 멈춘다. (time.sleep())
	- 이벤트 루프 없음, 필요 시 멀티 스레드 또는 멀티 프로세싱으로 작업
- 비동기(코루틴) — A작업이 실행되자마자 B작업으로 제어권이 넘어감 (await를 만나서 반납)
	- Non-Blocking — 지연 시간 동안 스레드 중단 없이 다른 작업을 처리한다. (await async.sleep())
	- 이벤트 루프 관여
#### 실행 환경에 따른 코루틴 가동 방식
- 주피터 노트북은 이벤트 감지하는 상태가 활성화 되어 있음 (이미 이벤트 루프가 가동 중)
	- await 함수명() 으로만 해도 비동기식 실행 가능
- 파이썬 파일은 이벤트 감지하는 상태가 아니기 때문에 코드에 asyncio.run()로 이벤트 루프를 생성해야 함
#### asyncip.gather()
- 작업을 동시에 실행, 마지막 작업까지 대기했다가 한꺼번에 결과 반환
```python
# 순차실행: 문법적으로는 비동기식이지만 흐름은 동기식
# 한 await가 끝날 때까지 기다린 다음 넘어감, 한 작업이 끝날 때까지 이벤트 루프는 깡통
async def main():
    await work('작업A', 2)
    await work('작업B', 3)
    await work('작업C', 1)

# 동시실행: 문법적으로도 흐름으로도 비동기식
# 세 코루틴을 한꺼번에 이벤트 루프에 등록하고, 모든 작업이 끝날때 까지 기다렸다가 반환
async def main():
    results = await asyncio.gather(
        work('작업A', 2),
        work('작업B', 3),
        work('작업C', 1)
    )
    print(results)
```
#### 게시글 수집 예제
```python
import httpx
import asyncio

async def get_post(num):
	# async with는 async 버전의 컨텍스트 매니저
	# 진입/종료 시 await가 필요한 경우(연결 열기/닫기가 비동기인 경우)에 사용
    async with httpx.AsyncClient() as client: # requests의 비동기 버전
        url = f'https://jsonplaceholder.typicode.com/posts/{num}'
        res = await client.get(url) # requests.get의 비동기 버전
        result = res.json()
        return result['id'], result['title']

# 비동기식 문법이지만 동기식 흐름
# async def main():
#     for i in range(1, 11):
#         result = await get_post(i)
#         print(result)

# gather 이용한 비동기식 문법과 흐름
async def main():
    get_posts = [get_post(i) for i in range(1, 11)]
    results = await asyncio.gather(*get_posts)
    print(results)

asyncio.run(main())
```
#### LLM(Large Language Model)
- 학습형 데이터를 보유하고 있는 것은 아니고 예측을 위한 규칙(모델)을 가지고 있는 것
	- AI 지능 정의는 얼마나 사람 같은지 측정하는 것이기 때문에 결과론적
		- 어떻게 사람처럼 동작하는가? 를 알 수 없고 얼마나 사람처럼 동작하는가? 를 측정
	- 현재 인공지능은 확률 아키텍처 트랜스포머 모델 — 확률 모델 없는 인공지능은 뇌과학의 영역
- 토큰(Token) — AI(LLM)가 읽고 쓰는 최소 단위
	- 일반적으로 영어는 단어 기준에서 토큰 소모
	- 한국어는 형태소 기준에서 토큰 소모 (단어 기준으로는 토큰 2개 이상 소모)
- 확률적 토큰 선택
	- 다음 토큰 예상 생성 방식으로 문장을 만든다. (다음 단어에 대한 가장 높은 확률의 토큰을 예측)
	- 환각이 발생하는 배경 (특정 시점이나 문제에 대해서는 예측할 수 있는 규칙이 없어서 확률이 떨어짐)
- 유사도 계산 방법
	- 유클리디안 유사도 (피타고라스 정의)
	- 코사인 유사도 (-1 to 1)
		-   1 — 유사하다.
		-  0 — 유사하지 않다.
		- -1 — 반대 의미로 유사하다.
- 입력 ⇢ 계산 가능한 숫자 벡터 (임베딩 벡터) 변환 ⇢ 유사도 계산* ⇢ 높은 유사도 그룹에서 토큰 조합
- 유사도를 학습한 모델 (임베딩 모델) ⇢ 단어가 들어오면 유사도를 계산하고 변환 작업을 하는 AI 내 AI
	- 선택 기준
		- Top-k : e.g. Top-k 10 인 경우, 가장 확률 높은 10개 중에서 토큰 선택
		- Top-p : e.g. Top-p 10 인 경우, 가장 확률 높은 10% 중에서 토큰 선택
		- 각 값은 이미 최적화된 숫자가 있음 (많은 실험을 하면서 뭐가 가장 좋은지 평가를 통해서 결정)
		- 보통 Top-k와 Top-p를 같이 사용 (Top-p로 범위를 산정하고 Top-k로 개수를 좁혀 나가는 식)
		- Temperature (0 to 1)
			- 온도의 높낮이에 따라 토큰의 확률 비율 변동
			- 낮은 온도 — 더 정확한 답변 / 확률분포 작음. 정답 구간 좁음. 선택의 폭 적음
			- 높은 온도 — 더 다양한 (창의적) 답변 / 확률분포 큼. 정답 구간 넓음. 선택의 폭 넓음
- 컨텍스트 엔지니어링
	- AI가 사용자의 질문에 즉시 답변하지 않고 프롬프트를 자체적으로 보완한 후에 답변하는 형태로 발전
		- 사용자의 질문 ⇢ 검색 (도구 사용)* ⇢ 내부적으로 프롬프트 보완 ⇢ 확률 계산 ⇢ 답변
		- LLM에 도구 선택 질의 ⇢ 도구 선택 및 값 전달 ⇢ 프로그래밍 함수 호출 ⇢ 프롬프트 보완
		- 사용자에 맞춰 유사도를 높이는 형태로 심화될 수 있다는 것 (맥락 상 데이터를 제공하기 때문)
			- 단, 선택해야 할 도구 또는배경지식인 프롬프트 내용이 너무 많으면 오히려 유사도 저하
	- 단, 프롬프트를 사용할 때 프롬프트의 크기가 한정되어 있기 때문에 (컨텍스트 윈도우) 항상성은 부족
- AI 검증 SIFT 프레임워크
	1. Stop (멈추기)
		- AI 답변을 곧바로 믿지 않고 정보를 공유하거나 활용하기 전에 멈춤. 출처의 신뢰성을 먼저 의심
	2. Investigate the source (출처 조사하기)
		- AI가 제시한 근거를 확인하고 저자, 매체, 기관의 공신력 확인. 출처 조작 등의 환각 현상 검증
	3. Find better coverage (더 나은 정보 찾기)
		- 다른 엔진 또는 전문가나 신뢰할 수 있는 출처에서 같은 내용을 확인하고 교차 검증
	4. Trace claims to the original context (원래 맥락 추적하기)
		- 인용된 원본 데이터 (논문, 통계 등의 원문) 를 직접 찾고 AI가 요약하면서 맥락을 왜곡했는지 대조
#### Git 줄바꿈 문자 자동 변환 경고
- 무시해도 됨
- .gitattributes 파일 설정으로 해소 가능
```bash
# 기존 레포에 .gitattributes 추가 
echo "* text=auto eol=lf" > .gitattributes
git add .gitattributes
git commit -m "doc: gitattributes 추가, 줄바꿈 LF로 통일"
git push

# git init 할때마다 (또는 git clone 할 때) 자동으로 신규 레포에 복사 (템플릿 디렉토리)
mkdir %USERPROFILE%\.git-templates # 프로젝트 폴더가 아닌 전역환경에서 디렉토리 생성
echo * text=auto eol=lf > %USERPROFILE%\.git-templates\.gitattributes
git config --global init.templateDir "%USERPROFILE%/.git-templates" # 템플릿 폴더 알림
```
- 기타 — 원격 레포 별칭 까먹었을 때 : git remote
### 데일리 퀘스트
#### 1번 문항
- **Q**. 비동기 카페 시뮬레이션 실습에서 철수의 커피는 3초, 영희의 커피는 1초가 걸립니다. asyncio.gather()를 사용해 두 주문을 동시에 접수했을 때, 전체 작업이 완료되기까지 걸리는 총 소요 시간은 얼마인가요?
- **A**. 3초
- *asyncio.gather()로 여러 코루틴을 동시에 실행하면 각 작업의 대기 시간이 중첩되어 처리되므로, 전체 소요 시간은 가장 오래 걸리는 작업(철수의 3초)을 기준으로 결정됩니다. 두 시간을 합산한 4초가 걸린다는 것은 순차(동기) 처리 방식에 대한 오해입니다.*
#### 2번 문항
- **Q**. 실행 도중 필요한 경우 제어권(함수실행권한)을 잠시 양보하고, 다시 자기 차례가 되면 멈췄던 지점부터 이어서 작업을 수행할 수 있는 파이썬의 특수 함수를 무엇이라고 하나요?
- **A**. await **(오답)**
- *코루틴(Coroutine)은 일반 함수(서브루틴)와 달리 실행 중간에 멈췄다가 나중에 멈춘 지점부터 다시 이어갈 수 있는 협력형 함수로, async def로 정의되고 await 지점에서 제어권을 양보합니다.*
#### 3번 문항
- **Q**. 다음 중 'I/O Bound(입출력 중심)' 작업에 해당하는 사례로 가장 적절한 것은 무엇인가요?
- **A**. 외부 API 서버에 데이터를 요청하고 응답을 기다리는 작업
- *I/O Bound는 외부에 요청을 보내고 응답을 기다리는 지연 시간이 전체 속도를 좌우하는 상태입니다(외부 서버에 요청을 보내고 응답을 기다리는 작업). 반면 그래픽 렌더링, 파일 암호화, 이미지 압축은 모두 CPU가 쉬지 않고 연산을 수행하는 CPU Bound 작업에 해당합니다.*
#### 4번 문항
- **Q**. 대형언어모델(LLM)이 객관적 사실과 다르거나 현실에 존재하지 않는 내용을, 마치 확립된 진실인 것처럼 확신에 찬 어조로 그럴싸하게 생성해 내는 현상을 무엇이라고 하나요?
- **A**. 환각
- *환각 현상(Hallucination)은 LLM이 사실 검증 없이 통계적으로 가장 자연스러운 다음 단어를 예측하여 문장을 조립하는 원리에서 비롯되는 필연적인 기술적 부작용입니다.*
#### 5번 문항
- **Q**. AI 모델의 '컨텍스트 윈도우(Context Window)'에 대한 설명으로 가장 적절한 것은 무엇인가요?
- **A**. AI 모델이 한 번의 추론 과정에서 동시에 읽어 들이고 참고할 수 있는 텍스트(토큰)의 최대 허용 길이를 의미한다.
- *컨텍스트 윈도우는 AI의 단기 기억 용량이자 작업 책상의 크기로, 이 한도를 넘으면 오래된 대화 내용부터 삭제되어 기억 상실 현상이 발생합니다. 학습 마감 시점은 지식 컷오프, 텍스트 분할은 토큰화, 벡터 변환은 임베딩에 대한 설명입니다.*
