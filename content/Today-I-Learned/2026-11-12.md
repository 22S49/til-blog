# LLM (Large Language Model) 의 한계 

- 환각 현상 ─ 그럴듯하지만 사실이 아닌 잘못된 정보를 사실인 것처럼 생성한다.
- 지식 컷오프 ─ 학습 시점의 지식으로 고정되어 있어 그 이후의 지식은 없다. 그리고 특정 도메인의 지식도 없다.
	- 다만, 최근 API를 이용한 구현에서는 정제되기 때문에 이 문제는 꽤 해소되고 있다.
## 한계를 극복하기 위한 방안

| 구분          | RAG                                 | 파인튜닝                        |
| ----------- | ----------------------------------- | --------------------------- |
| **모양**      | 아키텍처, 패턴, 프레임워크                     | 학습 기법, 모델 적응 기법             |
| **대상**      | 모델 바깥의 시스템 구성 (검색기, 벡터 DB, 프롬프트 조립) | 모델 내부 (가중치)                 |
| **모델 영향도**  | 없음 (그대로 사용)                         | 있음 (파라미터 업데이트)              |
| **LLM 보완법** | 질문 때 필요한 지식을 프롬프트에 실어 보냄            | 사전에 데이터를 더 학습시켜 모델 자체를 바꿈   |
| **효과성 영역**  | 지식 주입과 근거 추적                        | 말투와 형식 보완 / 여전히 환각, 망각, 컷오프 |
| **최신화 방법**  | 문서만 갱신하면 즉시 반영 (인덱싱)                | 매번 모델 재학습                   |
| **초기 비용**   | 청킹, 임베딩, DB 영역 (상대적으로 저렴)           | 고품질 학습 데이터, GPU (상대적으로 비쌈)  |
| **추론 부담**   | 검색 지연과 긴 프롬프트 비용                    | 검색 단계가 없어 부담 없음             |
# RAG (Retrieval Augmented Generation)

- 기본 LLM의 한계를 극복하기 위해 제안된 아키텍처 
- 질문할 때마다 필요한 지식을 프롬프트에 실어 보내는 방식
- ① 지식 저장소(벡터DB)를 검색해서 ② 프롬프트를 작성하고(컨텍스트를 주입하고) ③ LLM 답변 생성
##### ※ RAG 파이프라인별 주요 요소

| 단계                      | 입력        | 출력       | LLM 관여       |
| ----------------------- | --------- | -------- | ------------ |
| 1단계 : 검색 (Retrieval)    | 사용자 질의    | 관련 배경지식  | 없음 (임베딩 모델만) |
| 2단계 : 증강 (Augmentation) | 질의 + 배경지식 | 증강된 프롬프트 | 없음 (템플릿 조립)  |
| 3단계 : 생성 (Generation)   | 증강된 프롬프트  | 최종 답변    | 있음           |
## 프롬프트 증강

- 증강의 대상은 LLM 답변이 아니라 입력하는 프롬프트
- 예시 
	- 증강 전 프롬프트 ─ `전자책 환불되나요?`
	- 증강 후 프롬프트 ─ 지시문 + 참고자료 + 질문 (아래 참조)
```
[시스템 지시] 아래 참고 자료만 근거로 답하세요.

[참고 자료]
- 문서 A: 환불은 구매 후 14일 이내 가능...
- 문서 B: 디지털 상품은 다운로드 후 환불 불가...

[질문]
전자책 환불되나요?
```

### 1. 인덱싱

| 단계             | 원래 의미         | RAG에서 하는 일                      |
| -------------- | ------------- | ------------------------------- |
| Extract (추출)   | 원천 데이터를 가져옴   | PDF, 웹, DB, 노션 등에서 문서 로드        |
| Transform (변환) | 쓸 수 있는 형태로 가공 | 텍스트 정제, 청킹, 임베딩(청크 텍스트 → 청크 벡터) |
| Load (적재)      | 목적지에 저장       | 벡터 DB에 저장                       |
#### 1-1. 청킹 ─ 데이터를 적당한 크기로 나누어 묶음 

- 컨텍스트 윈도우 크기에 한계가 있기 때문에 모든 지식을 담지 못하고 중요한 지식만 청킹할 필요가 있다.
		- 너무 긴 컨텍스트는 의미적 유의성이 떨어지고 LLM 답변 품질이 떨어지므로 관련성 높은 지식만 청킹
	- 청크 크기의 정답은 없고 최적 사이즈는 품질 평가를 통해 조정
			- *e.g.* 청크 크기는 보통 300~500 토큰에 10~20% 오버랩으로 시작하고 `small-to-big` 기법 사용
##### ※ 청크 크기별 장단점

| 구분            | 작은 청크 (~100~200 토큰)        | 큰 청크 (~800~1500 토큰 이상)        |
| ------------- | -------------------------- | ----------------------------- |
| **검색 정밀도**    | 높음 (한 청크에 한 주제만 담김)        | 낮음 (여러 주제가 섞여 벡터가 흐려짐)        |
| **문맥 보존**     | 약함 (앞뒤 설명이 잘려 나감)          | 좋음 (맥락이 통째로 들어감)              |
| **검색 누락 위험**  | 답이 여러 청크에 쪼개져 일부만 검색될 수 있음 | 답이 들어 있어도 노이즈에 묻혀 순위가 밀릴 수 있음 |
| **LLM 입력 비용** | 적음 (top-k를 늘려도 부담 작음)      | 큼 (토큰 비용, 지연 증가)              |
| **저장·인덱스 규모** | 청크 수가 많아져 벡터 DB 커짐         | 청크 수 적음                       |
| **환각 위험**     | 문맥이 부족해 LLM이 추측할 여지가 생김    | 불필요한 내용이 섞여 엉뚱한 근거를 쓸 수 있음    |
| **잘 맞는 문서**   | FAQ, 짧은 정의, 용어집            | 논문, 계약서, 법령처럼 문맥 의존이 큰 문서     |
##### ※ 청크 크기와 함께 고려할 것

- 오버랩(Overlap) ─ 청크 경계를 겹치게 잘라서 문장이 경계에서 의미가 끊기는 문제를 줄임 (저장량 증가)
- 구조 기반 분할 ─ 글자 수가 아닌 문단, 제목, 문장 경계에서 자르는 방식 (크기는 상한선으로만 사용)
	- 문단은 이미 완결된 의미 단위라 오버랩의 필요성이 낮다.
	- 문단 간 맥락이 중요하면 오버랩을 문단 길이 수준으로 늘리거나 청크 크기를 줄여서 성능을 높인다.
- top-k 균형 ─ 청크가 작으면 k를 키우고 청크가 크면 k를 줄여서 LLM에 들어가는 전체 컨텍스트 양을 맞춤
#### 1-2. 임베딩 ─ 지식을 컴퓨터가 읽을 수 있는 언어인 벡터로 압축하는 과정

- 임베딩 모델에 따라 최대 입력 길이 제한이 있기 때문에 청크 크기는 반드시 이 한도 안에 있어야 한다. 
- 도메인의 특성을 잘 받영할 수 있는 고성능 임베딩 모델을 선정하는 것이 RAG 구현 시 성능 튜닝 포인트
#### 1-3. 적재 ─ 사전 지식을 굳이 벡터 DB에 영구 저장하지 않고 메모리에 적재하는 경우도 있다. 

- **영구 저장이 필요한 경우**
	- 문서가 많아서 매번 재임베딩하면 시간과 비용(임베딩 API 호출)이 큰 경우
	- 서비스로 운영해서 여러 서버와 사용자가 같은 지식을 써야 하는 경우
	- 문서가 자주 추가되거나 수정돼서 부분 갱신이 필요한 경우
- **메모리 적재를 쓰는 경우**
	- 학습, 프로토타입, 실습처럼 빠르게 흐름만 확인하려는 경우
	- 문서 양이 적은 경우 (수천 청크 이하)
	- 사용자가 올린 파일 하나를 그 세션 동안만 질의하는 경우 (파일 업로드 후 질문하는 챗봇 등)
	- 테스트나 평가처럼 매번 깨끗한 상태에서 돌리고 싶은 경우
### 2. 검색

- (검색 전) Rewrite Query
	- 질문을 LLM 에 주입하고 검색에 적합한 질문으로 변환
		- *e.g.* `그거 어떻게 해?` → `Python에서의 리스트 중복 제거 방법이 뭐야?`
- 질문을 임베딩 모델에 통과 ─ 유사도 계산을 위한 수치로 변경 (질문 → 고차원 벡터)
	- 단, 질의와 청크는 반드시 같은 임베딩 모델로 벡터화해야 한다.
	- 임베딩 모델이 다르면 벡터 공간이 달라서 유사도 점수에 의미가 없어진다. 
	- 사용자가 질의한 내용과 관련있는 내용을 검색하는 것이 결국 LLM 품질에 영향을 준다. 
- 질문과 가장 의미가 유사한 배경지식 청크 추출 ─ 유사도 측정 (코사인 유사도, 유클리드 거리, 내적 등)
##### ※ 유사도 측정 기법 비교

| 구분        | 코사인 유사도               | 유클리드 거리 (L2)                      | 내적 (Dot Product)         |
| --------- | --------------------- | --------------------------------- | ------------------------ |
| **측정 대상** | 두 벡터 사이의 각도 (방향)      | 두 점 사이의 직선 거리                     | 방향 + 크기                  |
| **계산 공식** | `a·b / (‖a‖‖b‖)`      | `√Σ(aᵢ − bᵢ)²`                    | `Σ aᵢbᵢ`                 |
| **값의 범위** | -1 ~ 1                | 0 ~ ∞ (음수 없음)                     | -∞ ~ ∞                   |
| **유사도 값** | 클수록                   | 작을수록                              | 클수록                      |
| **최고 점수** | 1 (같은 방향)             | 0 (완전히 같은 점)                      | 상한 없음                    |
| **음수 의미** | 반대 방향                 | 나올 수 없음                           | 반대 방향                    |
| **벡터 크기** | 무시함                   | 반영함                               | 반영함                      |
| **정규화 값** | 내적과 값이 동일             | 값은 다르지만 순위는 동일<br>(코사인과 단조 감소 관계) | 코사인과 값이 동일               |
| **계산 비용** | 정규화 과정 필요 (분모 계산)     | 제곱합 + 제곱근 필요                      | 가장 가벼움                   |
| **활용 예시** | 텍스트 임베딩, 문서 검색 (RAG)  | 이미지·좌표 등 절대적 거리가 중요한 경우, 클러스터링    | 추천 시스템, 정규화된 임베딩의 고속 검색  |
| **주의 사항** | 크기에 담긴 정보(인기도 등)는 버려짐 | 고차원에서 거리 값이 서로 비슷해지는 경향           | 정규화하지 않으면 크기가 큰 벡터가 유리해짐 |
- *cf.* 키워드 유사성 조회 ─ BM25 (BestMatching25) 검색 알고리즘 
	- 보통 유사도 측정과 키워드 유사성 조회를 조합해서 사용한다. (하이브리드 검색)
- (검색 후) Reranking 
	- 조회 데이터를 여러 개 가져와서 맥락에 맞는 우선순위로 재배치 (선택적으로 LLM 활용)
	- 선택적으로 LLM 을 사용하기도 하지만 보통 Cross-Encoder 같은 전용 reranker 모델을 사용한다. 
### 3. 증강 및 생성

```python
import os
from langchain.chat_models import init_chat_model
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter, CharacterTextSplitter

API_KEY = os.getenv('API_KEY')  # 키를 한 곳에서만 읽어서 재사용

# ---------- 1. 인덱싱 ----------
raw_text = """텍스트 입력 / 한 줄로 이어서 붙여도 되지만 문단을 나눠도 된다."""

# 청킹: 긴 문서를 검색 단위로 자르는 단계
#  - Recursive는 문단(\n\n) → 줄(\n) → 공백 → 글자 순으로 구분자를 내려가며 자름
#  - chunk_size   : 조각 하나의 최대 길이(글자 수)
#  - chunk_overlap: 앞뒤 조각이 겹치는 길이. 문장 중간이 잘려도 맥락이 이어지게 하는 안전장치
text_splitter = RecursiveCharacterTextSplitter(chunk_size=90, chunk_overlap=20,)
split_docs = text_splitter.create_documents([raw_text])

# [참고] CharacterTextSplitter를 쓰는 경우 (위 Recursive 대신 사용)
#  - 구분자를 하나만 쓰는 단순한 분할기. 기본 구분자는 "\n\n"(문단)
# text_splitter = CharacterTextSplitter(separator="", chunk_size=90, chunk_overlap=20,)

# 임베딩: 텍스트 → 숫자 벡터. 의미가 비슷하면 벡터도 가까워짐
embedding_model = OpenAIEmbeddings(model='text-embedding-3-small', api_key=API_KEY,)

# 적재: 청크를 임베딩해서 메모리 벡터저장소에 저장 (프로그램 종료 시 사라짐)
vector_store = InMemoryVectorStore.from_documents(
    documents=split_docs,
    embedding=embedding_model,
)

# ---------- 2. 검색 ----------
# k=1: 질문과 가장 유사한(기본값: 코사인 유사도) 청크 1개만 가져옴
retriever = vector_store.as_retriever(search_kwargs={'k': 1})
user_query = 'raw_text 기반으로 질문할 내용을 작성한다.'
retrieved_docs = retriever.invoke(user_query)

# ---------- 3. 생성 ----------
model = init_chat_model(model_provider='openai', model='gpt-6-luna', api_key=API_KEY)

# 프롬프트: 검색된 문서(context)만 근거로 답하게 해서 환각(없는 말 지어내기)을 줄임
prompt = ChatPromptTemplate.from_messages([
    ('system', '제공된 [참고문서]의 내용만을 근거해 답변하세요. '
               '[참고문서]에서 없는 내용은 모른다고 답변하세요.\n\n[참고문서]:\n{context}'),
    ('user', '{question}'),
])

# LCEL: '|' 로 프롬프트 → 모델 → 문자열 파서를 순서대로 연결
chain = prompt | model | StrOutputParser()
response = chain.invoke({
    # k를 늘려도 동작하도록 검색된 청크 전부를 합쳐서 전달
    'context': '\n\n'.join(doc.page_content for doc in retrieved_docs),
    'question': user_query,
})
print(response)
```
# **PEFT**(Parameter-Efficient Fine-Tuning)
- 기존 LLM의 학습 파라미터는 유지하고 새로운 파라미터를 추가하는 파인튜닝 기법
	- 기존 모델 가중치는 고정하고 작은 추가 파라미터만 학습
	- 전체를 다시 학습하지 않아서 메모리와 비용을 줄여서 일반 파인튜닝 모델의 한계를 일부 보완하지만
	- LLM 과 마찬가지로 학습 시점에 지식이 고정되기 때문에 LLM의 한계를 그대로 답습하는 한계가 있다. 
- LoRA ─ 작은 행렬(저랭크)을 추가해서 학습하고, 기존 가중치와 합쳐서 사용 (가중치 조합)
- ReFT ─ 가중치가 아니라 모델 내부 표현(hidden representation)을 조정하는 방식 
	- LoRA와의 비교를 위해 가중치 조합보다는 모델 내부 표현에 개입하는 형식으로 이해하는 것이 적절
# 유사도 측정 실험

| 입력                | 유사도   | 해석                     |
| ----------------- | ----- | ---------------------- |
| 단어 : 사과, 포도       | 0.256 | 단어 하나는 의미 구분이 약함       |
| 사과는 맛있어 / 포도는 시어요 | 0.245 | 순서는 맞지만 유사도 절댓값은 낮음    |
| 사과는 맛있어 / 나무가 울창해 | 0.155 | 술어가 달라서 유사도 낮음         |

| 사과는 맛있어 / 나무는 맛있어 | 0.529 | 어색한 문장인데도 유사도가 포도보다 높음 |
## 확인한 내용

- 짧은 문장에서는 주제(과일)보다 술어와 문장 형태가 유사도를 좌우함
- 절댓값이 낮은 것은 정상이며, 상대 순위로 판단해야 함
- 영어로 실험해도 순위 패턴은 동일했고, 한국어는 전체 값이 0.1~0.2 낮았음
	- 물론 임베딩 모델이 영어권 기반으로 만들어져 있어 영어, 한국어 사용 간 차이가 있다는 점은 고려해야 함
- 벡터가 정규화되어 있으면 `cos = 1 − d²/2`가 성립하여 코사인과 유클리드는 같은 정보임
	- 유클리드 1.005는 코사인 0.495와 일치함
- RAG처럼 문장이 길고 정보가 많은 경우에는 이 현상이 줄어듦
