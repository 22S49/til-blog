쿼리스트링 ─ 질의를 위한 언어
- 변경되는 식별자는 쿼리스트링보다 URI에 포함해서 작성하는 것이 표준 ??????????????????
- 실제 의미는 **식별자 값을 경로 변수(path variable)로 넣는다**는 뜻이야.

```
표준:     GET /users/123
비표준:   GET /users?id=123
```

여기서 `123`이라는 식별자 값이 URI 경로의 한 세그먼트로 들어가 있지. “URI에 포함”이라고 하면 "쿼리스트링도 URI의 일부인데?"라는 반박이 나올 수 있어서 부정확한 표현이고, 정확히 쓰면 이렇게 돼.

> 리소스를 식별하는 값은 쿼리스트링이 아니라 **경로(path)** 에 작성한다.

이게 REST 관점에서 맞는 이유는, 경로는 "어떤 리소스인가"를 가리키고 쿼리스트링은 그 리소스(또는 컬렉션)를 **필터링·정렬·페이징** 같은 방식으로 조회하는 옵션을 나타내기 때문이야.

```
GET /users/123              → 특정 사용자 한 명 (식별)
GET /users?role=admin&page=2 → 사용자 컬렉션을 조건으로 조회 (필터/페이징)
```

"쿼리스트링을 그대로 쓰지 않는다"는 건 **식별자를 `?id=123` 형태로 넘기지 않고, 경로에 녹여서 URI 자체가 리소스를 가리키게 한다**는 뜻이야. 둘은 같은 원칙의 앞뒤 면이라고 보면 돼.

### 핵심 개념: URI = 리소스의 이름

REST에서 URI는 "무엇에 대한 요청인가"를 나타내는 **리소스의 주소**야. 그래서 어떤 리소스인지를 결정하는 값(식별자)은 주소의 일부, 즉 경로에 있어야 해.

```
/users/123          → "사용자 123"이라는 리소스의 주소
/users?id=123       → "사용자 컬렉션"에 id=123이라는 옵션을 붙여 요청
```

후자는 주소가 `/users`로 같고 옵션만 다른 거라, 리소스를 **식별**하는 게 아니라 컬렉션을 **검색**하는 모양이 돼.

### 쿼리스트링을 그대로 쓰면 생기는 문제

1. **리소스 계층이 안 드러남**  
    `/users/123/orders/456`은 “123번 사용자의 456번 주문”이라는 관계가 읽히지만, `/orders?userId=123&orderId=456`은 단순한 파라미터 나열이야.
2. **의미가 흐려짐**  
    쿼리스트링은 원래 필터·정렬·페이징처럼 "조회 방식"을 위한 자리야. 식별자까지 여기 넣으면 식별과 검색의 경계가 사라져.
3. **캐싱·로깅·라우팅이 불리함**  
    경로 기반이면 `/users/123` 같은 단위로 캐시하고 모니터링하기 쉽고, 프레임워크나 게이트웨이도 경로 패턴으로 라우팅하기 편해. 쿼리스트링은 파라미터 순서나 유무에 따라 같은 요청이 다른 URL로 취급될 수도 있어.
4. **응답 형태가 모호해짐**  
    `/users?id=123`은 결과가 한 명인지 목록(길이 1)인지 애매해. `/users/123`은 단건이라는 게 명확해.

### 정리

|구분|위치|역할|
|---|---|---|
|식별자 (어떤 리소스?)|경로 `/users/{id}`|리소스를 **특정**|
|필터·정렬·페이징|쿼리스트링 `?role=admin&page=2`|리소스(컬렉션)를 **조회하는 방식**|

## 비교

|       | 기본값 방식                                         | Annotated 방식                                        |
| ----- | ---------------------------------------------- | --------------------------------------------------- |
| 코드    | `item_id: int = Path(..., description='상품ID')` | `item_id: Annotated[int, Path(description='상품ID')]` |
| 타입    | `int`                                          | `int` (`Annotated`의 첫 번째 인자)                        |
| 메타데이터 | 기본값 자리에 `Path(...)`를 넣음                        | 타입 옆에 `Path(...)`를 붙임                               |
| 기본값   | 기본값 자리를 메타데이터가 차지함                             | 기본값 자리가 비어 있어서 `= None`처럼 진짜 기본값을 쓸 수 있음            |
