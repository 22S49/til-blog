## 이어서 보면 좋은 연결

**1. 요청이 지나가는 길**

```
브라우저/앱 ─ HTTP 요청 ─▶ uvicorn ─▶ FastAPI 라우터 ─▶ 스키마 검증(Pydantic)
                                                          ↓
                                                    도메인 규칙 검사
                                                          ↓
브라우저/앱 ◀─ JSON 응답 ◀─ 응답 모델(APIResponse) ◀─ 처리 결과
                                  ↑ 실패하면 예외 핸들러가 4xx로 변환
```

**2. Next.js와 FastAPI의 관계**

- Next.js는 **화면 쪽**, FastAPI는 **데이터와 규칙 쪽**이라 서로 대체하는 게 아니라 연결해서 써.
- Next.js에서 `fetch('http://서버/books')`로 FastAPI의 엔드포인트를 호출하는 구조야. 우리가 Flashpost로 `POST /books`를 보낸 게 그 호출을 손으로 흉내 낸 거야.
- 응답을 `{success, data, error}`로 통일해 둔 것도 프론트가 응답을 일정하게 처리하려는 이유가 커.

**3. Jinja2와 Next.js는 같은 문제를 푸는 다른 방법**

|구분|Jinja2 (FastAPI)|Next.js|
|---|---|---|
|누가 HTML을 만드나|파이썬 서버|Node 서버 (React)|
|데이터를 넣는 법|`context`와 `{{ }}`|props, 컴포넌트|
|화면 쪼개기|`include`, `macro`, `extends`|컴포넌트, 레이아웃|
|언제 쓰나|단순한 서버 렌더링 페이지|상호작용이 많은 화면|
**프론트 프로젝트와 지금 백엔드의 차이**

|구분|Next.js + Supabase|FastAPI + (앞으로) DB|
|---|---|---|
|데이터 저장소|Supabase(Postgres)를 서비스로 빌려 씀|직접 DB를 연결하고 관리|
|서버 로직|Server Actions와 queries에서 Supabase 호출|라우터와 도메인 모델에서 처리|
|인증|Supabase Auth가 제공|직접 구현해야 함 (JWT 등)|
|API|Supabase가 자동으로 제공|엔드포인트를 직접 설계|
|ERD, 테이블 설계|`createTable.sql`|똑같이 필요|

- Supabase는 DB, 인증, API를 묶어서 주는 BaaS야. 그래서 FastAPI 같은 별도 API 서버 없이 Next.js에서 바로 DB로 갔던 거야.
- 지금 배우는 건 그 "묶음"을 직접 풀어서 만드는 거야. 인증, 검증, 규칙, API 설계를 내가 직접 하는 거지.
- ERD와 테이블 설계는 방식이 달라도 그대로 쓰여. 다음에 FastAPI에 DB를 붙일 때 네가 그린 ERD 감각이 바로 도움이 될 거야.
- 네 Next.js 프로젝트의 `domains/todo/queries`, `actions`, `utils`(검증) 구조는 지금 배우는 도메인 분리, 검증, 저장 분리와 같은 생각이야. 이름만 다르고 구조는 비슷해.

**흐름에 한 줄 보정하면**

```
Next.js + Supabase → 화면과 DB를 직접 연결 (BaaS가 서버 역할을 대신함)
  ↓ 여러 화면이 같은 규칙을 쓰고, 서버 로직을 직접 통제하고 싶어서
API 서버(FastAPI) → 직접 만드는 백엔드
  ...
  ↓ 메모리 저장의 한계
DB 연동 → Supabase 때 쓴 Postgres + ERD를, 이번엔 SQLAlchemy로 서버에서 직접 연결
```


보통은 **API 구조가 어느 정도 잡힌 직후**에 해. 순서로 보면 이래.

```
1. 요구사항 파악, 엔드포인트 설계 (어떤 자원이 있고 어떤 메서드가 필요한지)
2. 도메인 모델, 스키마 작성 (규칙과 검증)
3. 메모리(리스트, dict)로 먼저 동작시켜 보기   ← 지금 네 위치
4. 라우터 분리, 예외 처리 정리
5. DB 연동 (저장소만 교체)
6. 인증, 테스트, 배포
```

**왜 이 시점이냐면**

- 메모리로 먼저 돌려 보면 API 설계와 규칙이 맞는지 DB 없이 빠르게 확인할 수 있어. 테이블을 먼저 만들면 설계가 바뀔 때마다 마이그레이션까지 따라 바꿔야 해서 번거로워.
- 도메인이 DB를 모르게 만들어 뒀다면, 저장하는 부분(`books = []` 같은 곳)만 DB 코드로 바꾸면 돼. 이게 도메인 독립성을 지키는 이유야.
- 메모리 저장은 서버를 재시작하면 날아가니까, "데이터가 남아야 의미 있는 시점"이 오면 붙여.

**예외도 있어**

- 데이터 구조가 핵심인 서비스(주문, 결제, 재고 등)는 ERD를 먼저 그리고 시작하기도 해. 네가 Next.js 프로젝트에서 ERD부터 그린 것처럼.
- 그래도 순서는 보통 "ERD 설계(종이/도구) → 도메인, API → DB 연동"이야. ERD는 일찍 그리지만 실제로 DB를 코드에 붙이는 건 뒤야.

파일 업로드 시
**`multipart/form-data`** 를 말하는 거야. 파일은 글자가 아니라 바이너리 데이터라서 JSON으로 보낼 수 없어서, 요청 본문을 여러 조각(part)으로 나눠서 보내는 방식을 써.

## 요청 방식 비교

|Content-Type|언제 쓰나|본문 모양|
|---|---|---|
|`application/json`|API 데이터 (지금까지 쓴 것)|`{"title": "파이썬"}`|
|`application/x-www-form-urlencoded`|일반 HTML 폼 (practice03 폼의 기본값)|`title=a&content=b`|
|**`multipart/form-data`**|**파일 업로드**, 파일과 글자를 같이 보낼 때|조각마다 이름, 타입, 내용|

multipart는 이런 모양이야.

```
--경계문자열
Content-Disposition: form-data; name="title"

파이썬
--경계문자열
Content-Disposition: form-data; name="file"; filename="a.png"
Content-Type: image/png

(바이너리 데이터)
--경계문자열--
```

## HTML 폼에서

```html
<form method="post" action="/upload" enctype="multipart/form-data">
  <input type="file" name="file" />
  <button type="submit">업로드</button>
</form>
```

- `enctype="multipart/form-data"`를 **꼭 써야 해**. 안 쓰면 파일 내용 대신 **파일 이름 글자만** 전송돼.
- `method`는 `post`여야 해.

## FastAPI에서

```python
from fastapi import UploadFile, File, Form

@app.post('/upload')
async def upload(
    title: str = Form(...),          # 글자 필드
    file: UploadFile = File(...),    # 파일 필드
):
    content = await file.read()      # 파일 내용 (bytes)
    return {'title': title, 'filename': file.filename, 'size': len(content)}
```

|구분|의미|
|---|---|
|`UploadFile`|업로드된 파일 객체 (`filename`, `content_type`, `read()`)|
|`File(...)`|이 매개변수가 파일 파트라는 표시|
|`Form(...)`|글자 파트. 앞에서 정리한 `Form`이 이거야|

- 매개변수 이름(`file`, `title`)은 HTML `name="..."`과 **같아야** 해.
- `file.read()`는 비동기라서 `await`를 붙여.
- **`Body(...)`와 `File`/`Form`은 한 요청에서 같이 못 써.** 파일을 보낼 땐 JSON 본문이 아니라 폼이라서, 나머지 값도 `Form`으로 받아야 해.

{% extends %}와 {% include %}의 용도 차이에 대한 설명으로 가장 적절한 것은?
