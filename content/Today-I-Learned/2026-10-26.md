3. 그래도 밑줄이 남으면 `Ctrl+Shift+P`에서 `Developer: Reload Window`를 실행합니다.

**참고**

- VS Code를 `ax_study` 루트에서 열었다면 `chapter01-1` 안의 `.venv`를 자동으로 찾지 못합니다. 그래서 위처럼 직접 선택해야 합니다. `chapter01-1` 폴더를 따로 열면 자동으로 잡힐 가능성이 큽니다.
- 터미널에서 실행할 때는 `uv run uvicorn src.main:app --reload`처럼 `uv run`을 쓰거나, 먼저 `.venv\Scripts\activate`를 하세요. 그냥 `python`이나 `uvicorn`을 치면 시스템 파이썬이 실행돼서 같은 오류가 납니다.



`uv run uvicorn main:app --app-dir src --reload`는 "프로젝트 가상환경에서 uvicorn 서버를 띄워 `src/main.py`의 FastAPI 앱을 실행하고, 코드가 바뀌면 자동으로 재시작해라"라는 뜻입니다.

| 단어              | 의미                                                                                                                                                  |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uv`            | 파이썬 패키지·환경 관리 도구입니다. pip와 venv를 합친 것에 가깝습니다.                                                                                                        |
| `run`           | uv의 하위 명령입니다. 프로젝트의 `.venv`를 쓰는 상태에서 뒤의 명령을 실행합니다. 의존성이 `pyproject.toml`과 맞는지도 확인하고 필요하면 동기화합니다.                                                    |
| `uvicorn`       | 실행할 프로그램입니다. FastAPI는 그 자체로 서버가 아니라서, HTTP 요청을 받아 앱에 넘겨주는 ASGI 서버가 따로 필요합니다. uvicorn이 그 역할을 합니다.                                                    |
| `main:app`      | uvicorn이 실행할 앱의 위치입니다. `모듈명:변수명` 형식입니다. 여기서는 `main.py` 파일 안의 `app` 변수, 즉 `app = FastAPI()`로 만든 객체를 뜻합니다.                                            |
| `--app-dir src` | uvicorn이 `main`을 찾을 때 `src` 폴더 안에서 찾게 합니다. `main.py`가 프로젝트 루트가 아니라 `src/`에 있어서 필요합니다. 이 옵션이 없으면 `ModuleNotFoundError: No module named 'main'`이 납니다. |
| `--reload`      | 코드 파일이 저장될 때마다 서버를 자동으로 다시 시작합니다. 개발할 때 편하게 쓰는 옵션입니다. 운영 환경에서는 쓰지 않습니다.                                                                             |

**실행 순서**

1. `uv`가 `.venv`를 준비합니다. 여기에 fastapi와 uvicorn이 들어 있습니다.
2. 그 환경에서 `uvicorn`이 실행됩니다.
3. uvicorn이 `src` 폴더를 기준으로 `main.py`를 불러옵니다.
4. 그 안의 `app` 객체를 서버에 연결합니다. 기본 주소는 `http://127.0.0.1:8000`입니다.
5. 파일을 감시하다가 수정되면 서버를 다시 띄웁니다.

**참고**

- 앞에서 쓴 `src.main:app`과 지금 쓴 `main:app --app-dir src`는 같은 일을 하는 다른 방식입니다. `src/__init__.py`가 없어도 동작하는 쪽은 지금 쓴 `--app-dir` 방식입니다.
- 포트나 외부 접속이 필요하면 `--port 8080`, `--host 0.0.0.0`을 덧붙이면 됩니다.

`uv run uvicorn main:app --app-dir src --reload --log-level debug`

3. REST의 6대 설계 원칙 (RESTful의 조건)

IBM과 Red Hat 등에서 정의하는 REST 아키텍처 원칙은 다음과 같습니다:
• 균일한 인터페이스 (Uniform Interface): URI로 지정한 자원을 통일된 방식으로 조작합니다.
• 클라이언트-서버 분리 (Client-Server): 클라이언트(UI 등)와 서버(데이터 처리/저장)의 역할이 완전히 독립적입니다.
• 무상태 (Stateless, 스테이트리스): 서버는 클라이언트의 상태를 기억하지 않으며, 각각의 요청은 독립적으로 처리됩니다.
• 캐시 가능 (Cacheable): HTTP 캐시 기능을 사용하여 응답을 재사용할 수 있습니다.
• 계층화된 시스템 (Layered System): 중간에 프록시, 게이트웨이 등의 보안·로드밸런싱 계층을 둘 수 있습니다.
• 코드 온디맨드 (Code on Demand): 서버에서 클라이언트로 실행 가능한 코드(예: JavaScript)를 전송해 기능을 확장할 수 있습니다 (선택 사항).


REST와 SOAP의 가장 핵심적인 차이는 REST는 유연한 '아키텍처 스타일'인 반면, SOAP은 보안과 신뢰성을 보장하는 엄격한 '프로토콜'이라는 점입니다.

---

1. REST vs SOAP 핵심 비교

|비교 항목|REST (Representational State Transfer)|SOAP (Simple Object Access Protocol)|
|---|---|---|
|**개념**|웹 표준(HTTP)을 활용한 설계 아키텍처 스타일|자체 표준 규격을 가진 엄격한 메시지 프로토콜|
|**데이터 형식**|**JSON**, XML, Text, HTML 등 다양하게 지원|**XML만 사용 가능** (봉투 구조로 래핑 필요)|
|**프로토콜**|HTTP / HTTPS 만 사용|HTTP, HTTPS, SMTP, FTP 등 다양한 프로토콜 사용 가능|
|**보안성**|HTTPS(SSL/TLS) 기반 전송 보안 위주|WS-Security 표준 지원 (메시지 레벨의 고도 보안)|
|**성능/무게**|구조가 단순하고 JSON을 써서 **가볍고 빠름**|XML 파싱 및 무거운 헤더 때문에 **상대적으로 느림**|
|**상태 관리**|무상태 (Stateless) 지원|상태 저장 (Stateful) 및 무상태 모두 지원|

---

2. 주요 차이점 상세 분석

- **데이터 포맷과 오버헤드**: REST는 현대 웹에서 가장 많이 쓰이는 가벼운 JSON을 주로 사용하여 데이터 전송량이 적고 처리가 빠릅니다. 반면 SOAP은 모든 메시지를 복잡한 XML 형태(`Envelope`, `Header`, `Body` 구조)로 감싸야 하므로 시스템 리소스를 더 많이 소모합니다.
- **보안 및 신뢰성**: REST는 웹 표준 보안(HTTPS)에 의존합니다. 반면 SOAP은 자체적인 기업용 보안 규격인 `WS-Security`를 지원하여, 데이터가 전송되는 과정뿐만 아니라 메시지 자체를 암호화하는 등 금융 거래 수준의 고도 보안을 제공합니다. 또한 오류가 발생했을 때 복구할 수 있는 ACID 트랜잭션 처리가 기본으로 지원됩니다.
- **표준과 엄격함**: SOAP은 `WSDL(Web Services Description Language)`이라는 명세서를 통해 서버와 클라이언트가 주고받을 데이터 타입을 엄격하게 정의합니다. 규칙을 어기면 통신 자체가 불가능합니다. 반면 REST는 상대적으로 규칙이 느슨하여 개발자 친화적이고 유연합니다.

3. 언제 어떤 것을 써야 할까요?

- **REST를 선택해야 하는 경우**
    - 모바일 앱, 웹 애플리케이션 등 트래픽이 많고 빠른 응답 속도가 중요할 때
    - 리소스(서버 용량, 대역폭)가 제한적인 환경일 때
    - 데이터 가독성과 빠른 개발 속도가 필요할 때
- **SOAP를 선택해야 하는 경우**
    - 은행 시스템, 결제 게이트웨이, 항공 예약 등 금융·결제 관련 보안이 절대적으로 중요할 때
    - 엄격한 API 계약(Contract)이 필요하여 데이터 규격 오류를 원천 차단해야 할 때
    - 비동기 처리나 레거시 시스템(엔터프라이즈 환경)과의 연동이 필요할 때

1. URI는 자원(Resource)을 표현하는 데 집중

- **명사를 사용하세요:** 행위를 뜻하는 동사(`/getUser`, `/deleteOrder`)는 URI에 포함하지 않습니다. 행위는 HTTP 메서드로 표현합니다.
    
    - ❌ `GET /getUsers` -> ⭕ `GET /users`
    - ❌ `POST /createNewUser` -> ⭕ `POST /users`
- **단수형보다는 복수형 명사를 권장합니다:** 일관성을 위해 컬렉션을 의미하는 복수형 명사(`users`, `products`)를 사용하는 것이 관례입니다.
    - ⭕ `GET /users/123` (아이디가 123인 유저 조회)
- **계층 관계는 슬래시(/)로 표현합니다:**
    - ⭕ `GET /users/123/orders` (123번 사용자의 주문 목록 전체 조회)
    - ⭕ `GET /users/123/orders/5` (123번 사용자의 5번 주문 상세 조회)

---

2. 가독성을 위한 URI 규칙

- **소문자를 사용하세요:** URI는 대소문자를 구분하지만, 혼란을 방지하기 위해 표준적으로 소문자만 사용합니다.
- **하이픈(-)을 쓰고, 언더바(_)는 쓰지 마세요:** 가독성을 높일 때는 하이픈(케밥 케이스)을 사용합니다. 언더바는 폰트에 따라 밑줄에 가려져 안 보일 수 있어 금지합니다.
    - ❌ `/user_profile` -> ⭕ `/user-profiles`
- **파일 확장자를 포함하지 마세요:** 데이터 포맷은 URI에 쓰지 않고, HTTP 헤더(`Accept: application/json`)를 통해 소통합니다.
    - ❌ `/users/123/profile.jpg`

3. HTTP 메서드의 올바른 역할 부여

- **GET**: 서버 상태를 바꾸지 않는 **안전한 조회(Read)** 요청에만 씁니다. (비밀번호 변경 등 상태 변경에 절대 금지)
- **POST**: 새로운 자원을 **생성(Create)**할 때 씁니다.
- **PUT vs PATCH**: 수정(Update) 시 반드시 구분하세요.
    - **PUT**: 자원 **전체**를 교체할 때 사용합니다. (보내지 않은 필드는 null 처리될 수 있음)
    - **PATCH**: 자원의 **일부 필드**만 수정할 때 사용합니다. (실무에서 대부분 권장)

4. HTTP 상태 코드(Status Code) 명확히 반환하기

성공 시 무조건 `200 OK`만 던지거나, 실패 시 무조건 `500 Server Error`로 퉁치는 것은 나쁜 설계입니다.

- **성공 (2xx)**
    - `200 OK`: 요청 성공 (조회, 수정 등)
    - `201 Created`: 생성 성공 (POST 요청 후 새 자원이 만들어졌을 때)
    - `204 No Content`: 성공했으나 응답 본문에 보낼 데이터가 없을 때 (주로 DELETE 성공 후)
- **클라이언트 잘못 (4xx)**
    - `400 Bad Request`: 요청 파라미터가 잘못되었거나 형식이 맞지 않을 때
    - `401 Unauthorized`: 인증되지 않은 사용자 (로그인 필요)
    - `403 Forbidden`: 인증은 되었으나 해당 자원에 접근 권한이 없을 때
    - `404 Not Found`: 존재하지 않는 URI 또는 찾을 수 없는 자원
- **서버 잘못 (5xx)**
    - `500 Internal Server Error`: 서버 내부 로직 오류 (이 코드가 클라이언트에게 자주 노출되지 않도록 예외 처리를 잘해야 합니다.)

---

5. 정렬, 필터링, 페이징은 Query Parameter로

자원의 본질을 바꾸지 않고, 보여주는 방식을 제어할 때는 URI 경로가 아닌 **쿼리 스트링(**`?`**)**을 사용합니다.

- ⭕ `GET /users?page=2&size=10` (페이징)
- ⭕ `GET /products?category=electronics&sort=price-desc` (필터 및 정렬)


# FastAPI 프로젝트 기본 구조
- 로깅 설정 → 앱 인스턴스 (서버 진입점) → 라우트 (엔드포인트 등록)
```python
import logging # 기록 모듈 (이제 더이상 pring() 쓰지 않음)
from fastapi import FastAPI

# 특정 파일을 지정할 수도 있고, 변수로 그룹지어 볼 수도 있음
# 로그 레벨별 메서드: .debug, .info, .warning, .error, .critical, ...
# 출력 기본값은 warning 이상이기 때문에 info 이하 출력을 위해서는 basicConfig 설정 필요
logging.basicConfig(
    level = logging.INFO, # info 레벨 이상의 로그 출력
    format = '%(asctime)s [%(levelname)s] (%(name)s) - %(message)s',
    datefmt = '%Y-%m-%d %H:%M:%S'
)
logger = logging.getLogger('app')

# 서버 실행 (인스턴스 초기화)
# @app: HTTP 요청 메서드가 정의되어 있는 데코레이터. 앞서 선언했기 때문에 사용 가능
app = FastAPI()

# 특별한 이유 없으면 비동기, 딕셔너리(JSON) 형태 사용
@app.get('/')
async def hello_world() -> dict:
    logger.info('로깅 연습, hello world')
    return {
        'message':'Hello World'
    }
```
`@app.get('/books')`는 **`app` 변수에 담긴 FastAPI 객체의 `get()` 메서드를 호출하는 것**입니다. 이 메서드가 "GET /books 요청이 오면 아래 함수를 실행해라"라고 객체 안에 등록해 줍니다. `@`는 파이썬의 **데코레이터** 문법으로, 아래 함수를 받아서 등록 처리를 해주는 역할입니다.

백엔드 프로젝트 폴더 구조(예시)
- `main.py`: 앱 생성과 라우터 등록만 담당
- `routers/`: 엔드포인트를 기능별로 분리 (`APIRouter`)
- `schemas/`: Pydantic 요청/응답 모델
- `services/` 또는 `crud/`: 비즈니스 로직과 DB 처리
- `core/config.py`: 설정과 로깅 설정

# 엔드포인트
- 클라이언트가 서버에 요청을 보낼 수 있는 **URL 경로 + HTTP 메서드 조합**
- 데코레이터 + 함수 한 세트가 엔드포인트 하나 
- API를 만든다 = 엔드포인트를 하나씩 추가해 나가는 일 → `/docs`에 엔드포인트 목록이 자동 정리되어 확인 가능
```python 
@app.get('/')
async def hello_world() -> dict:
    ...
```
- **메서드**: `GET`
- **경로**: `/`
- **동작**: 요청이 오면 `hello_world()`가 실행되고 `{'message': 'Hello World'}`를 JSON으로 응답합니다.
## 구성요소

|요소|의미|예시|
|---|---|---|
|HTTP 메서드|어떤 행동인지|GET(조회), POST(생성), PUT/PATCH(수정), DELETE(삭제)|
|경로(path)|어떤 자원인지|`/`, `/users`, `/users/1`|
|핸들러 함수|요청을 처리하는 코드|`hello_world()`|

같은 경로라도 메서드가 다르면 다른 엔드포인트입니다.

```python
@app.get('/users')      # 사용자 목록 조회
@app.post('/users')     # 사용자 생성
@app.get('/users/{id}') # 특정 사용자 조회
@app.delete('/users/{id}') # 특정 사용자 삭제
```

  %(asctime)s    기록한 시간             예: 2026-11-03 14:05:11,123
  %(levelname)s  레벨(INFO, ERROR ...)  예: ERROR
  %(name)s       로거 이름               예: app.handlers
  %(filename)s   기록을 남긴 파일 이름    예: handlers.py
  %(lineno)d     기록을 남긴 줄 번호      예: 118
  %(message)s    우리가 적은 내용
