## 앱 라우터(`app/`)의 역할

`app/` 안의 폴더와 파일 이름이 그대로 **URL 경로**가 돼요.

- `app/page.tsx` → `/`
- `app/todo/page.tsx` → `/todo`
- `layout.tsx`, `loading.tsx` 같은 특수 파일도 Next.js가 정해둔 이름이에요.

즉 `app/`은 "어떤 URL에 어떤 화면을 보여줄까"를 담당하는 **라우팅 전용 공간**이에요.

## `domains/`의 역할

`domains/`는 **업무(도메인) 단위로 코드를 묶어두는 공간**이에요. 지금 구조는 이래요.

```
app/                      ← 라우팅 (URL ↔ 페이지 연결만)
domains/
  todo/
    components/Todoitem.tsx   ← 할 일(todo) 관련 UI
    (hooks/, api/, types/ ... 나중에 추가 가능)
```

"todo"라는 기능에 필요한 컴포넌트, 훅, API 호출, 타입을 한 폴더에 모아요. 폴더 이름이 URL이 되지 않아서 `domains/todo`가 `/todo` 경로를 만들지는 않아요.

## 왜 나누나요?

1. **관심사 분리**: `app/`의 `page.tsx`는 얇게 두고, `domains/`의 컴포넌트를 가져다 조립만 해요.
    
    ```tsx
    // app/todo/page.tsx
    import TodoItem from "@/domains/todo/components/Todoitem";
    export default function Page() { return <TodoItem /> }
    ```
    
2. **재사용**: 같은 todo 컴포넌트를 여러 페이지에서 import해서 쓸 수 있어요.
3. **확장성**: 기능이 늘어나면 `domains/user`, `domains/order`처럼 폴더만 추가하면 돼요. 한 기능의 코드가 `app/` 곳곳에 흩어지지 않아요.
4. **라우트 변경에 안전**: URL 구조를 바꿔도 도메인 코드는 건드릴 필요가 없어요.

## 한 줄 요약

- `app/` = **어디에** 보여줄지 (라우팅)
- `domains/` = **무엇을** 보여줄지 (기능별 로직·UI)

참고로 `app/` 안에 `_components` 같은 폴더를 두는 방식도 있어요(언더스코어로 시작하면 라우트에서 제외돼요). 하지만 `domains/`처럼 `app/` 밖으로 빼면 라우팅과 완전히 분리돼서 더 명확해요.


# 가상 DOM과 상태값, 막무가내 버전

## 1. 먼저 DOM이 뭔지

브라우저가 화면을 그릴 때 쓰는 **진짜 설계도**예요. `<input>`, `<button>` 같은 태그가 나무 모양으로 연결돼 있어요. 이 진짜 DOM을 건드리면 화면이 바로 바뀌는데, 건드리는 작업이 **느리고 비싸요**.

## 2. 가상 DOM은 "연습용 복사본 설계도"

React는 진짜 DOM을 바로 건드리지 않고, **메모리에 가짜 설계도(가상 DOM)를 따로 만들어요.** 일의 순서는 이래요.

1. 뭔가 바뀌면 새 가짜 설계도를 **처음부터 다시 그려요.** 메모리 안에서 그리니까 빨라요.
2. 이전 가짜 설계도와 새 가짜 설계도를 **비교해요.** 이 비교를 diff라고 해요.
3. **달라진 부분만** 진짜 DOM에 반영해요.

건물 리모델링에 비유하면 이래요. 집을 허물고 새로 짓는 게 아니라, 도면 두 장을 겹쳐 놓고 "여기 벽지만 바뀌었네" 하고 그 벽지만 갈아요.

## 3. 상태값(state)은 "화면이 기억하는 값"

이 페이지의 이 줄이 상태값이에요.

```tsx
const [form, setForm] = useState<Todo>({});
```

- `form`: 지금 기억하고 있는 값이에요. 읽기 전용이라 직접 고치면 안 돼요.
- `setForm`: 값을 바꾸는 **유일한 공식 창구**예요.
- `useState({})`: 처음엔 빈 객체로 시작한다는 뜻이에요.

일반 변수(`let title = ''`)로 하면 안 되는 이유가 있어요. 변수는 값이 바뀌어도 React가 모르니까 화면이 안 바뀌어요. `setForm`을 부르면 React가 **"아, 바뀌었네. 다시 그려야겠다"** 하고 알게 돼요. 이게 핵심이에요.

## 4. 이 페이지에서 글자를 한 글자 칠 때 일어나는 일

사용자가 input에 `a`를 쳤다고 해볼게요.

|단계|무슨 일이 생기나|
|---|---|
|① 입력|키보드로 `a`를 침|
|② 이벤트|`onChange`가 호출됨. `e.target.value`는 `"a"`|
|③ 상태 변경 요청|`setForm({ ...form, title: "a" })` 실행|
|④ 다시 그리기|React가 `TodoPage` 함수를 **처음부터 다시 실행**해요. 이때 `form`은 `{title: "a"}`예요.|
|⑤ 가상 DOM 비교|이전: `value=""`, 새것: `value="a"`. 달라진 건 이것뿐이에요.|
|⑥ 진짜 DOM 반영|input의 value 하나만 바꿈|

`{ ...form, title: ... }`는 기존 객체를 **복사하고 title만 덮어쓴** 새 객체예요. 기존 객체를 직접 수정하지 않고 새 객체를 만들어서 넘겨야 React가 "값이 바뀌었구나" 하고 알아채요. 같은 객체를 수정만 하면 React는 변화를 못 느껴요.

## 5. 한 줄로 정리

> **상태값이 바뀌면 → 함수를 다시 실행해서 새 가상 DOM을 만들고 → 이전 것과 비교해서 → 달라진 곳만 진짜 화면에 반영한다.**

개발자는 "어떻게 바꿀까"를 고민하지 않고 "상태가 이러면 화면은 이렇게 생겼다"만 적으면 돼요. 나머지는 React가 해요.

## 1. React 타입은 쓰는 방법이 2가지

```tsx
// 방법 A: import해서 이름만 쓰기 (지금 코드)
import { SubmitEvent } from 'react';
const onSubmit = (e: SubmitEvent<HTMLFormElement>) => {};

// 방법 B: import 없이 React. 붙여서 쓰기
const onSubmit = (e: React.SubmitEvent<HTMLFormElement>) => {};
```

`React.`는 "React 라이브러리 안에 있는 그 타입"이라고 출처를 밝히는 거예요. 둘의 결과는 같아요. `React.JSX.Element`도 같은 원리예요.

- **`React.` 안 붙임**: import 한 줄이 필요하고, 코드는 짧아져요.
- **`React.` 붙임**: import가 없어도 되고, 출처가 바로 보여요.

## 2. 함정: `SubmitEvent`는 브라우저에도 있어요

브라우저(DOM)에는 원래 `SubmitEvent`라는 **네이티브 타입이 따로 있어요.** 그래서 이름만 쓰면 이렇게 갈려요.

|쓰는 방식|가리키는 타입|
|---|---|
|`import { SubmitEvent } from 'react'` 후 `SubmitEvent`|**React의** SubmitEvent (`onSubmit={...}`에 맞는 것)|
|import 안 하고 그냥 `SubmitEvent`|**브라우저 기본** SubmitEvent (React 이벤트와 다름)|
|`React.SubmitEvent`|항상 **React의** SubmitEvent|

React 컴포넌트의 `onSubmit`에는 React가 감싼 이벤트(SyntheticEvent)가 들어와요. 그래서 import를 빼먹고 그냥 `SubmitEvent`만 쓰면 브라우저 타입이 잡혀서 타입 에러가 나거나 엉뚱하게 동작해요. 에디터가 자동으로 import를 넣어주지 않으면 헷갈리기 쉬워요.

`??`는 **"왼쪽 값이 없으면(`null` 또는 `undefined`) 오른쪽 값을 대신 써라"**는 연산자예요. 이름은 Nullish Coalescing(널 병합)이에요.

```tsx
form.title ?? ''
```

- `form.title`에 값이 있으면 → 그 값을 그대로 써요.
- `form.title`이 `undefined`거나 `null`이면 → 빈 문자열 `''`을 써요.

## 왜 필요하냐

`form`의 초기값이 `{}`라서 처음에는 `form.title`이 **아예 없어요(`undefined`)**.

|시점|`form.title`|`value`에 들어가는 값|
|---|---|---|
|`?? ''` 없이, 처음|`undefined`|`undefined`|
|`?? ''` 있고, 처음|`undefined`|`''`|
|글자를 친 뒤|`"abc"`|`"abc"`|

`<input value={undefined}>`이면 React가 "값을 내가 관리 안 하는 입력창"으로 취급해요. 그러다 글자를 치면 `value`가 `"a"`로 바뀌어서 "관리 안 하던 입력창이 관리하는 입력창으로 바뀌었다"는 경고가 떠요. 처음부터 `''`로 시작하면 항상 React가 관리하는 입력창이라 경고가 안 나요.

## `||`와는 뭐가 달라요?

비슷해 보이지만 기준이 달라요.

```tsx
0  || 10   // 10   (0도 "없는 값"으로 취급)
0  ?? 10   // 0    (null/undefined만 "없는 값"으로 취급)

'' || 'x'  // 'x'
'' ?? 'x'  // ''
```

- `||`: 0, `''`, `false`도 전부 없는 걸로 봐요.
- `??`: **`null`과 `undefined`만** 없는 걸로 봐요.

입력창에서는 둘 다 결과가 같지만, 숫자 0이나 false가 의미 있는 값일 때 `||`를 쓰면 버그가 생겨요. 그래서 "값이 아예 없을 때만 기본값"을 원하면 `??`가 더 안전해요.

## 방법 B: 초기값을 처음부터 채워두기

`{}` 대신 `title`이 있는 객체로 시작하는 방식이에요.

```tsx
const [form, setForm] = useState<Todo>({ title: '' });
...
<input value={form.title} />   // ?? '' 필요 없음
```

처음부터 `title`이 `''`이라서 `undefined`가 될 일이 없어요. 등록 후 비울 때도 `setForm({})`이 아니라 `setForm({ title: '' })`로 해야 해요.

초기값이 두 군데(`useState`, 등록 후 리셋)에 중복되는 게 싫으면 상수로 빼요.

```tsx
const INITIAL_FORM: Todo = { title: '', checked: false };

const [form, setForm] = useState<Todo>(INITIAL_FORM);
...
setForm(INITIAL_FORM);   // 리셋
```

## 비교

||A: `?? ''`|B: 초기값 채우기|
|---|---|---|
|코드 위치|input마다 붙여야 함|`useState` 한 곳|
|입력창이 늘어나면|모든 input에 `?? ''` 반복|초기값에 필드만 추가|
|`form` 안의 실제 값|`undefined`가 섞여 있음|항상 값이 있음|
|리셋(`setForm({})`)|그대로 가능|초기값으로 다시 세팅해야 함|
|타입 안전성|약함 (값이 있는지 불확실)|강함|

## 뭐가 더 나은가: **B를 추천해요**

이유는 이래요.

1. **문제를 원인에서 해결해요.** A는 `undefined`가 생기는 걸 그대로 두고 화면에서 가리는 방식이고, B는 `undefined`가 아예 안 생기게 해요.
2. **나중에 서버로 보낼 때 안전해요.** 등록 시 `form`을 그대로 보내면, A는 `title`이 없는 객체가 나갈 수 있어요. B는 항상 `title`이 `''`이라도 존재해요.
3. **input이 여러 개가 되면 차이가 커져요.** 제목, 내용, 마감일이 생기면 A는 `?? ''`를 전부 붙여야 해요.

다만 B에는 한 가지 문제가 있어요. 지금 `Todo`의 필드가 전부 `?`(선택)라서 `{}`도 타입상 통과해요. 이 상태에서는 타입이 "초기값 빼먹지 마"라고 강제해주지 못해요. 규모가 커지면 폼용 타입을 따로 만드는 게 더 깔끔해요.

```tsx
interface TodoForm {
    title: string;   // 필수 → 초기값 안 채우면 TS가 바로 에러
}
const [form, setForm] = useState<TodoForm>({ title: '' });
```


`useCallback`은 **"함수를 매번 새로 만들지 말고 기억해뒀다가 재사용해라"**는 도구예요. 일반적인 방법이라고 들으셨다면 맞긴 한데, **지금 코드에서는 이득이 없고 버그가 숨어 있어요.**

## 왜 하는 건가 (원래 목적)

아까 설명한 대로 상태가 바뀌면 `TodoPage` 함수가 **처음부터 다시 실행**돼요. 그러면 안에 있는 `onChange`도 **매번 새 함수**로 만들어져요. 내용은 똑같아도 메모리상으로는 다른 함수예요.

```tsx
// 렌더 1번째: onChange = 함수①
// 렌더 2번째: onChange = 함수②  (내용은 같지만 다른 객체)
```

이게 문제가 되는 경우는 하나예요. 이 함수를 **자식 컴포넌트에 props로 내려주고, 그 자식이 `React.memo`로 감싸져 있을 때**예요. `memo`는 "props가 안 바뀌면 다시 안 그린다"인데, 함수가 매번 새것이면 "props가 바뀌었네" 하고 불필요하게 다시 그려요. `useCallback`으로 같은 함수를 유지하면 이걸 막아줘요.


# onChange 3종류 정리

## ① 일반 함수 (기존 코드)

```tsx
const onChange = (e: ChangeEvent<HTMLInputElement>) => {
    setForm({ ...form, title: e.target.value });
};
```

- **특징**: 렌더링될 때마다 함수가 새로 만들어지고, 그때마다 최신 `form`을 읽어요.
- **개념**: 클로저(함수가 만들어질 때의 `form`을 기억함). 매번 새로 만들어지니 항상 최신 값이에요.
- **장단점**: 가장 단순하고 틀릴 일이 없어요. 함수를 새로 만드는 비용은 무시해도 될 정도예요.

## ② `useCallback` + `[form]`

```tsx
const onChange = useCallback(
    (e: ChangeEvent<HTMLInputElement>) => {
        setForm({ ...form, title: e.target.value });
    },
    [form],
);
```

- **특징**: `form`이 바뀔 때만 함수를 새로 만들어요.
- **개념**: 메모이제이션(함수 기억해두기) + 의존성 배열(`form`이 바뀌었는지 확인하는 기준).
- **장단점**: 동작은 정확해요. 하지만 글자를 한 자 칠 때마다 `form`이 바뀌니까 **매번 새로 만드는 거나 마찬가지**예요. `useCallback`을 쓴 의미가 없어서 ①보다 복잡하기만 해요.

## ③ `useCallback` + `[]` + 함수형 업데이트 (현재 코드)

```tsx
const onChange = useCallback((e: ChangeEvent<HTMLInputElement>) => {
    setForm((prev) => ({ ...prev, title: e.target.value }));
}, []);
```

- **특징**: 함수를 **딱 한 번만** 만들고 계속 재사용해요.
- **개념**: 메모이제이션 + 함수형 업데이트(`prev`). `prev`는 React가 "지금 최신 상태"를 넣어주기 때문에, 함수가 `form`을 직접 기억할 필요가 없어요. 그래서 `[]`로 고정해도 낡은 값 문제가 안 생겨요.
- **장단점**: 함수가 진짜로 안 바뀌어서 `useCallback` 본래 목적(`memo`된 자식의 불필요한 리렌더링 방지)을 제대로 달성하는 유일한 버전이에요. 대신 개념이 더 필요해요.

## 한눈에 비교

||① 일반|② `[form]`|③ `[]` + `prev`|
|---|---|---|---|
|함수 재생성|매 렌더링|입력할 때마다|**안 함**|
|최신 `form` 보장|✅|✅|✅ (`prev` 덕분)|
|`useCallback` 효과|-|❌ 거의 없음|✅|
|코드 복잡도|낮음|중간|중간|


**`onChange` 전체는 순수함수가 아니에요.** 다만 그 안의 `(prev) => ...` 부분은 순수함수예요.

## 순수함수의 조건

1. **같은 입력이면 항상 같은 결과**를 돌려줘요.
2. **바깥 세상에 영향을 주지 않아요.** 이걸 부수효과(side effect)라고 해요.

## 3번을 쪼개서 보면

```tsx
const onChange = useCallback((e) => {
    setForm((prev) => ({ ...prev, title: e.target.value }));
}, []);
```

|부분|순수함수?|이유|
|---|---|---|
|바깥 `onChange`|❌|`setForm(...)`을 호출해서 **상태를 바꾸는 부수효과**가 있어요. 이벤트 핸들러는 원래 그런 일을 하려고 만든 거예요.|
|안쪽 `(prev) => ({ ...prev, title })`|✅|`prev`를 **수정하지 않고** 복사해서 새 객체를 만들어 돌려줘요. 같은 `prev`와 `title`이면 항상 같은 결과예요.|

## 안쪽이 순수해야 하는 이유

`setForm`에 넘기는 함수는 React가 **여러 번 호출할 수도 있어요**(개발 모드의 Strict Mode에서는 일부러 두 번 실행해요). 그래서 순수해야 해요. 반대로 쓰면 이렇게 돼요.

```tsx
// ❌ 순수하지 않음: prev를 직접 수정
setForm((prev) => { prev.title = e.target.value; return prev; });
```

- 같은 객체를 수정만 하고 돌려주니까 React가 "바뀌었다"고 못 알아채요.
- 두 번 실행되면 결과가 꼬일 수 있어요.

```tsx
// ✅ 순수함: 복사 후 새 객체 반환
setForm((prev) => ({ ...prev, title: e.target.value }));
```

## 한 줄 정리

- **이벤트 핸들러(`onChange`)**: 상태를 바꾸는 게 일이라서 순수하지 않아도 돼요.
- **상태 업데이트 함수(`prev => ...`)**: 반드시 순수해야 해요. 3번의 이 부분은 조건을 만족해요.

# onChange·onSubmit 시행착오 스토리

## 1막. 가장 단순하게 시작 (일반함수 ver)

```tsx
const onChange = (e) => {
    setForm({ ...form, title: e.target.value });
};
```

- **상황**: 입력창에 글자를 치면 `form`을 바꾸는 가장 기본형이에요.
- **결과**: 잘 돌아가요.
- **궁금증**: "렌더링마다 함수가 새로 만들어진다던데, 이거 낭비 아닌가? 다들 `useCallback`을 쓴다던데?"

## 2막. 최적화해보려고 `useCallback`을 감쌈 (콜백함수 ver)

```tsx
const onChange = useCallback((e) => {
    setForm({ ...form, title: e.target.value });
}, []);
```

- **시도**: 함수를 한 번만 만들고 재사용하려고 `[]`를 넣었어요.
- **문제 발견**: ESLint가 "`form`이 의존성에 빠졌다"고 경고해요. `[]`로 두면 함수가 **처음 `form`만 기억하는 낡은 값 문제(stale closure)**가 생겨요.
- **1차 수정**: 경고대로 `[form]`을 넣었어요.
    
    ```tsx
    }, [form]);   // form이 바뀔 때만 함수 재생성
    ```
    
- **새 깨달음**: 글자를 칠 때마다 `form`이 바뀌니까 **결국 매번 새로 만드는 것과 같아요.** 복잡해지기만 하고 최적화 효과가 없어요.

## 3막. 해결책 발견 (순수함수 ver, 현재)

```tsx
const onChange = useCallback((e) => {
    setForm((prev) => ({ ...prev, title: e.target.value }));
}, []);
```

- **아이디어**: `form`을 직접 읽지 말고, React가 주는 **"최신 상태(`prev`)"**를 받아 쓰자.
- **효과**: 함수가 `form`을 기억할 필요가 없으니 `[]`로 고정해도 낡은 값 문제가 없어요. `useCallback`이 진짜로 동작하는 유일한 형태예요.
- **라벨 정정**: 주석의 "순수함수ver"는 정확히는 `prev => ...` 부분이 순수함수라는 뜻이에요. `onChange` 전체는 상태를 바꾸니까 순수함수는 아니에요. "함수형 업데이트 ver"로 바꾸면 더 정확해요.

## 4막. 같은 고민이 `onSubmit`에도 반복됨

```tsx
const onSubmit = useCallback((e) => {
    e.preventDefault();
    setItems((prev) => prev.concat([{ ...form, id: Date.now() }]));
    setForm({ ...initialValue });
}, [form]);
```

- `items`는 `prev`로 바꿔서 `items` 의존을 없앴어요. (3막에서 배운 방식 적용)
- 그런데 **`form`은 새 항목의 내용을 직접 읽어야 해서** `prev`로 해결이 안 돼요. 그래서 `[form]`이 남았어요.
- **다시 2막의 결론**: `form`이 입력할 때마다 바뀌니 `onSubmit`도 입력할 때마다 새로 만들어져요. 이 `useCallback`은 사실상 효과가 없어요.

## 흐름 요약

|단계|코드|배운 점|
|---|---|---|
|1막|일반 함수|기본형. 문제없이 동작|
|2막|`useCallback` + `[]` → `[form]`|의존성 배열의 의미, 낡은 값 문제, `[form]`은 효과가 없음|
|3막|`useCallback` + `[]` + `prev`|함수형 업데이트로 의존성 제거|
|4막|`onSubmit`에 적용|`form`을 읽어야 하면 `prev`로 못 풀어서 한계가 있음|

## 최종 정리

- **`onChange`**: 3막(`prev` 방식)이 가장 안전해요. `useCallback`은 있어도 없어도 괜찮아요.
- **`onSubmit`**: 4막의 `useCallback`은 효과가 없으니 일반 함수(주석 처리된 원본)로 둬도 돼요.
- **전체 결론**: 이 페이지는 `memo`된 자식에 함수를 내려주지 않으니 `useCallback`은 **필수가 아니에요.** 연습 삼아 써본 건 좋고, 실무에서는 "필요가 생겼을 때 추가한다"가 기본이에요.

이 시행착오 자체가 학습 포인트라서, 주석에 "1막~4막" 흐름을 한두 줄 요약으로 남겨두면 나중에 복습할 때 도움이 될 거예요.

**함수 안에서 `form`을 읽으면 → 의존성에 `[form]`이 필요하고, `form`을 안 읽고 `prev`만 쓰면 → `[]`로 고정할 수 있다.**

## 짝궁 조합

### 짝 1. 일반 + 일반 (기본형)

```tsx
const onChange = (e) => setForm({ ...form, title: e.target.value });

const onSubmit = (e) => {
    e.preventDefault();
    setItems(items.concat([{ ...form, id: Date.now() }]));
    setForm({ ...initialValue });
};
```

- `useCallback` 없이 매 렌더링마다 새로 만들고, 항상 최신 `form`과 `items`를 읽어요.
- **추천**: 지금 페이지에서는 이게 가장 단순하고 충분해요.

### 짝 2. `useCallback [form]` + `useCallback [form, items]`

```tsx
const onChange = useCallback((e) => {
    setForm({ ...form, title: e.target.value });
}, [form]);

const onSubmit = useCallback((e) => {
    e.preventDefault();
    setItems(items.concat([{ ...form, id: Date.now() }]));
    setForm({ ...initialValue });
}, [form, items]);
```

- 둘 다 `form`(과 `items`)을 읽으니 배열에 다 넣어야 해요.
- 입력할 때마다 둘 다 재생성돼서 **`useCallback` 효과가 없어요.** (2막의 결론)

### 짝 3. 현재 코드: `onChange`는 `[]` + `prev`, `onSubmit`은 `[form]`

```tsx
const onChange = useCallback((e) => {
    setForm((prev) => ({ ...prev, title: e.target.value }));
}, []);

const onSubmit = useCallback((e) => {
    e.preventDefault();
    setItems((prev) => prev.concat([{ ...form, id: Date.now() }]));
    setForm({ ...initialValue });
}, [form]);
```

- `onChange`는 고정, `onSubmit`만 `form`이 바뀔 때 재생성돼요.
- **어중간한 짝**이에요. `onChange`만 최적화되고 `onSubmit`은 안 돼요.

### 짝 4. 둘 다 `[]`로 고정 (`useReducer`)

`form`을 읽는 문제를 없애려면 **상태 변경 로직을 `reducer` 안으로 옮겨요.**

```tsx
const [state, dispatch] = useReducer(reducer, { form: initialValue, items: [] });

const onChange = useCallback((e) => {
    dispatch({ type: 'change', title: e.target.value });
}, []);

const onSubmit = useCallback((e) => {
    e.preventDefault();
    dispatch({ type: 'submit' });
}, []);
```

- `dispatch`는 React가 **항상 같은 함수를 보장**해줘서 `[]`로 안전해요.
- 두 함수 다 진짜로 안 바뀌어요. 대신 `reducer`를 따로 작성해야 해서 코드가 길어져요.

## 한눈에 비교

|짝|`onChange`|`onSubmit`|함수 안 바뀜?|난이도|
|---|---|---|---|---|
|1|일반|일반|❌ (필요 없음)|쉬움|
|2|`[form]`|`[form, items]`|❌ 거의 매번 바뀜|중간|
|3 (현재)|`[]` + `prev`|`[form]`|`onChange`만 ✅|중간|
|4|`[]` + `dispatch`|`[]` + `dispatch`|✅ 둘 다|어려움|


`onClick`은 **"이 요소가 클릭되면 이 함수를 불러달라"고 등록해두는 것**이에요. 이걸 이벤트 리스너(event listener)라고 해요.

## 1. 등록하는 단계 (화면을 그릴 때)

```tsx
<button onClick={() => onRemove(id)}>
```

React는 이 줄을 보고 이렇게 **기억만 해둬요.**

> "이 `<button>`이 클릭되면 `() => onRemove(2)`를 실행한다"

함수를 **실행하는 게 아니라 보관**하는 거예요. 앞에서 말한 "쪽지를 건넨다"가 이 단계예요.

## 2. 실행되는 단계 (사용자가 클릭할 때)

```
① 사용자가 버튼을 클릭
② 브라우저가 "click 이벤트"를 만들어요
③ React가 어느 요소가 클릭됐는지 찾아요
④ 그 요소에 등록된 함수를 꺼내 호출해요  → () => onRemove(2) 실행
⑤ 그 안에서 onRemove(2)가 실행돼요
```

## 3. 브라우저가 클릭을 처리하는 방식

순수 자바스크립트로 쓰면 이래요.

```js
button.addEventListener('click', () => onRemove(2));
```

`onClick`은 이걸 React가 편하게 써주는 방식이에요. 비교하면 이래요.

||순수 JS|React|
|---|---|---|
|등록|`addEventListener('click', 함수)`|`onClick={함수}`|
|해제|`removeEventListener` 직접 호출|요소가 사라지면 React가 알아서 정리|

## 4. React가 하는 일: 이벤트 위임

React는 모든 버튼에 리스너를 따로 달지 않아요. **맨 위(루트) 한 곳에만 리스너를 달아두고** 클릭이 올라오면 어느 요소인지 보고 처리해요.

```
클릭한 버튼 → 위로 전파(버블링) → 루트에서 React가 받음 → 해당 요소의 onClick 함수 실행
```

- 항목이 1000개여도 리스너는 한 곳이라 가벼워요.
- 클릭이 안쪽에서 바깥으로 전파되는 걸 **버블링(bubbling)**이라고 해요.

## 5. 함수에 넣어주는 인자: 이벤트 객체

클릭을 처리할 때 React는 `e`(이벤트 객체)를 만들어서 함수에 넘겨줘요.

```tsx
onClick={(e) => { console.log(e.target) }}   // e: 클릭 정보
```

- `e.target`: 클릭된 요소
- `e.preventDefault()`: 기본 동작 막기 (폼 제출 때 썼던 것)
- `e.stopPropagation()`: 위로 전파 막기

우리 코드 `() => onRemove(id)`는 `e`를 안 받으니 무시되고, 이미 알고 있는 `id`만 써요.

`<Link>`와 `<a>`는 **페이지를 이동하는 방식**이 달라요. `<a>`는 브라우저가 전체 페이지를 새로 받아오고, `<Link>`는 Next.js가 **필요한 부분만 바꿔치기**해요.

## `<a href="/login">` → MPA 방식 (전체 새로고침)

1. 클릭하면 브라우저가 서버에 `/login` 페이지를 **통째로 새로 요청**해요.
2. 현재 화면이 사라지고, 흰 화면이 잠깐 보였다가 새 페이지가 떠요.
3. **React가 처음부터 다시 시작**해서 `useState`로 관리하던 상태가 전부 날아가요.

MPA(Multi Page Application)는 페이지마다 서버에서 HTML을 새로 받는 전통적인 방식이에요.

## `<Link href="/login">` → SPA 방식 (부분 교체)

1. 클릭을 가로채서(브라우저의 기본 이동을 막고) **새로고침 없이** 이동해요.
2. 공통 부분(`layout`)은 그대로 두고, **바뀌는 페이지 부분만** 교체해요.
3. 주소창 URL은 바뀌지만 페이지가 깜빡이지 않고, 공유되는 상태나 스크롤도 유지될 수 있어요.

SPA(Single Page Application)는 페이지를 한 번만 불러와두고 내용만 갈아 끼우는 방식이에요.

## 비교

||`<a>` (MPA)|`<Link>` (SPA)|
|---|---|---|
|이동 방식|전체 페이지 새로 요청|필요한 부분만 교체|
|화면 깜빡임|있음|거의 없음|
|속도|느림|빠름|
|React 상태(`useState`)|**초기화됨**|유지될 수 있음|
|미리 불러오기(prefetch)|없음|**있음** (화면에 보이면 미리 받아둠)|
|import|필요 없음|`import Link from 'next/link'`|

`<Link>`의 동작이 AJAX와 같은 계열

||이동/요청 방식|서버에서 받는 것|화면 처리|
|---|---|---|---|
|`<a>` (MPA)|브라우저가 직접 이동|**HTML 문서 전체**|현재 화면을 버리고 통째로 교체|
|`<Link>` (SPA)|**자바스크립트가 요청 (AJAX 방식)**|**필요한 데이터 조각**|바뀐 부분만 교체|

`<Link>`를 클릭하면 이런 일이 벌어져요.

1. 브라우저의 기본 이동을 막아요 (`preventDefault`).
2. 자바스크립트가 서버에 `fetch`로 새 페이지의 데이터를 요청해요. (AJAX)
3. 받은 데이터로 **가상 DOM을 비교해서** 달라진 부분만 교체해요.
4. `history.pushState`로 **주소창 URL만** `/login`으로 바꿔줘요.

즉 새로고침 없이 이동하는 것처럼 보이지만, 뒤에서는 AJAX와 같은 원리로 데이터를 받아오고 있어요.

**RSC = React Server Components(리액트 서버 컴포넌트)**예요. 컴포넌트를 **브라우저가 아니라 서버에서 실행**하는 방식이에요. 앞에서 `<Link>`가 받아오는 게 "RSC payload"라고 한 그 RSC예요.

## 핵심 아이디어

```
기존 React (클라이언트 컴포넌트):  코드 전체를 브라우저로 보냄 → 브라우저에서 실행
RSC (서버 컴포넌트):               서버에서 실행 → 결과만 브라우저로 보냄
```

## 이 프로젝트에서 이미 쓰고 있어요

Next.js 앱 라우터(`app/`)는 **기본이 서버 컴포넌트**예요. 파일 맨 위에 아무것도 안 쓰면 서버 컴포넌트고, `'use client'`를 쓰면 클라이언트 컴포넌트가 돼요.

|파일|종류|근거|
|---|---|---|
|`app/board/[id]/page.tsx`|**서버 컴포넌트**|`'use client'` 없음, `async`/`await` 사용|
|`app/todo/page.tsx`|**클라이언트 컴포넌트**|`'use client'` 있음, `useState` 사용|

그래서 `board` 페이지의 `console.log`는 **서버 터미널**에 찍히고, `todo` 페이지의 로그는 **브라우저 콘솔**에 찍혀요.

## 둘의 차이

||서버 컴포넌트 (기본)|클라이언트 컴포넌트 (`'use client'`)|
|---|---|---|
|실행 위치|서버|브라우저 (첫 화면은 서버에서도 한 번 렌더링됨)|
|`async/await`|✅ 컴포넌트에서 바로 가능|❌ (`use()`로 대체)|
|DB·파일·비밀키 접근|✅ 가능 (브라우저로 안 나감)|❌ 노출 위험|
|`useState`, `useEffect`|❌|✅|
|`onClick` 등 이벤트|❌|✅|
|브라우저로 가는 JS 양|**0** (결과만 감)|코드가 다 감|

## 왜 쓰나

1. **JS가 가벼워져요.** 서버에서만 실행되는 코드는 브라우저로 안 가서 페이지가 빨리 떠요.
2. **데이터 가져오기가 단순해져요.** 서버에서 DB를 바로 읽을 수 있어서 `fetch` + `useState` + `useEffect` 조합이 필요 없어요.
    
    ```tsx
    export default async function Page() {
        const posts = await db.query('select * from posts');   // 서버에서 직접
        return <ul>{posts.map(...)}</ul>;
    }
    ```
    
3. **보안**: API 키나 DB 접속 정보가 코드에 있어도 브라우저로 안 나가요.

## 흔한 오해

- "서버 컴포넌트 = SSR"이 아니에요. SSR은 **첫 HTML을 서버에서 만드는 것**이고, RSC는 **컴포넌트 자체가 서버에서만 실행되는 것**이에요. 클라이언트 컴포넌트도 첫 화면은 서버에서 렌더링돼서 둘이 헷갈려요.
- 서버 컴포넌트가 **HTML**을 보내는 게 아니라, 렌더 결과를 담은 **RSC payload**라는 특수 형식을 보내요. React가 이걸 받아 화면에 합쳐요. `<Link>` 이동 때 받는 것도 이 payload예요.

## 섞어 쓰는 방법

서버 컴포넌트 안에 클라이언트 컴포넌트를 넣을 수 있어요.

```tsx
// 서버 컴포넌트 (기본)
export default async function Page() {
    const items = await fetchTodos();           // 서버에서 데이터 조회
    return <TodoList initialItems={items} />;   // 클라이언트 컴포넌트에 전달
}
```

```tsx
// TodoList.tsx
'use client';   // 상태·클릭이 필요한 부분만 클라이언트로
```

**원칙**: 기본은 서버 컴포넌트로 두고, `useState`나 `onClick`이 필요한 **작은 부분만** `'use client'`로 빼요.

## 한 줄 요약

> **RSC는 "서버에서만 실행되고 결과만 보내는 컴포넌트"이고, Next.js 앱 라우터의 기본값이에요. 상태나 클릭 이벤트가 필요한 곳에만 `'use client'`를 붙여요.**
