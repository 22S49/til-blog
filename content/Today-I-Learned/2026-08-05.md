#### (복습) 브랜치
- 개념
	- 공간을 만드는 게 아니라 공간을 나누는 개념
	- 기능 명세에 따라 브랜치를 나누어 작업 (작업 단위로 쪼개도 좋음, 체계적 개발)
	- HEAD 이동으로 시점을 바꿔서 다루는 원리
	- main branch (master branch) ⇢ 프로젝트의 완성본
- 생성
	- - git branch "브랜치명"
- 이동
	- git checkout "브랜치명"
		- 브랜치 전환, 파일 체크아웃, 커밋으로 돌아가기 등 다양한 용도로 사용
	- git switch "브랜치명"
		- 오직 브랜치 전환에만 사용
- 생성+이동
	- git checkout -b "브랜치명"
	- git switch -c "브랜치명"
- 삭제
	- 삭제하려는 브랜치가 아닌 다른 브랜치로 이동
		- (일반) git branch -d "브랜치명"
		- (강제) git branch -D "브랜치명"
- 변경
	- 변경하고자 하는 브랜치로 이동
		- (일반) git branch -m "브랜치명"
		- (강제) git branch -M "브랜치명"
- 조회
	- git branch 
		- * 표기가 있는 브랜치는 현재 위치하고 있는 브랜치
- 병합
	- 몸체가 될 브랜치로 이동
		- git merge "병합할 브랜치명"
			- Fast-forward
				- 새로운 기록이 필요하지 않아서 HEAD 포인터만 이동
				- 충돌이 발생할 수 없음
			- 3way-merge
				- 새로운 커밋이 만들어지고 거기에 병합됨
				- 병합하고 새로운 기록을 해야 하기 때문에 commit 됨
				- 충돌이 발생하면 충돌 해결 후 새로운 커밋이 만들어지고 병합됨
- 재배치
	- 기록 이력을 깔끔하게 선형으로 정리하기 위함 (분기 ⇢ 선형 또는 3way ⇢ FF 변형과 유사)
	- 공유 프로젝트에서는 지양해야 함
	- 분기된 브랜치로 이동 
		- git rebase "몸체 브랜치"
			- git rebase main
	- 충돌 발생 
		- 충돌 해결이 완료된 경우
			- git add
			- git rebase --continue
		- 충돌 해결 안 하는 경우 
			- git rebase --skip
				- 충돌 건너뛰기
			- git rebase --abort
				- 리베이스 취소

#### git pull 관련 
- 원격 브랜치의 삭제 정보를 동기화 하지 않음 ⇢ 로컬에 브랜치 정보가 캐싱되어 있기 때문
	- Git은 의도적으로 이 방식을 선택
	- 네트워크 비용을 최소화하고 명시적으로 동기화(`fetch`, `pull`)할 때만 원격과 통신하는 철학 때문입니다. 그래서 `git fetch`를 주기적으로 해주는 게 습관적으로 중요한 이유
- 원격에서 삭제된 브랜치를 로컬에 반영하려면
	- git fetch —prune 또는 git fetch -p
- 자동으로 prune하려면
	- git config —global fetch.prune true
		- 이렇게 하면 git fetch, git pull 할 때마다 자동으로 삭제된 원격 브랜치를 정리

### 나머지 공부 — rebasd

- 상황 예시
```
develop
└── PR #1: setup-openapi-config
    └── PR #2: implement-token-auth   ← #1 기반
        └── PR #3: fetch-stock-price  ← #2 기반
```
```
- 리뷰어가 PR #1 코드 수정 요청 
	  → #1 브랜치에 커밋 추가  
		  → #2, #3 은 아직 수정 전 #1 기준이라 코드가 안 맞음
```

- rebase로 해결
```bash
# PR #1 의 최신 커밋 위로 PR #2 커밋들을 다시 쌓는 개념입니다.

# PR #2 브랜치에서
git rebase feature/trading/setup-openapi-config

# PR #3 브랜치에서
git rebase feature/trading/implement-token-auth
```

- rebase, merge 차이
	- PR 체인에서는 rebase 선호 — 히스토리가 지저분해지지 않기 때문에
```
# merge: 수정된 #1을 #2에 합치는 커밋이 하나 생김
# rebase: #2 커밋들이 수정된 #1 위에 깔끔하게 재배치됨
```

- rebase 후 push 주의
	- rebase하면 커밋 히스토리가 바뀌기 때문에 일반 push가 거부됩니다.
	- `--force-with-lease`로 강제 push 해야 하는데, `--force` 대신 아래 옵션을 쓰는 이유는 **다른 사람이 올린 커밋을 실수로 덮어쓰는 걸 방지**하기 위해서입니다.
```bash
git push origin feature/trading/implement-token-auth --force-with-lease
```


### 오늘의 퀘스트
#### 1번 문항
- **Q**. PR 머지 전략 중 'Squash and merge'의 특징으로 가장 적절한 것은?
- **A**. PR 전체 커밋을 하나로 압축하여 main에 커밋 1개로 반영한다
- *Squash and merge는 PR에 포함된 여러 커밋(특히 WIP 커밋 등)을 하나의 커밋으로 압축해 main에 반영하는 전략입니다. 첫 번째 선지는 Merge commit, 세 번째는 Rebase and merge에 해당하는 설명입니다. AI 프로젝트처럼 실험적 커밋이 많을 때 히스토리를 깔끔하게 유지하기 위해 자주 사용됩니다.*
#### 2번 문항
- **Q**. 작업이 미완성 상태일 때 변경 사항을 임시로 스택에 저장하고 워킹 트리를 마지막 커밋 상태로 되돌리는 Git 명령어는 무엇인가?
- **A**. stash
- *git stash는 현재 작업 디렉토리와 스테이징 영역의 변경사항을 스택에 임시 저장하고 워킹 트리를 마지막 커밋 상태로 되돌립니다. 이후 git stash pop이나 apply로 복원할 수 있어, 긴급하게 다른 브랜치로 전환해야 할 때 유용합니다.*
#### 3번 문항
- **Q**. 코드 리뷰에서 리뷰어가 'Request changes'를 선택했을 때 발생하는 상황으로 옳은 것은?
- **A**. Branch Protection Rules 설정 시, 리뷰어가 다시 Approve하기 전까지 머지가 불가능하다
- *Request changes는 버그, 보안 이슈, 설계 문제처럼 머지 전 반드시 수정이 필요한 경우 사용하는 액션입니다. Branch Protection Rules가 설정되어 있다면 리뷰어가 재확인 후 Approve하기 전까지 머지가 차단되어, 문제 있는 코드가 실수로 배포되는 것을 막아줍니다.*
#### 4번 문항
- **Q**. PR 본문에 'Closes #12'와 같이 특정 키워드와 Issue 번호를 함께 작성하면, PR이 머지될 때 자동으로 일어나는 동작은 무엇인가? (한 단어 또는 짧은 문장으로 답하시오)
- **A**. 이슈 해소
- *PR 본문에 Closes, Fixes, Resolves 등의 키워드와 Issue 번호를 함께 작성하면 PR이 머지되는 순간 해당 Issue가 자동으로 닫힙니다. 이를 통해 어떤 작업이 어떤 문제를 해결했는지 히스토리에서 추적할 수 있습니다.*
#### 5번 문항
- **Q**. GitHub Flow와 Git Flow를 비교한 설명 중 옳은 것은?
- **A**. GitHub Flow는 브랜치 구조가 단순해 소규모·빠른 배포 주기의 팀에 적합하다
- *GitHub Flow는 main과 기능 브랜치만으로 동작하는 단순한 구조로, 소규모 팀이나 빠른 배포 주기에 적합합니다. 반면 Git Flow는 main, develop, feature, release, hotfix 등 복잡한 브랜치 구조를 가지며 중대형 팀의 버전 관리에 적합하고, 대형 팀의 짧은 주기 CI/CD 통합에는 Trunk-based Development가 더 적합합니다.*
