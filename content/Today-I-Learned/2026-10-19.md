## 강제 규칙 (어기면 에러)

- **`"use server"` 파일은 async 함수만 export할 수 있습니다.** 상수, 타입이 아닌 값, 동기 함수는 export하면 안 됩니다. 타입(`type`, `interface`) export는 컴파일 때 사라져서 괜찮습니다.
- **인자와 반환값은 직렬화 가능한 값이어야 합니다.** 문자열, 숫자, 배열, 일반 객체, `FormData`는 되고, 함수, 클래스 인스턴스, 심볼은 안 됩니다.
- **`"use server"`는 파일 맨 위나 함수 본문 첫 줄에 둬야 합니다.** 함수 안에 인라인으로 쓰는 건 서버 컴포넌트에서만 가능합니다.

## 관례 (지키면 좋은 것)

- **서버 액션은 공개 HTTP 엔드포인트라고 생각해야 합니다.** 호출은 POST 요청으로 갑니다. 그래서 함수 안에서 매번 인증과 권한을 확인해야 합니다. UI에서 버튼을 숨기는 것만으로는 막히지 않습니다.
- **입력값은 서버에서 다시 검증합니다.** zod 같은 스키마로 검증하세요. 클라이언트 검증은 믿으면 안 됩니다.
- **에러는 던지지 말고 결과 객체로 반환합니다.** 예: `{ success: false, error: "..." }`. 던진 에러는 프로덕션에서 메시지가 가려지고, 사용자에게 보여줄 수 없습니다. 예상 못 한 오류만 던지세요.
- **쓰기 작업 뒤에는 캐시를 갱신합니다.** `revalidatePath`, `revalidateTag`로 갱신하고, 이동은 `redirect`로 합니다. `redirect`는 내부적으로 예외를 던지므로 `try/catch` **밖**에서 호출하세요.
- **파일을 분리합니다.** `actions/` 폴더에 `*.actions.ts`로 모으고 맨 위에 `"use server"`를 둡니다. 지금 프로젝트의 `domains/auth/actions/signup.actions.ts`가 이 구조입니다.
- **조회(GET)용으로 쓰지 않습니다.** 서버 액션은 변경 작업용이고, 같은 컴포넌트에서 호출하면 순차 실행됩니다. 데이터 조회는 서버 컴포넌트에서 직접 하거나 Route Handler를 쓰세요.
- **폼에서는 `useActionState`를 씁니다.** 보류 상태와 반환된 에러를 처리하기 쉽습니다. 로딩 표시는 `useFormStatus`를 쓰세요.
- **비밀 값은 서버 액션 안에서만 사용합니다.** `process.env`의 비밀 키가 클라이언트 번들로 새지 않게, `NEXT_PUBLIC_` 접두사가 없는 변수만 쓰세요.

## 컴포넌트도 함수입니다

React 컴포넌트는 props를 받아 UI(JSX)를 반환하는 함수입니다. 그래서 "함수가 컴포넌트 역할을 한다"는 생각 자체는 틀리지 않습니다. 다만 모든 함수가 컴포넌트는 아닙니다.

## 구분하는 기준

||컴포넌트|서버 액션|일반 함수|
|---|---|---|---|
|반환값|JSX(화면)|데이터/결과 객체|아무 값|
|호출 주체|React가 렌더링할 때|이벤트·폼 제출|내가 직접|
|실행 위치|서버 또는 클라이언트|**서버에서만**|어디서나|
|이름|대문자 시작 (`SignInForm`)|동사형 (`signUp`)|동사형 (`formatDate`)|
|쓰는 방법|`<SignInForm />`|`action={signUp}` 또는 `signUp(data)`|`formatDate(d)`|

## 왜 구분해야 하나

- **호출 방식이 다릅니다.** 컴포넌트는 `SignInForm()`처럼 직접 호출하지 않고 `<SignInForm />`으로 씁니다. React가 훅 상태, 리렌더링, 생명주기를 관리하기 때문입니다.
- **훅을 쓸 수 있는 곳이 다릅니다.** `useState` 같은 훅은 컴포넌트나 커스텀 훅 안에서만 쓸 수 있습니다. 서버 액션이나 일반 함수에서는 쓸 수 없습니다.
- **실행 위치가 다릅니다.** 서버 액션 안의 코드는 서버에서만 돕니다. 그래서 DB 접근, 비밀 키 사용이 가능합니다. 클라이언트 컴포넌트(`"use client"`)에는 이런 코드를 넣으면 안 됩니다.
- **async 여부가 다릅니다.** 서버 액션은 반드시 async여야 합니다. 클라이언트 컴포넌트는 async로 만들 수 없습니다. async 컴포넌트는 서버 컴포넌트에서만 가능합니다.


양식 처리에 대한 상태 관리 
useActionState(…)
- 서버액션 컴포넌트 반환값(state)
- formAction에 연동할 함수
- 비동기식 ─ 양식 처리 상태값(boolean)

is_Pending
## 역할

서버에 요청을 보내고 응답을 기다리는 동안 UI에 반영하는 데 씁니다.

- 제출 버튼을 비활성화해서 **중복 제출을 막습니다.**
- "가입 중..." 같은 **로딩 표시**를 보여줍니다.
- 입력창을 잠가서 제출 중에 수정하지 못하게 합니다.

## 작동 원리

1. 처음에는 `isPending = false`입니다.
2. 사용자가 제출하면 `<form action={formAction}>` 때문에 React가 `FormData`를 모아 `signUpAction(prevState, formData)`를 호출합니다.
3. 서버 액션이 끝나기 전까지 `isPending = true`가 되고, 컴포넌트가 리렌더링됩니다. 이 시점에 버튼을 비활성화할 수 있습니다.
4. 서버 액션이 결과를 반환하면 그 값이 새 `state`가 되고 `isPending`은 다시 `false`가 됩니다. 컴포넌트는 한 번 더 리렌더링됩니다.

즉 React가 서버 액션 호출을 **트랜지션(transition)**으로 감싸서 진행 상태를 추적해 주는 겁니다. `useState`로 `loading`을 직접 만들고 `try/finally`로 켜고 끄는 코드가 필요 없습니다.

## 비교

|`useActionState`의 `isPending`|`useFormStatus`의 `pending`|
|---|---|---|
|import|`react`|`react-dom`|
|호출 위치|폼을 가진 컴포넌트|`<form>`의 **자식** 컴포넌트|
|하는 일|액션 연결 + 상태 + 진행 여부|진행 여부만 읽음|
|반환값|`[state, formAction, isPending]`|`{ pending, data, method, action }`|
|액션 결과(`state`)|받을 수 있음|받을 수 없음|
|필요한 구조|컴포넌트 하나로 충분|버튼용 자식 컴포넌트를 따로 만들어야 함|

핵심 차이는 `useFormStatus`가 **부모 `<form>`의 상태를 읽기만 한다**는 점입니다. 폼과 같은 컴포넌트에서 호출하면 부모 폼이 없어서 항상 `pending: false`입니다.

## 예시 1: `useActionState`, 폼 하나에서 다 처리

- **에러 메시지 표시와 로딩 표시를 한 곳에서** 하는 경우에 맞습니다.
- 서버 액션이 돌려준 에러(`state`)와 진행 여부(`isPending`)를 한 컴포넌트에서 씁니다.
- 파일이 하나라서 단순합니다.

## 예시 2: `useFormStatus`, 재사용 가능한 제출 버튼

- **로딩 표시 버튼을 여러 폼에서 공유**하고 싶을 때 맞습니다. 폼마다 `isPending`을 props로 내려주지 않아도 됩니다.
- `<form>` 안에 들어 있는 자식이라서 동작합니다.
- 폼이 5개여도 버튼 컴포넌트는 하나만 만들면 됩니다.
- ## 흔한 실수

```tsx
// 동작하지 않음: 같은 컴포넌트가 <form>을 직접 렌더링하므로 부모 폼이 없음
function Form() {
    const { pending } = useFormStatus();   // 항상 false
    return <form action={action}><button disabled={pending}>제출</button></form>;
}
```

## 선택 기준

- 에러나 결과 메시지도 화면에 보여줘야 한다면 `useActionState`를 쓰면 됩니다.
- 여러 폼이 같은 로딩 버튼을 공유한다면 `useFormStatus` 기반 `SubmitButton`이 맞습니다.
- 지금 프로젝트처럼 폼이 `SignInForm`, `SignUpForm` 두 개이고 둘 다 `useActionState`를 쓰고 있다면, 그대로 `isPending`을 쓰는 게 가장 간단합니다.
