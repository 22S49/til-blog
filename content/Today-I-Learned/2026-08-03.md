### 연습장
#### Git 설치
- master는 인종차별적 표현으로 읽히는 경우가 있어서 최근 커뮤니티에서는 main을 많이 사용 (GitHub)
- 보통 서버에 올릴 떄는 리눅스 문법을 사용하는데, 윈도우 환경에서 코드를 작성하면 더 붙는 게 있음 (Enter) 
- 그래서 Git 설치 시 자동으로 변경해서 적용될 수 있도록 설정하는 단계가 있음
#### DOS 명령어
- 화면 지우기: cls
- 디렉토리 변경: cd
- 파일 미리보기: type
- 파일 목록보기: dir (/w 가로로 넓게 보기)
- 현재 위치: .
- 상위 위치: ..
- 상상위 위치: ..\..
- 폴더 생성하기: mkdir
- 자동완성: 헤드 스펠링 + tab
- 빠져 나가기: q
- 빈 파일 만들기

| 명령어 (예시)             | 결과                             |
| -------------------- | ------------------------------ |
| `type nul > main.py` | 완전히 0바이트 빈 파일                  |
| `echo. > main.py`    | 개행 문자 하나 들어간 파일 (거의 0바이트에 가까움) |
| `echo > main.py`     | `echo.`와 사실상 동일 (빈 줄 하나)       |
| `echo 내용 > main.py`  | "내용"이라는 텍스트가 들어간 파일            |
#### Git 설정 범위
- git config 뒤에 오는 옵션
	- --global: 현재 사용자의 전역에 (모든 경로에) 접근 가능
	- --system: 모든 사용자의 전역에 (모든 경로에) 접근 가능
	- -- local: 특정 경로만 (특정 저장소만)
	- 적용 우선순위: local > global > system
		- PC를 공유하지 않기 때문에 local 쓸 일은 많이 없지만 우선순위가 어떻게 지정되는지 이해 필요

#### Git
- 소프트웨어, 형상관리(버전관리) 도구
- 변경사항이 아니라 파일 자체를 (파일 그대로) 기록 (스냅샷) 
	- 계산보다는 용량의 문제가 있을 수 있는 것 아닌지? 
	- 변경된 파일만 복구하기 때문에 용량적인 부분들도 문제 없음 
	- 파일 위치만 변경해서 시점을 복구하기 때문에 훨씬 빠르게 복구 가능
1. 버전 관리를 디렉토리로 관리: working directory (버전관리의 영향을 받는 경로)
	- 워킹 디렉토리 생성 명령어: git init
	- working directory = main
2. 스테이징 단계: 기록하기 전에 준비하는 단계 (기록하기 위한 준비 단계)
	- 기록할 파일이 뭔지 알려주는 단계
	- git add <파일명>
		- .git 폴더 내 index에 기록됨
	- 변경사항 모두 스테이징: git add .
		- 원치 않는 파일로 올라 갈 가능성 있음
		- 관리가 되면 안 되는 파일도 있을 수 있음 
3. 커밋 단계: 스냅삿 찍고 실제로 버전이 기록되는 단계
	- git commit -m "메세지"
	- 시점을 기록해서 복구할 때 잘 찾기 위함
	- 필수로 기록에 메시지를 남겨야 함 (메세지는 관례가 있긴 함)
	- .git 폴더 내 objects 폴더에 변경 내용에 대한 것이 기록됨 (파일 자체의 코드)
	- 코드에 대한 HEAD를 기록하면서 버전을 바꾼다 ⇢ 바뀌지 않은 파일들은 생성되지 않음 (용량관리방법)
	- add 하면서 commit 하기: git commit -a -m "메세지"
- 기록 확인: git log
	- 기본 log는 HEAD가 위치한 이하 내역만 보여줌. 그리고 가독성 좋게 변경할 수 있음
	- 한 줄로 보기: -- oneline
	- 브랜치 흐름 보기(시각화): --graph 
		- 줄기는 * 표기로 나타남 
	- 짧게 요약 보기: --decorate
		- 해시코드가 짧게 줄어듦
	- 모든 해시 보기: --all
	- 가장 최근 몇 개 해시만 보기: -n(숫자)
- 시점 변경: HEAD 태그가 현재 우리가 있는 위치. HEAD의 위치를 바꿔야 복구가 되는 것
	- HEAD = 글쓰기 할 때 커서의 위치와 같은 개념 
	- 커밋되어 있는 해시 아이디를 이용해서 특정 시점으로 이동 (기본)
	- git checkout "커밋ID"
- git hash-object MEMBER.md
	- 4bdfc04e924e853a3776e559c513fa90e222d875
	- 앞 두자리는 폴더, 그 뒷 코드가 파일명, 변경사항 발생 시마다 변경됨 
- git diff --staged
	- 스테이징된 파일 이전 버전과 차이 한 눈에 보기 ⇢ 아직 적용이 된 건 아니고 스테이징만 된 상태
- cf. 레거시 형상관리 도구: CVS, SVN, …
	- 코드의 변경사항들을 기록
	- 코드 변경 시 계산 후 복구
	- 계산량이 많아지면 속도가 느려지고 성능 상의 이점이 없어짐 


### 오늘의 퀘스트

#### 1번 문항

- **Q**. Git의 3영역 모델에서 'git add'와 'git commit' 명령어가 각각 변경 사항을 이동시키는 방향으로 옳은 것은?
- **A**. add: Working Directory → Staging Area, commit: Staging Area → Repository
- *git add는 작업 디렉터리의 변경 사항을 스테이징 영역으로 올리고, git commit은 스테이징된 내용을 저장소에 스냅샷으로 영구 저장합니다. 이 흐름을 이해하는 것이 Git의 기본 동작 원리를 파악하는 핵심입니다.*
#### 2번 문항

- **Q**. Git은 커밋 시 파일의 차이(diff)를 저장하는 것이 아니라, 커밋 시점의 모든 파일 상태를 사진처럼 저장하는 방식을 사용합니다. 이 저장 방식을 부르는 용어는 무엇인가요?
- **A**. snapshot
- *Git은 diff 기반이 아닌 스냅샷 기반으로 커밋을 저장합니다. 변경이 없는 파일은 이전 스냅샷을 재사용하여 저장 공간 낭비 없이 각 커밋 시점의 전체 상태를 기록합니다.*
#### 3번 문항

- **Q**. 중앙 집중식 버전 관리(CVCS)와 비교했을 때, Git과 같은 분산 버전 관리(DVCS)의 특징으로 옳은 것은?
- **A**. 모든 참여자가 전체 이력을 로컬에 보유하므로 오프라인 작업과 빠른 속도가 가능하다
- *Git은 분산 방식(DVCS)으로, 모든 개발자가 저장소의 전체 이력을 로컬에 복사해 보유합니다. 이 덕분에 서버 장애 시에도 이력이 보존되고, 인터넷 없이도 로컬에서 작업이 가능하며 속도도 빠릅니다.*
#### 4번 문항

- **Q**. git config의 적용 범위는 system, global, local 세 가지가 있습니다. 동일한 설정 항목에 대해 global과 local이 동시에 설정되어 있을 때, 실제로 적용되는 범위는 무엇인가요?
- **A**. local
- *git config의 범위는 system < global < local 순으로 좁을수록 우선순위가 높습니다. 따라서 local 설정이 존재하면 global 설정보다 local 설정이 우선 적용됩니다.*
#### 5번 문항

- **Q**. 개인 개발자의 노트북에서 GitHub 인증 방식으로 SSH 키가 Personal Access Token(PAT)보다 편리하다고 설명되는 주된 이유는?
- **A**. SSH 키는 만료가 없어 한 번 설정하면 계속 사용할 수 있기 때문이다
- *SSH 키가 설정은 다소 복잡하지만 만료 없이 계속 사용할 수 있어 개인 개발 머신에 적합합니다. 반면 PAT는 설정이 간단하지만 만료일이 있어 CI/CD 같은 자동화 환경에 더 적합합니다. 인증 방식의 선호도는 사람마다 견해 차이가 있을 수 있습니다.*
